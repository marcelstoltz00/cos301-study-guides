Architecture

Monolithic architecture

One application, one deployment.

In easy terms

Think of one shop with several departments under one roof. Orders, products and payments are all handled inside the same running application. The code can still be neatly organised, but a release normally replaces the application as a whole.

Follow the diagram

A customer sends an order from the client. The application checks products, calculates the total and handles payment, then saves the result in its database. Calls between its internal parts do not need to cross a network.

What each part does

Client
The screen or program the customer uses. It sends requests and displays the results.
One application · Orders + Products + Payments
Runs the order, product and payment rules together. Coordinates the work and decides which information to read or save.
Application database
Keeps information after the application stops, such as products, orders and payment records.
How to draw it and when to choose it

Draw in this order

  1. Draw a client.
  2. Draw one application boundary with the capabilities inside.
  3. Connect that application to its database.

Use it when

Small teams or closely related capabilities with one release cycle.

Cost / trade-off

Deployment and scaling generally move the whole application.

Common exam mistake

One deployable does not mean one physical server: replicas can improve availability.

Architecture

Modular monolith

Many internal modules, one deployable.

In easy terms

This is one application divided into clearly defined departments. Each module owns one business job and offers an agreed way for other modules to ask it for help. Everything is still released together, so you get clearer code without running many separate services.

Follow the diagram

The client starts an order. The order module asks the inventory module about stock; the illustrated internal calls also reach the payment module. Saved information goes into storage. The storage arrow is an example connection, rather than a rule that only inventory may save data.

What each part does

Client
Sends the customer’s request and shows its result.
Orders module · Public interface
Creates and manages orders. Its public interface is the set of operations other modules are allowed to call.
Inventory module · Public interface
Checks, reserves and updates available stock through its public interface.
Payments module · Public interface
Handles charging and refunding through its public interface.
Saved information
Keeps the modules’ saved information. Clear ownership rules should prevent modules from changing each other’s records directly.

Dashed enclosures: The large enclosure is one running application released as a unit. The separate boxes inside it are code modules, rather than independent network services.

How to draw it and when to choose it

Draw in this order

  1. Draw one deployable application boundary.
  2. Place business modules and their public interfaces inside.
  3. Connect modules through interfaces; add persistence below.

Use it when

Maintainable boundaries without distributed operational overhead.

Cost / trade-off

Modules cannot normally deploy or scale independently.

Common exam mistake

Separate folders do not enforce a boundary; callers must use public interfaces.

Architecture

Layered architecture — four layers

Stack responsibilities; stay inside the next layer.

In easy terms

Think of a stack of helpers, each with a different job. The screen handles interaction, business code decides what is allowed, storage-access code translates requests into database operations, and the database keeps the information. These are divisions of responsibility in the code, even if they all run on one machine.

Follow the diagram

A customer clicks Buy. The presentation layer passes the input down. The business layer checks the order rules. The persistence layer saves the order in the database. The result returns up the same path. In this strict example, a layer talks only to the layer immediately below it.

What each part does

Presentation layer
Displays information and collects user input. It should not decide business rules or issue database operations directly.
Business / domain layer
Applies the rules of the business, such as whether stock is available or a discount is allowed.
Persistence layer
Turns requests to save or retrieve business information into storage operations. Hides database details from business code.
Database layer
Stores records and carries out the requested reads and writes.
How to draw it and when to choose it

Draw in this order

  1. Stack Presentation above Business.
  2. Add Persistence and Database below.
  3. Draw downward calls between adjacent layers; responses return through the call path.

Use it when

Clear separation of concerns in a conventional business application.

Cost / trade-off

Strict layering adds indirection; rules can become coupled to storage if boundaries leak.

Common exam mistake

Layers describe code organisation, not separate machines.

Architecture

Tiered architecture — three tiers

Split runtime placement: client → server → database.

In easy terms

Think of three places where the system runs: the customer’s browser, an application server and a database server. Requests travel between these places over a network. Unlike layers, tiers describe where parts run, rather than just how code is organised.

Follow the diagram

The browser sends a request to the application server and waits for a reply. The server checks the business rules, asks the database server to read or save information, then returns a result to the browser. Any network link can be slow or fail independently.

What each part does

Browser interface
Shows the interface and collects input on the customer’s device.
Application server · Business logic · + persistence
Processes requests, applies business rules and accesses saved information on behalf of the browser.
Database server
Hosts and protects the saved records. Answers database requests from the application server.

Dashed enclosures: The three enclosures are separate places where parts run. A network request crosses from one tier to another; they are not simply folders in the code.

How to draw it and when to choose it

Draw in this order

  1. Draw separate Client, Application-server and Database-server enclosures.
  2. Place the browser, application and database in their respective tiers.
  3. Label the network links with protocol and timing.

Use it when

Separating presentation, application processing and data hosting.

Cost / trade-off

Network latency, connection management and partial failures.

Common exam mistake

Three code folders do not prove three deployment tiers.

Architecture

Client–server

Client asks; server provides.

In easy terms

Several clients ask one shared server for a service. A client is the program making a request; a server is the program answering it. This diagram describes their relationship, without specifying how the server’s code is organised inside.

Follow the diagram

A browser or mobile application asks the server for information or an action. The server performs the work and sends back a result. Both clients can use the same service instead of maintaining separate copies of the business logic.

What each part does

Web client
Lets a person access the service through a browser. Sends requests and displays replies.
Mobile client
Lets a person access the same service through a mobile application.
Shared server
Provides the shared capability, processes requests and returns results. Its capacity must support the clients using it.
How to draw it and when to choose it

Draw in this order

  1. Draw two clients on the left.
  2. Draw a shared server on the right.
  3. Draw labelled request arrows to the server; returned results use the same communication path.

Use it when

Shared services accessed by multiple clients.

Cost / trade-off

The server is a dependency; capacity and availability need an explicit design.

Common exam mistake

This shape does not tell you whether the server is internally layered or microservice-based.

Architecture

Microservices

Capability → service → own data.

In easy terms

Think of separate specialist businesses cooperating. One service handles orders, another products and another payments. Each can be changed and released separately, and each controls its own saved information. They communicate through agreed messages or requests instead of freely changing one another’s database tables.

Follow the diagram

The client sends a secure web request to the gateway, which forwards it to the appropriate service. The chosen service performs its own job and reads or writes its own database. Cooperation between services needs additional agreed interactions; the gateway does not replace those business rules.

What each part does

Client
Collects user input and sends requests to the system.
Request gateway
Provides an entry point and forwards requests to the right service. It may also check access or limit excessive traffic.
Orders service
Creates and manages orders. Owns the meaning and rules of order information.
Products service
Manages product details and the rules for changing them.
Payments service
Handles payment actions and payment results.
Orders database
Stores order information. Other services request it through the order service instead of editing these records directly.
Products database
Stores product information under the product service’s control.
Payments database
Stores payment information under the payment service’s control.
How to draw it and when to choose it

Draw in this order

  1. Draw a client and a request gateway.
  2. Draw capability services with separate owned stores.
  3. Connect services through agreed requests or events; avoid direct access to another service’s tables.

Use it when

Independent teams, release needs or very different scaling demands, with distributed operating capacity.

Cost / trade-off

Remote failures, eventual consistency, tracing, deployment and data-management overhead.

Common exam mistake

Separate processes sharing writable tables can form a distributed monolith.

Architecture

Event-driven architecture

Publish a fact; interested consumers react.

In easy terms

An event is a message saying something has happened, such as “an order was placed”. The sender announces the fact, and interested parts react to it. The sender does not have to wait for every reaction to finish. Different reactions may finish at different times.

Follow the diagram

The order service publishes an order-placed message. The broker delivers a copy to each interested consumer. Shipping prepares delivery, email sends a notification and analytics updates reports. Consumers need rules for handling duplicate messages safely.

What each part does

Order service
Creates the order and announces that it was placed.
Event broker / topic
Receives events and delivers them to interested consumers. A topic is a named channel grouping related events.
Shipping consumer
Listens for order events and starts delivery-related work.
Email consumer
Listens for order events and sends customer notifications.
Analytics consumer
Listens for order events and updates reporting information.
How to draw it and when to choose it

Draw in this order

  1. Draw a producer, then a broker/topic.
  2. Fan out dashed arrows to separate consumers.
  3. Name the event and label asynchronous delivery.

Use it when

Multiple reactions to one fact, extensible processing and temporary burst buffering.

Cost / trade-off

Lag, duplicate delivery, ordering, schema compatibility and difficult cross-service debugging.

Common exam mistake

Events describe what happened; commands request an action. A queue alone does not make work durable.

Architecture

Service-oriented architecture

Consumers → mediation → business services.

In easy terms

Existing business systems expose useful operations as services so other applications can reuse them. In this example a central enterprise service bus helps systems communicate by routing requests and translating formats. It is useful when old and new systems need to work together.

Follow the diagram

The portal or another application requests a business operation. The service bus sends the request to billing, identity or the older finance system, translating messages when necessary. Each service does its own business work and returns a result through the agreed interface.

What each part does

Portal consumer
Provides a user-facing application that requests shared business services.
Other application
Another system that reuses the same services instead of implementing them again.
Enterprise service bus · Routing and translation
Routes requests and translates message formats or communication methods. It connects systems; business responsibility remains with the services.
Billing service
Calculates bills and manages billing operations.
Identity service
Provides shared identity operations, such as checking who a user is.
Legacy finance service
Exposes finance operations from an older system through an agreed service interface.
How to draw it and when to choose it

Draw in this order

  1. Draw business consumers at the top.
  2. Draw an enterprise service bus / mediation layer in the middle.
  3. Draw business services underneath and label their contracts.

Use it when

Enterprise integration across existing systems and protocols.

Cost / trade-off

A central bus can concentrate complexity, coupling and failure.

Common exam mistake

A central service bus and a formal web-service messaging protocol are common choices, but are not requirements of every service-oriented design.

Architecture

Command and query responsibility segregation

Write one way; read another.

In easy terms

Use one path for changing information and another for reading it. A command asks for a change, such as “place this order”. A query asks for information, such as “show my orders”. The reading side can keep a convenient copy shaped for screens or reports.

Follow the diagram

The client sends a change to the command handler, which checks it and updates the write store. A later update refreshes the read copy. Requests to view information go through the query handler to that copy. In this illustrated arrangement, a screen may briefly show old information while the copy catches up.

What each part does

user interface / client
Sends change requests or asks to display information.
Command handler
Checks whether a requested change is allowed and applies it to the write model.
Query handler
Answers read-only questions without changing the business information.
Write model / store
Holds the authoritative information used when making changes.
Read projection / store
Holds information arranged for convenient reading. It is a derived copy in this example, so it may lag behind the write store.
How to draw it and when to choose it

Draw in this order

  1. Draw a user interface splitting into Command and Query paths.
  2. Connect commands to the write model and queries to the read model.
  3. Show the write-side event/update feeding the read projection; label its delay.

Use it when

Read-heavy dashboards or very different read and write models.

Cost / trade-off

Projection lag and duplicated modelling/maintenance.

Common exam mistake

command and query responsibility segregation does not require two databases or event sourcing. Here two stores are an explicit example choice.

Architecture

Event sourcing

Store the history; rebuild current state.

In easy terms

Keep the history of meaningful changes as the main record. Instead of only saving “the account balance is 80”, save changes such as “100 deposited” and “20 withdrawn”. The present state can be rebuilt by applying those changes in order.

Follow the diagram

The command handler checks an action and appends the resulting event to the event store. The projector reads those events in order and builds a current-state view. Replaying the history can rebuild that view; it must not send the original payments or emails again.

What each part does

Command handler
Validates the requested action and decides which business events should be saved.
Event store · Ordered domain history
Keeps the ordered, authoritative history of business events.
Replay / projector
Applies the recorded events to calculate current information. Can rebuild derived information from the history.
Current-state view
Shows the calculated present situation, such as an order’s current status or an account’s balance.
How to draw it and when to choose it

Draw in this order

  1. Draw a command handler appending domain events.
  2. Draw the event store as the authoritative history.
  3. Draw replay/projection into current state; show a reader of that state.

Use it when

Business history, auditability and reconstructing prior state where its added complexity is justified.

Cost / trade-off

Event versioning, replay correctness, ordering and snapshot/projection management.

Common exam mistake

An event-driven system need not use event sourcing; an ordinary audit log is not automatically the authoritative event store.

Architecture

Model–view–controller

Input → controller → model; view displays.

In easy terms

Separate handling input, business information and displaying output. The controller decides what to do with the input. The model represents business information and rules. The view displays a result. This makes it easier to change the screen without rewriting the business rules.

Follow the diagram

A person submits an action. The controller asks the model to perform the relevant work, then selects or coordinates the view. The view uses model data to display the result. This is one common interaction arrangement; other implementations can update the view differently.

What each part does

User input
The action entered by a person, such as submitting a form or clicking a button.
Controller
Receives input, chooses the operation to run and coordinates the resulting display.
Model · Domain + state
Holds business information and behaviour. Applies rules independently of how the screen looks.
View · Rendered output
Renders the information as the screen or page the person sees.
How to draw it and when to choose it

Draw in this order

  1. Place a user/input entry, Controller, Model and View.
  2. Draw input to Controller and action to Model.
  3. Draw model data to View; Controller selects/coordinates the view.

Use it when

Separating input handling, business state and presentation.

Cost / trade-off

Responsibility can drift into a large controller or business-heavy view.

Common exam mistake

model–view–controller variants differ in update flow; a folder called Controller does not prove the separation.

Architecture

Model–view–presenter

View reports actions; presenter drives the view.

In easy terms

The view focuses on showing things and reporting user actions. A presenter does the thinking needed to coordinate that screen: it asks the model for work, prepares the result and explicitly tells the view what to display.

Follow the diagram

A button click travels from the view to the presenter. The presenter calls the model, receives the result and tells the view how to update. The screen can be replaced by a simple test substitute when checking presenter behaviour.

What each part does

View
Displays information and passes user actions to the presenter. Keeps presentation decisions minimal.
Presenter
Coordinates the screen’s behaviour, requests business work and explicitly updates the view.
Model
Provides business information and rules without depending on the screen.
How to draw it and when to choose it

Draw in this order

  1. Draw View, Presenter and Model.
  2. Connect View → Presenter for user actions.
  3. Connect Presenter → Model for work and Presenter → View for explicit display updates.

Use it when

Testable presentation logic with a relatively passive view.

Cost / trade-off

Extra interfaces and synchronising view updates.

Common exam mistake

The presenter coordinates behaviour; it is not merely a rendered template.

Architecture

Model–view–view-model

View binds to viewmodel state + commands.

In easy terms

A view model holds information in a form the screen can directly use, together with actions the screen can invoke. Binding means connecting a displayed value to a view-model value so changes can update the screen automatically.

Follow the diagram

The person activates an action in the view. The view model calls the model to do business work and updates its display-ready information. The binding connection reflects that change in the view, instead of the view model manually updating every screen element.

What each part does

View
Displays values from the view model and connects user actions to its available commands.
ViewModel · State + commands
Prepares screen-ready values, tracks presentation state and exposes actions. Uses the model for business work.
Model · Domain behaviour
Owns business information and rules, independently of the displayed screen.
How to draw it and when to choose it

Draw in this order

  1. Draw View, ViewModel and Model.
  2. Label View ↔ ViewModel with binding/state and commands.
  3. Connect ViewModel to Model for domain operations.

Use it when

Interfaces with significant reactive state and testable presentation transformations.

Cost / trade-off

Binding/debugging complexity and keeping business rules out of the view model.

Common exam mistake

Using a frontend framework alone does not make the implementation model–view–view-model.

Architecture

Model–view–template

Django view coordinates; template renders.

In easy terms

This example builds a web page on the server. A router chooses which request-handling function should run. In Django that function is called a view. It gets information from the model and passes it to a template, which creates the page.

Follow the diagram

The browser requests a page. The address router selects the Django view. The view reads or changes model information and supplies values to the template. The template produces the rendered page, which the server sends back to the browser. The return arrow summarises that response.

What each part does

Browser
Requests a page and displays the returned page to the person.
web address router
Matches the requested web address to the correct view function.
Django View
Handles the request, performs the appropriate model work and chooses the template and values to supply.
Model
Represents business information and provides the operations for accessing or changing it.
Template
Defines the page layout and inserts the values supplied by the view. Produces the page content, rather than deciding the business rules.
How to draw it and when to choose it

Draw in this order

  1. Draw browser → web address router → Django View.
  2. Connect the View to the Model.
  3. Draw View → Template for context, then Template → browser for the rendered response.

Use it when

Server-rendered, content-oriented applications.

Cost / trade-off

Complex client-side interactions may require additional frontend state management.

Common exam mistake

The Django View is controller-like; Template is the renderer. Do not swap these roles.

Architecture

Coordinator / master–worker

One coordinator distributes work to many workers.

In easy terms

Split a large job into smaller tasks and give them to several workers. A coordinator decides who does what and collects the results. Workers can process independent tasks at the same time, which can shorten the overall job.

Follow the diagram

The task source submits a job. The coordinator assigns tasks to workers, tracks completion and collects their results. If a worker fails, the coordinator can reassign its task. Repeated tasks must be safe, and the coordinator itself needs a recovery plan.

What each part does

Task source
Provides the job that needs to be processed.
Coordinator
Splits or schedules work, assigns tasks, tracks progress and collects results.
Worker 1
Performs an assigned task and returns its result.
Worker 2
Performs another assigned task, potentially at the same time as the other workers.
Worker 3
Provides additional processing capacity and reports its task result.
How to draw it and when to choose it

Draw in this order

  1. Draw one coordinator and several workers.
  2. Fan task arrows out to workers.
  3. Label returned results and describe how failed tasks are retried safely.

Use it when

Parallel independent processing tasks.

Cost / trade-off

Coordinator bottleneck/failure, scheduling and duplicate task recovery.

Common exam mistake

Parallel workers do not remove a single coordinator failure dependency.

Supporting pattern

Saga with orchestration

Local commits + business compensation.

In easy terms

A saga is a business process spread across services, where each step saves its own changes. A coordinator tracks the steps. If a later step fails, earlier steps may need a compensating action, such as releasing stock or refunding money.

Follow the diagram

First reserve inventory, then charge the customer, then confirm the order. If payment fails, release the inventory. If confirmation fails after payment succeeds, the workflow may refund the customer and release stock. Compensation is new business work and can also fail; it does not magically erase the past.

What each part does

Saga coordinator
Tracks which steps succeeded, decides the next step and arranges compensation or recovery when something fails.
1. Reserve inventory · Own local transaction
Reserves stock using its own saved changes. Releases that reservation when compensation is required.
2. Charge payment · Own local transaction
Charges the customer and records the result. Refunds a successful charge when the workflow requires it.
3. Confirm order · Own local transaction
Finalises and records the order once the earlier steps permit confirmation.
How to draw it and when to choose it

Draw in this order

  1. Draw a Saga coordinator.
  2. Connect reserve, charge and confirm participants with numbered actions.
  3. Label compensation paths: release reservation / refund when final confirmation fails.

Use it when

Workflows across independently owned stores, such as booking and payment.

Cost / trade-off

Compensation can fail or be impossible; reconciliation and idempotency are necessary.

Common exam mistake

Refund is a new business action, not erasing every consequence of the original payment.

Supporting pattern

Event choreography

No central boss; services react to facts.

In easy terms

Services cooperate by reacting to events instead of following instructions from one central workflow controller. Each service owns its reaction and publishes the outcome. The broker moves messages; it does not decide the business sequence.

Follow the diagram

The order service announces that an order was created. Inventory reacts by reserving stock and announcing success or failure. Payment reacts to a successful reservation and publishes its payment result. Completing the wider order process also needs subscribers for those results and explicit rules for failures and compensation.

What each part does

Order service
Creates an order and publishes the starting event. The wider design must specify how order status is updated from later outcomes.
Event broker
Delivers published events to the interested services. Does not own the business workflow decisions.
Inventory service
Reacts to order creation, attempts a reservation and publishes the result. Owns inventory recovery rules.
Payment service
Reacts to a successful reservation, attempts payment and publishes the result. Owns payment and refund rules.
How to draw it and when to choose it

Draw in this order

  1. Draw services around an event broker.
  2. Label each publication and reaction.
  3. Write who handles failure and compensation; do not hide those responsibilities in the broker.

Use it when

Loosely coupled workflows with clear event ownership and manageable coordination.

Cost / trade-off

Harder global tracing, cycles and ambiguous failure/compensation ownership.

Common exam mistake

Choreography is not simply orchestration with the coordinator renamed Event Bus.

Supporting pattern

Slow-dependency resilience

Bound calls; keep accepted work; resolve pending state.

In easy terms

Protect the application when a service it depends on becomes slow. A timeout stops waiting after a limit. A circuit breaker temporarily stops calls to a failing service. A bulkhead limits how many calls can be active, preserving capacity for other work. Accepted unfinished work is saved so it can be completed later.

Follow the diagram

Checkout attempts a protected payment call. If it cannot obtain a clear result, it keeps a pending record and an outgoing message together, then forwards the message to a saved queue. A worker checks the payment outcome and retries only when appropriate. The same operation identifier must be used for the initial attempt and retries to avoid charging twice.

What each part does

Checkout handler
Receives checkout requests and returns a clear completed or pending status. Must preserve accepted work and its operation identifier.
Timeout + breaker · Bounded bulkhead
Limits waiting time and simultaneous calls. Stops repeated calls temporarily when the provider is failing.
External payment service
Performs the actual payment and reports its outcome. Must support safe repeated requests or a way to check earlier outcomes.
Pending record · + message outbox
Saves the pending business record and outgoing message together, so neither is saved without the other. An outbox is the saved list of messages still to send.
Durable queue
Keeps unfinished work until a worker handles it. Delivery can repeat, so processing must tolerate duplicates.
Worker + result checking · Stable operation identifier
Checks uncertain outcomes, performs limited retries and updates the final result. Uses one stable identifier for the same operation; retries also need the waiting and capacity limits.
How to draw it and when to choose it

Draw in this order

  1. Draw the checkout handler, protection against slow calls and the external payment service.
  2. Draw pending state/outbox + queue → worker as the fallback path.
  3. Label idempotency, bounded retry and final-state reconciliation.

Use it when

Surviving a slow external payment/eligibility service without exhausting web workers.

Cost / trade-off

Pending user experience, backlog, repeated delivery and operational recovery.

Common exam mistake

Retries are unsafe without stable identity and remote-result reconciliation; a queue alone can lose accepted work before publication.

Deployment pattern

Two-zone deployment

Replicas must live in different failure domains.

In easy terms

Run copies of the application in two locations that can fail independently. A load balancer directs requests to working copies. The main database has a standby copy in the other zone so database service can be restored after a failure.

Follow the diagram

Normally both zones use the primary database, whose changes are copied to the standby. If one zone fails, traffic can go to healthy application copies. If the primary database fails, the standby must be promoted under a controlled recovery procedure. How changes are copied determines how much recent data might be lost.

What each part does

Load balancer
Checks which application copies are healthy and sends requests to them.
Application replicas · zone A
Runs application work in the first zone. Other copies can take over its traffic if that zone fails.
Application replicas · zone B
Runs application work in a separate zone so the same zone failure should not stop both sets of copies.
database primary
Normally accepts database reads and writes and copies its changes to the standby.
database standby
Keeps a copy of database changes. Becomes the active database only after controlled promotion; independent historical backups are still needed.

Dashed enclosures: Each enclosure is a location that can fail independently. Application copies and database copies are placed in different zones so one zone failure should not remove every copy.

How to draw it and when to choose it

Draw in this order

  1. Draw a load balancer and two zone enclosures.
  2. Place application replicas and primary/standby state in different zones.
  3. Label replication mode, failover and acceptable data loss and recovery time; mention independent backups.

Use it when

Availability targets requiring survival of a single zone failure.

Cost / trade-off

Extra cost, replication latency/lag and failover complexity.

Common exam mistake

Two containers on one host are not independent failure domains; replicas are not historical backups.

Deployment pattern

Blue/green deployment

Run old + new; switch traffic after validation.

In easy terms

Keep the current application version running while preparing a new version in a separate environment. Test the new environment, then switch customer traffic to it. Keeping the old environment can make a return to the previous version faster if a problem appears.

Follow the diagram

Customers initially reach the blue environment. The green environment is checked before the traffic switch sends customers to it. Both versions must understand the shared saved information. Switching back to blue can restore the old application, but cannot automatically reverse incompatible changes already made to the database.

What each part does

Traffic switch
Directs customer traffic to the chosen environment and controls the switch between versions.
Blue environment · Current version
Runs the current application version and is kept available for a possible return to it.
Green environment · New version
Runs the candidate version for checks before it receives customer traffic.
Shared saved information · Compatible with both versions
Keeps saved information in a form both versions can use. Database changes and recovery need their own compatibility plan.
How to draw it and when to choose it

Draw in this order

  1. Draw entry/traffic switch.
  2. Draw Blue (current) and Green (candidate) environments.
  3. Label traffic to Blue and the validated switch to Green; state the database compatibility assumption.

Use it when

Reducing interruption and risk during releases.

Cost / trade-off

Extra capacity and compatible shared-state/schema changes.
