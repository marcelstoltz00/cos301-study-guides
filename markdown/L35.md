## 2. High-value distinctions

| Pair | Distinction |
|---|---|
| Style guide / design system | Human-readable brand guidance / reusable implemented decisions and components |
| Entity / value object | Continuity of identity / meaning determined by value |
| Unit / integration test | Isolated responsibility / real collaboration across the claimed boundary |
| Authentication / authorisation | Who is calling / what they may do to a resource |
| QA / QC | Process assurance / artifact and product evaluation |
| Fault / failure | Latent defect / observed incorrect behaviour |
| Reliability / availability | Failure-free operation over a period / being operational when needed |
| Replication / backup | Current copies for continuity / recoverable history |
| RPO / RTO | Acceptable data-loss interval / acceptable restoration duration |
| Scalability / elasticity | Capacity for growth / adapting resource allocation to demand |
| Sync / async | Caller waits for a response / work can be deferred with coordination costs |
| Prototype / production evidence | Exploration of an idea / verified behaviour and supportability |

Many terms depend on context. For example, organisations use release and deployment terminology differently; explain the actual act of installing software versus exposing it to users. Likewise, use the supplied QA notes' explicitly stated MTBF convention in calculations.

## 3. Trace a requirement all the way to evidence

Use the L22 chain: **NFR → quality attribute → tactic → pattern → ADR → architectural design → NFR test**. An ADR records context, the decision, alternatives and consequences; it is not simply a technology inventory.

Example: “After a single-zone failure, restore checkout within ten minutes, with at most one minute of lost order data.” The quality concern is recovery and availability. Candidate tactics include cross-zone redundancy and replicated storage. Record the chosen design and consistency/latency cost. Draw the actual placement and failover path. Test an induced zone failure and compare measured restoration and missing writes to the requirement.

A claim that “we use cloud microservices” skips nearly every reasoning step. A design can support a target without yet proving that the target is achieved.

## 4. Worked calculations

### Reliability and availability

For operating periods 180, 220 and 200 hours and repairs 3, 5 and 4 hours:

```text
MTTF = 600 / 3 = 200 h
MTTR = 12 / 3 = 4 h
MTBF = MTTF + MTTR = 204 h  (lecture convention)
Availability = 200 / 204 × 100 = 98.04%
```

For a request-based SLO allowing 99.9% successful requests, 100,000 valid measured attempts permit at most **100 failures** under that definition. A request-based failure allowance is different from a time-based downtime budget; do not swap denominators.

### Performance and buffering

At stable throughput 100 requests/s and mean time 0.2 s, Little's Law gives **20 mean in-flight requests**. At 50 events/s and 200 bytes/event, a one-hour outage produces **36 MB decimal raw payload**, before metadata and storage overhead.

Show the formula, substitution, units and interpretation. A correct arithmetic answer with the wrong measurement boundary can still imply the wrong engineering conclusion.

## 5. Integrated case: UniMarket

Students browse products and create orders. Payment runs through an external provider; staff review disputes. The team uses a design system, an agreed API contract, a queue, a database, and two application replicas on the same host.

- **Domain:** identify order identity, money values, ownership and legal state transitions. Do not choose service boundaries merely by splitting every table.
- **Contract:** define order input, response, pending/completed/failed states and errors. Mocks enable parallel development; real integration tests still verify the actual implementation.
- **Security:** authenticate callers and enforce student/staff/object permissions on the server. Review the payment and operator trust boundaries.
- **Messaging:** assign stable business identifiers, handle redelivery and reconcile uncertain payment outcomes.
- **Deployment:** same-host replicas share host failure. Show placement, communication, state, backups, recovery and ownership.
- **UX:** show pending status and prevent accidental duplicate action; an unresponsive spinner is weak feedback.
- **Quality:** test state transitions, real provider-adapter behaviour, access rejection, expected load and worker recovery.
- **Delivery:** enforce standards in CI and monitor after release. A clean build cannot establish runtime capacity.
- **Presentation:** demonstrate a useful journey, explain a failure case, show measurements and state what remains untested.

Each answer should connect a specific problem to a mechanism, verification and trade-off. Listing tool names earns little explanatory value by itself.

## 6. Distributed workflows and compatibility

A service contract reduces mismatched assumptions but cannot eliminate runtime outages, race conditions or incorrect semantics. A schema-compatible response can still contain the wrong student's data. Test contracts, business behaviour and authorisation separately.

For a multi-service purchase, a saga coordinates local transactions and compensating actions; compensation is a business operation, not a magical global database rollback. An email already sent cannot be unsent. Design for timeouts, duplicates and partial progress.

Changing a published field name can break consumers. Use a compatible migration or explicit versioned contract, communicate the change and verify provider/consumer behaviour. A new version label alone does not perform that migration.

## 7. Recovery, testing and evidence traps

A replica is not a backup, an untested backup is not measured recovery, and adding instances does not remove every bottleneck. A security scanner passing does not prove access rules. A high coverage number does not establish meaningful assertions. A working generated demo does not prove supportability.

When interpreting a result, ask: **Which requirement? Which conditions? Which metric? Which observation? What remains outside the evidence?** This same discipline improves a written exam answer, an ADR and a project presentation.

## 8. A practical revision cycle

Try a short definition, a comparison and a scenario for each weak topic. Practise calculations without looking at the worked result. Draw a deployment from memory and use L28's eight questions to review it. Explain one architecture choice aloud with its requirement and evidence, then answer a challenge about its limitation.

Use the flashcards for recall, MCQs for discriminating similar concepts and technical questions for connected explanations. The model answers illustrate reasoning; their length is not an official mark allocation or mandatory exam format.

## Guided learning: Connect the CT4 topics through one checkout design

This walkthrough stays within L28–L33. The rest of this broader revision guide also covers the earlier ST2 material.

### 1. State a measurable outcome

Replace “reliable” with a failure scenario, restoration target and acceptable data loss. Include user-visible states and permissions.

**Example:** After a worker outage, accepted orders remain pending and eventually finish without duplicate payment effects.

**Common trap:** A technology name is not an acceptance criterion.

### 2. Explain a mechanism and its cost

Choose placement, communication and state management that could support the requirement. Show shared dependencies and trust boundaries.

**Example:** A durable queue buffers accepted work, but introduces backlog, retries and delayed completion.

**Common trap:** A plausible topology supports a target; it does not measure achievement.

### 3. Try to falsify the claim

Exercise important failure and misuse paths and record relevant metrics. Verify the final business state as well as process liveness.

**Example:** Stop a worker, submit identifiable orders, restart it and verify one intended payment effect per order.

**Common trap:** A restarted process does not prove correct recovery of business data.

### 4. Report a bounded conclusion

Communicate the result with workload, environment and limitations. Use the outcome to improve the next design or test.

**Example:** The test covers a bounded worker outage, not a regional failure or unlimited queue capacity.

**Common trap:** One favourable observation cannot establish every quality attribute.

### Interactive experiment: Choose evidence for the claim

Switch between CT4 claims. Select the evidence set that actually supports each one, then inspect why the alternatives fall short. Open the HTML guide to change the inputs and see the result.

### Check 1: A service uses TLS, a cloud database and generated tests. Is its security established?

- Yes: those three labels are sufficient.
- No: access rules and abuse paths still need appropriate verification.
- Yes, if its UI has no admin button.

**Answer:** No: access rules and abuse paths still need appropriate verification. Correct. Ask what each control and test actually establishes.

### Check 2: What makes a strong scenario answer across these topics?

- A long list of tool names.
- A requirement, mechanism, verification method and trade-off.
- A claim that every quality can be maximised at once.

**Answer:** A requirement, mechanism, verification method and trade-off. Correct. The chain makes the reasoning assessable.
