## Scope

**General study guide — no L31 lecture slides were supplied.** This guide explains how to present and defend a software engineering project clearly. The goal is not to sound fancy. The goal is to help the audience understand your reasoning and trust your evidence.

## 1. A presentation is not a data dump

A weak technical presentation often tries to show everything: every screen, every tool, every file, every meeting, every feature. That usually overwhelms the audience.

A strong presentation answers a focused question:

```text
What should the audience understand, believe, or decide by the end?
```

Before making slides, identify:

- who the audience is
- what they already know
- what they care about
- what decision or judgement they need to make
- what evidence would convince them

A client may care about whether the workflow solves the business problem. A technical examiner may care about requirements, architecture, quality evidence, and trade-offs. A mixed audience needs plain language first, then enough technical depth to defend the solution.

The bigger picture: presentation skill in software engineering is really **explanation skill**. You are showing not only what you built, but why your choices make sense.

## 2. Use a narrative that explains reasoning

A useful structure is:

```text
problem -> constraints -> approach -> evidence -> limitations -> next step
```

Each part answers a different audience question:

| Part | Audience question |
|---|---|
| Problem | Who has a need, and why does it matter? |
| Constraints | What limits or requirements shaped the solution? |
| Approach | What design did you choose, and why? |
| Evidence | What shows that it works or is reasonable? |
| Limitations | What has not been proven or completed? |
| Next step | What should happen after this presentation? |

This is better than simply listing technologies. A technology name is not an explanation.

Weak:

```text
We used a queue because it is modern.
```

Stronger:

```text
Payment processing may be temporarily unavailable. A durable queue lets us accept an order as pending and process it when workers recover. The trade-off is that we must handle duplicate messages and show users a pending state.
```

The second version explains the need, mechanism, and cost.

## 3. Claims need matching evidence

Every claim should have evidence that actually supports that kind of claim.

| Claim | Weak evidence | Better evidence |
|---|---|---|
| The screen exists | None | Screenshot or demo |
| Users can complete checkout | Screenshot only | Demo of the user journey |
| Permissions are enforced | Hidden button | Direct server-side authorised and unauthorised tests |
| The system is fast | “It felt quick” | Latency result with workload and environment |
| Recovery works | Restart message | Failure test with measured recovery and state check |

The important study point is **scope of evidence**. A screenshot proves appearance, not security. A unit-test count proves tests exist, not that production capacity is adequate. A happy-path demo proves one path under shown conditions, not every failure case.

Use precise words:

- **Implemented**: built in the system
- **Demonstrated**: shown during the presentation
- **Tested**: checked under stated conditions
- **Planned**: intended but not done
- **Assumed**: believed without direct verification

Being honest about these categories makes your presentation stronger because the audience can trust your boundaries.

## 4. Explain design choices through trade-offs

A design choice is convincing when the audience can see why it fits the problem.

Use this pattern:

1. Requirement or constraint
2. Option chosen
3. Why it helps
4. Cost or limitation
5. Evidence or next verification

Example:

```text
Requirement: orders must not be lost if payment workers pause.
Choice: durable queue between order API and payment worker.
Why it helps: accepted work can wait while workers recover.
Cost: users may see pending status, and workers must handle duplicates.
Evidence: demo worker outage, queue depth, and one payment effect per order ID.
```

This makes you sound like an engineer rather than a salesperson. No design is perfect in every dimension. Good presentations explain the trade-off.

## 5. Make visuals carry one clear message

A slide should not be a storage place for everything you know. It should help the audience understand one point.

Good visual habits:

- use readable text
- use direct labels
- include units on charts
- explain arrow direction in diagrams
- highlight the part being discussed
- avoid colour as the only signal
- cite external images, data, and diagrams

Choose the visual type based on the job:

| Need | Useful visual |
|---|---|
| Show structure | Diagram |
| Show sequence | Flow or sequence diagram |
| Compare measurements | Chart |
| Compare trade-offs | Small table |
| Explain code behaviour | Short code excerpt |

A giant architecture diagram may be correct but useless if the audience cannot read it. If the whole diagram is complex, show a simplified overview first, then zoom into the part needed for the current claim.

For code, show only the relevant excerpt. Explain the invariant, rule, or risk. Reading a full file aloud rarely helps.

## 6. A demo is a planned experiment

A demo should have a purpose. It is not just clicking around.

Plan:

1. Starting state
2. Action
3. Expected outcome
4. What the outcome proves
5. What it does not prove

Example:

```text
Start: payment worker stopped.
Action: submit an order.
Expected: order is accepted as pending, not paid.
Then: restart worker and show completion once.
Evidence: queue event and one recorded payment effect.
```

Include a negative case if time allows. For example, show that an unauthorised user is rejected. Negative cases are powerful because they prove the system does not merely work for the easiest path.

Protect sensitive data. Do not project real passwords, tokens, personal data, or private logs.

Prepare a fallback: screenshots, a recording, or a guided walkthrough. Label it honestly. If the live demo fails, do a bounded recovery attempt and then move on. Spending the whole remaining slot debugging usually damages the presentation more than the original failure.

## 7. Timing and rehearsal

Time is a design constraint. If you have ten minutes, you cannot explain every detail.

Illustrative ten-minute structure:

| Time | Focus |
|---|---|
| 1 min | Problem and users |
| 1 min | Key requirements |
| 2 min | Design and trade-offs |
| 3 min | Demo |
| 2 min | Evidence and limitations |
| 1 min | Conclusion and next step |

Adjust this to the actual rubric. The principle is to protect the core argument. If time runs short, cut optional detail, not the main evidence.

Rehearse aloud with the real slides and demo state. Time transitions and setup, not only speaking. Ask reviewers:

- Where did the story become confusing?
- Which claim lacked evidence?
- Which term needed explanation?
- Which slide had too much detail?
- Which demo step was risky or unclear?

## 8. Team presentations need coordination

In a team, the audience should still experience one coherent story. Avoid repeated introductions, inconsistent terminology, and awkward handoffs.

Agree on:

- shared vocabulary
- order of speakers
- handoff phrases
- who controls the laptop
- who handles which question areas
- what to do if the demo fails

Each person can specialise, but everyone should understand the overall system. If only one teammate can explain the architecture, the team looks fragile.

## 9. Handling questions honestly

Questions are not attacks by default. They are a chance to clarify evidence and reasoning.

Good question pattern:

1. Listen to the whole question.
2. Clarify if needed.
3. Answer the central point first.
4. Support the answer with evidence.
5. State limits if the evidence does not cover the whole question.

If you do not know, say what you do know and how you would verify the missing part.

Example:

```text
We measured recovery from a single-zone failure. We have not tested regional outage recovery. To verify that, we would need a separate failover exercise across regions and a data consistency check.
```

This is much better than inventing a number.

## 10. Worked example: defending a queue

Claim:

```text
Orders can remain pending during a temporary payment-worker outage.
```

Reasoned explanation:

| Part | Content |
|---|---|
| Problem | Payment worker may pause or fail |
| Design | Durable queue between order API and worker |
| Why it helps | Accepted work waits for recovery instead of being lost |
| Demo | Stop worker, submit order, show pending, restart worker |
| Evidence | Queue depth, processing logs, one payment effect per order ID |
| Limitation | Depends on queue capacity, retention, and duplicate handling |
| Next step | Test longer outage and capacity limits |

Notice what this does not claim. It does not claim every reliability property is proven. It claims a specific behaviour under specific conditions.

## Exam answer pattern

For presentation questions:

1. Identify the audience and purpose.
2. Choose a structure that explains reasoning.
3. Match claims to evidence.
4. Explain one limitation honestly.
5. Describe how rehearsal or fallback improves delivery.

## Guided learning: Build an explanation the audience can assess

Select the four parts of a technical argument. Each part answers a different audience question.

### 1. Why does this matter?

Begin with a user and a concrete need. Select the depth for the audience, but keep the same factual behaviour across client and technical explanations.

**Example:** Students need to know whether a submitted order is awaiting payment or completed.

**Common trap:** A list of frameworks does not explain the user’s problem.

### 2. Why should this design help?

Connect a design choice to the requirement and describe how it works. Name an important cost rather than presenting the choice as universally best.

**Example:** A durable queue holds accepted work while payment workers recover, at the cost of delayed completion and retry handling.

**Common trap:** Calling a system modern is not a causal explanation.

### 3. What did you observe?

Show a relevant workflow or measurement with its conditions. Explain what the observation supports and how it connects to the claim.

**Example:** Stop a worker, submit a sample order, restart it and verify one payment effect for that order ID.

**Common trap:** A screenshot of a screen does not prove server-side permissions.

### 4. What remains uncertain?

State untested conditions and the next verification step. Honest boundaries make the conclusion more useful, not less technical.

**Example:** The team tested a five-minute worker outage; it has not established behaviour during a full regional outage.

**Common trap:** One successful demonstration is not evidence for every possible failure.
