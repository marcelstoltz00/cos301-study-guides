## Scope

**General recap — no L32 slides were supplied.** This guide connects the existing testing material with the supplied QA notes and deployment concepts. Numerical workloads and targets are illustrative study exercises, not course-prescribed thresholds.

## 1. From “it works” to “how well does it work?”

Functional testing asks whether an operation produces the required behaviour. Non-functional testing evaluates qualities and constraints such as performance, reliability, security, usability, compatibility and resource efficiency. The distinction is useful but not absolute: security rules can be functional requirements, while security assurance spans both categories.

Replace vague words such as “fast” with measurable conditions. A useful requirement identifies the operation, environment, workload, metric, threshold and observation window. Example: **Under 200 requests/second with the specified request mix, p95 successful checkout latency is at most 500 ms, errors are below 1%, for 30 minutes on the stated environment.** Define how timeouts and failed requests are counted so results cannot be improved by dropping them.

## 2. Match the test to the question

| Test | Workload or condition | Main question |
|---|---|---|
| Load | Expected and peak planned traffic | Does the system meet targets under expected use? |
| Stress | Push beyond normal capacity | Where does it degrade or fail, and can it recover? |
| Spike | Rapid traffic increase/decrease | Can it handle abrupt changes and scaling delay? |
| Soak/endurance | Sustained work for an extended period | Do leaks, accumulation or degradation emerge? |
| Volume | Large stored or processed datasets | What happens when data size grows? |
| Scalability | Compare capacity as resources change | How does useful capacity grow relative to resources? |
| Recovery/failover | Controlled component failure and restoration | Can service and data recover within targets? |

Do not confuse load shape with test level. A system-level test can be a load test; a regression suite can include a performance check.

## 3. Define representative workloads

Use an operational profile: request mix, arrival rate, session behaviour, read/write ratio, data sizes, cache state and geographic/network conditions. A cached homepage is not representative of a database-heavy checkout flow. Separate warm-up from the measured window and document both.

**Requests per second and concurrent users are not interchangeable.** Think time, response time and requests per journey connect them. A closed workload with a fixed number of waiting users can reduce its offered rate when the system slows, masking overload. State whether arrivals are externally paced or depend on completions.

Use repeatable data and a documented environment. Watch the load generator itself: if it is CPU-limited or network-limited, the apparent server capacity may simply be the client's limit. Use authorised, controlled test environments and isolate destructive failure experiments.

## 4. Measure more than an average

**Latency** measures elapsed time for an operation. **Throughput** counts completed work per time. **Error rate** measures failed work under a defined classification. **Saturation** indicates how close resources or queues are to useful capacity. Google's SRE monitoring chapter groups latency, traffic, errors and saturation as four useful signals.

A p95 latency value means roughly 95% of observations are at or below it under the stated method. It says nothing about how large the slowest 5% can be. Report tail percentiles and errors alongside central tendency. Do not average p95 values from different servers and assume the result is the global p95; aggregate the observations or compatible distributions.

Record CPU, memory, disk/network I/O, database wait times, connection pools, queue depth and garbage-collection behaviour where relevant. Correlate saturation with user-visible degradation before choosing a fix.

## 5. Two useful calculations

```text
Throughput = completed operations / observation duration
Error rate = failed operations / attempted operations × 100%
Little's Law (stable system): L = λ × W
```

In Little's Law, L is mean work in the system, λ is mean throughput and W is mean time in the system, with consistent boundaries and units. At 100 requests/s and 0.2 s mean time, mean in-flight requests are **20**. This is not a count of logged-in users. The stable-average relationship should not be applied blindly to a growing overload queue.

If 120 of 12,000 attempted requests fail, error rate is **1%**. If a target says “below 1%”, this run does not pass that strict threshold. State whether errors include timeouts and semantically incorrect success responses.

## 6. Diagnose before optimising

Plot throughput, latency and errors as load rises. Throughput may plateau while queues and tail latency grow. High API capacity cannot compensate for a saturated database connection pool. Adding app replicas can even increase pressure on that dependency.

Change one relevant factor at a time where practical, rerun comparable workloads and retain baselines. Include uncertainty and repeatability in the conclusion. A pass is bounded by the tested conditions; a single successful run does not prove capacity for every workload.

## 7. Reliability and recovery

Test process, host and network failures appropriate to the design. Verify service recovery, state integrity and duplicate handling, not just restart messages. Compare measured restoration time to **RTO** and lost data to **RPO**. Test restores from backups because replicas can reproduce deletion or corruption.

Control blast radius, define stop conditions and monitor user-visible impact during failure experiments. For a queue-backed system, test backlog growth during an outage and draining after recovery without repeated business effects.

## 8. Other quality dimensions

| Quality | Example evidence |
|---|---|
| Security | Role/object access tests, dependency review, targeted dynamic checks |
| Usability | Representative users completing defined tasks; success, time and observed difficulties |
| Accessibility | Keyboard navigation, focus behaviour, readable contrast and assistive-technology checks |
| Compatibility | Behaviour across explicitly supported browsers, devices or versions |
| Maintainability | Change effort, comprehensibility and testability, interpreted with code metrics |
| Resource efficiency | Useful work relative to CPU, memory, bandwidth or energy under stated conditions |

An automated accessibility scan or a high code-coverage number supplies partial evidence. Combine tools with task-based evaluation and review. Choose representative users and environments for the claims you want to make.

## 9. A reviewable test report

Record requirement and acceptance rule, system version, environment, dataset, workload, warm-up and duration, tools/configuration, results, anomalies, bottlenecks and follow-up. Preserve enough information to reproduce the run.

**Worked conclusion:** “At 200 requests/s, p95 was 470 ms but errors were 1.4%, so the combined latency-and-error requirement failed. Database waits grew during the run. Investigate that dependency, then repeat the same workload.” Passing one metric does not cancel failure of another required metric.

Keep suitable checks as regression coverage so a later feature does not silently remove an established quality.
