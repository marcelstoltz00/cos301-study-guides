## Scope

**General recap — no L32 slides were supplied.** This rewrite explains non-functional testing in a more study-friendly way and connects it to QA, reliability, deployment, and security.

## 1. Functional versus non-functional testing

Functional testing asks:

```text
Does the system do the required behaviour?
```

Non-functional testing asks:

```text
How well does the system behave under important conditions?
```

Examples:

| Functional question | Non-functional question |
|---|---|
| Can a user submit an order? | How fast is checkout at peak load? |
| Can a tutor update a mark? | Is unauthorised access rejected consistently? |
| Can the report be generated? | Does report generation still work with a large dataset? |
| Can the service restart? | How long does recovery take, and is data still correct? |

The distinction is useful, but not perfect. Security can be expressed as a functional rule, such as “students may read only their own marks,” while security testing also includes broader non-functional assurance.

The study idea: do not stop at “it works once.” Ask what happens under load, over time, across environments, during failures, and with real users.

## 2. Turn vague qualities into testable requirements

Words like fast, scalable, reliable, and usable are not testable by themselves.

A testable non-functional requirement should include:

- operation or user journey
- environment
- workload
- metric
- threshold
- duration or observation window
- how errors and timeouts are counted

Example:

```text
Under 200 requests/second with the specified request mix,
p95 successful checkout latency is at most 500 ms,
errors are below 1%,
for 30 minutes,
on the stated test environment.
```

Why this matters: without conditions, people can accidentally or deliberately test the easiest version of the claim. A cached homepage on a developer laptop says little about database-heavy checkout in production-like conditions.

## 3. Match the test type to the question

| Test type | What you do | Main question |
|---|---|---|
| Load test | Use expected or peak planned traffic | Does it meet targets under expected use? |
| Stress test | Push beyond expected capacity | Where does it break, and how does it recover? |
| Spike test | Increase or decrease demand suddenly | Can it handle abrupt changes? |
| Soak/endurance test | Run for a long time | Do leaks or degradation appear over time? |
| Volume test | Increase stored or processed data | What happens as data grows? |
| Scalability test | Change resources and compare capacity | Does useful capacity grow with resources? |
| Recovery/failover test | Break something in a controlled way | Can service and data recover within targets? |

Do not confuse the test type with the test level. A system-level test can be a load test. A regression suite can include a small performance check.

The reason to name the test type is that each one looks for a different kind of risk. A five-minute load test may pass but still miss a memory leak that appears after six hours.

## 4. Representative workloads

A workload describes what the system is being asked to do.

Include:

- request mix
- arrival rate
- concurrent users if relevant
- think time between user actions
- read/write ratio
- data sizes
- cache state
- network or geography assumptions
- external service behaviour

Requests per second and concurrent users are not the same thing.

Example: 100 logged-in users might generate 5 requests/second if they spend most of their time reading. The same 100 users might generate far more if they use an automated workflow. User count does not directly equal request rate.

A closed workload with a fixed number of waiting users can hide overload. If the system slows down, users wait longer, so they send fewer new requests. An externally paced workload keeps sending requests at a target rate, which may reveal queue growth.

Always watch the load generator. If the machine generating traffic is CPU-limited, then your test may measure the client machine, not the server.

## 5. Measure useful outcomes, not only averages

Important performance signals:

| Signal | Meaning |
|---|---|
| Latency | How long an operation takes |
| Throughput | Completed useful work per time |
| Error rate | Failed attempts as a percentage |
| Saturation | How close resources or queues are to capacity |

Average latency can hide user pain. If most requests are fast but a few are extremely slow, the average may still look acceptable.

p95 latency means about 95% of observed values are at or below that value under the chosen percentile method. It is not the maximum. The slowest 5% can still be much worse.

Also report errors with latency. A system that quickly rejects half the requests may have low latency, but it is not providing useful service. Fast failure should not be reported as success.

Do not average p95 values from several servers and call that the global p95. Percentiles need compatible aggregation or raw observations.

## 6. Useful calculations

Throughput:

```text
Throughput = completed operations / observation duration
```

Error rate:

```text
Error rate = failed operations / attempted operations x 100%
```

Example:

```text
120 failures out of 12,000 attempts
= 120 / 12,000 x 100
= 1%
```

If the requirement says “below 1%,” then exactly 1% does not pass. Wording matters.

Little's Law for stable systems:

```text
L = lambda x W
```

Plain meaning:

| Symbol | Meaning |
|---|---|
| L | Average work in the system |
| lambda | Average throughput/arrival rate |
| W | Average time in the system |

Example:

```text
100 requests/second x 0.2 seconds = 20 in-flight requests on average
```

This is not the same as 20 logged-in users. It is the average amount of work inside the measured boundary.

Do not apply this blindly during unstable overload where the queue is growing without bound.

## 7. Finding bottlenecks

As load rises, watch throughput, latency, errors, and saturation together.

Common pattern:

```text
Throughput rises -> reaches a plateau
Latency rises -> queues grow
Errors rise -> timeouts or rejections appear
```

The bottleneck may not be the part you first suspect. API replicas may be idle while the database connection pool is full. Adding more API replicas can even make the database pressure worse.

Investigate dependencies:

- CPU
- memory
- disk I/O
- network I/O
- database waits
- connection pools
- queue depth
- garbage collection
- external services

Change one relevant factor at a time where possible and rerun comparable tests. Keep baselines, otherwise you cannot tell whether the change helped.

## 8. Recovery and reliability testing

Recovery testing checks more than “the process restarted.”

You need to verify:

- service is usable again
- data is correct
- duplicate actions did not occur
- queues drained correctly
- users see accurate status
- measured recovery time meets RTO
- measured data loss meets RPO

RTO asks how long restoration may take. RPO asks how much data loss is acceptable.

Backups must be restored in tests. A backup that has never been restored is only a hope. Replication is also not enough for every failure, because accidental deletion or corruption may be copied to replicas.

Failure experiments need control: define blast radius, stop conditions, monitoring, rollback, and who is allowed to run them.

## 9. Other non-functional qualities

Non-functional testing is broader than performance.

| Quality | Evidence examples |
|---|---|
| Security | Access-control tests, dependency review, dynamic checks |
| Usability | Representative users attempting tasks |
| Accessibility | Keyboard navigation, focus order, contrast, assistive technology checks |
| Compatibility | Supported browsers, devices, operating systems |
| Maintainability | Review effort, code metrics interpreted with context, testability |
| Resource efficiency | Useful work per CPU, memory, bandwidth, or energy |

Automated tools give partial evidence. An accessibility scanner can catch some issues, but it cannot fully replace real keyboard and assistive-technology checks. High code coverage does not prove correct behaviour.

Choose evidence that matches the claim.

## 10. Writing a reviewable test report

A useful report lets someone understand and repeat the test.

Record:

- requirement and acceptance threshold
- system version
- environment
- dataset
- workload mix and pacing
- warm-up period
- measured duration
- tools and configuration
- results
- anomalies
- bottlenecks
- conclusion and follow-up

Worked conclusion:

```text
At 200 requests/s, p95 latency was 470 ms, but errors were 1.4%.
The latency target passed, but the error target below 1% failed.
Database waits increased during the run.
Investigate the database dependency and repeat the same workload.
```

Passing one metric does not cancel failure of another required metric.

## Exam answer pattern

For non-functional testing questions:

1. Name the quality being tested.
2. Turn the vague claim into a measurable requirement.
3. Choose the test type and workload.
4. State the metrics and thresholds.
5. Explain what the result proves and what it does not prove.

## Guided learning: Follow a request to the real bottleneck

Read this from left to right. Capacity at one stage does not establish the capacity of the whole path.

### 1. Define the offered work

Specify request mix, arrival rate, data and pacing. Monitor the driver so its own resource limit is not mistaken for server capacity.

**Example:** A fixed-user test can send fewer requests when responses slow because clients are waiting.

**Common trap:** Concurrent user count is not the same unit as requests per second.

### 2. Observe useful outcomes

Measure successful and failed work together with latency. Timeouts and fast failures affect what a performance result means.

**Example:** An overloaded API may reject quickly, lowering an average latency while delivering fewer useful results.

**Common trap:** A fast error response does not satisfy a successful checkout requirement.

### 3. Look for accumulated waiting

Measure queues, connection pools and dependent services. A saturated database can constrain otherwise idle application instances.

**Example:** More API replicas can create more competing database requests rather than higher completed throughput.

**Common trap:** Adding capacity to the wrong tier need not remove the bottleneck.

### 4. Report the tail and the context

Inspect percentiles alongside throughput and errors. Use consistent measurement boundaries and state the duration and environment.

**Example:** If nineteen requests take 100 ms and one takes 2,000 ms, the maximum exposes a tail that p95 may not show under the nearest-rank method.

**Common trap:** A percentile is not a maximum, and averaging several p95 values is not generally a global p95.

### Interactive experiment: See an average hide the tail

### Check 1: p95 passes, but the required error threshold fails. What is the overall result?

- Pass: use the more favourable metric.
- Fail: every mandatory criterion must hold.
- The errors should be excluded.

**Answer:** Fail: every mandatory criterion must hold. Correct. Report both outcomes and investigate the failing criterion.

### Check 2: You need to find a memory leak that appears after hours. Which test shape fits?

- A sustained soak test.
- A single idle request.
- A diagram export.

**Answer:** A sustained soak test. Correct. Sustained operation can reveal accumulation over time.
