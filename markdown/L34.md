## Scope

**General study guide — no L34 lecture slides were supplied.** This is vendor-neutral coverage with illustrative design exercises. NIST references support the cloud and distributed-computing vocabulary; the scenarios and engineering trade-offs are study applications of those concepts.

## 1. Cloud computing vocabulary

NIST's cloud model describes shared, configurable resources accessed over a network and provisioned with limited management effort. Its five essential characteristics are **on-demand self-service, broad network access, resource pooling, rapid elasticity and measured service**.

Distinguish service models by what the consumer manages: **IaaS** supplies infrastructure while the consumer manages operating systems and applications; **PaaS** provides a managed application platform; **SaaS** provides the application itself. These labels do not eliminate customer responsibility for data, access and correct configuration.

NIST distinguishes public, private, community and hybrid deployment models. “Private cloud” concerns exclusive organisational use, not simply a server with no public address. A service model and a deployment model answer different questions.

## 2. Scaling, elasticity and stateless instances

**Vertical scaling** increases resources on a machine. **Horizontal scaling** changes the number of instances. **Scalability** is the ability to handle growth; **elasticity** is adapting resources to changing demand. Neither promises instant capacity or linear speedup.

Scale-out application instances work more predictably when request state does not depend on one instance's memory or local disk. “Stateless” at this tier does not mean the system has no state: databases, queues and session stores still need capacity and recovery plans.

Autoscaling has detection, provisioning and warm-up delay. Scale on a metric tied to the bottleneck and include capacity limits and budget constraints. If the database is saturated, additional application instances may increase contention instead of improving throughput.

## 3. Placement and shared responsibility

Regions, zones, hosts and runtimes are failure domains. Place redundant components across domains relevant to the requirement. A two-zone service can still depend on a single regional database or identity endpoint. Review the whole user path rather than counting replicas.

Managed services shift some operational tasks to a provider; the exact division depends on the service. The application team still needs to understand permissions, data handling, configuration, dependency behaviour and recovery evidence. A managed database is not a substitute for testing application reconnection or accidental-deletion recovery.

## 4. What edge computing changes

**Edge computing** places computation near data sources or users: a device, local gateway, branch site or nearby network location. It can reduce the distance travelled for time-sensitive decisions and avoid transmitting every raw observation to a central service.

Fog computing is related terminology for distributed capabilities between devices and central cloud resources. NIST's fog model discusses decentralising applications and analytics in IoT settings. Terminology varies; make the location and responsibility of each component explicit.

| Dimension | Central cloud | Edge |
|---|---|---|
| Latency | Includes wide-area round trips | Local processing can reduce network delay |
| Compute/storage | Pooled resources and central services | Constrained and heterogeneous devices/sites |
| Connectivity | Remote dependency for clients | Can support local operation if designed for it |
| Data movement | Central aggregation of transmitted data | Filtering/aggregation can reduce uplink traffic |
| Operations | Fewer central deployment targets | Distributed fleet, versions and physical conditions |
| Security | Central access and platform controls | Device identity, local storage and physical exposure |

Edge is not automatically faster: local compute may be slow or overloaded. Compare end-to-end latency, including network, queueing and execution. Keeping data local can reduce transmission, but privacy depends on collection, retention and access controls too.

## 5. A cloud-edge split

Use local processing for time-sensitive actions, outage-tolerant operation or bandwidth reduction. Use central services for aggregated analysis, coordination, durable history or distributing approved configuration. Split by requirements rather than placing everything at one end.

```text
Sensors -> Local gateway -> Cloud ingestion -> Analytics/history
             |                   |
         local action       fleet configuration
             ^                   |
             +--- signed, versioned updates ---+

During a network outage:
- local permitted actions continue under explicit rules
- events enter bounded durable storage
- synchronisation resumes with deduplication after reconnect
```

For a campus greenhouse, a gateway can apply a locally approved watering policy while cloud analytics compare trends. If connectivity fails, define which actions remain permitted, how long cached policy stays valid and what happens when local storage fills. Safety-critical real deployments require domain-specific engineering beyond this study example.

## 6. Offline operation is a consistency decision

Specify what state can be read or changed locally, how stale it may be and how conflicts resolve. An offline device cannot always know whether another site already changed the same record. Some operations can queue; others must be refused or restricted when current central state is required.

A durable **store-and-forward** buffer records events for later transmission. Use stable event identifiers, retry policies, acknowledgements and deduplication. Include sequence or version information where ordering matters. Wall-clock timestamps alone may misorder events when devices have clock drift.

A network partition forces choices for operations that require shared up-to-date state: wait/reject rather than risk inconsistency, or accept a defined weaker consistency model and reconcile. Do not reduce this to an unconditional “pick any two” slogan; identify the partition and the operation's guarantee.

## 7. Device identity and fleet operations

Give each device an identity and limit its permissions. Protect and rotate credentials, authenticate update channels and verify update integrity. A shared secret across an entire fleet creates a large compromise scope. Define what revocation means for disconnected devices.

Deploy gradually with version tracking, health checks and rollback or recovery. Interrupted updates and incompatible configuration must be considered. Observe device health, connection status, queue backlog, software version and time since last contact. Plan ownership for lost, replaced or compromised devices.

## 8. Capacity, cost and recovery calculations

If a gateway records 50 events/s at 200 bytes/event for a one-hour outage, the raw payload is **50 × 200 × 3,600 = 36,000,000 bytes**, about **36 MB decimal**. Allocate additional space for metadata, indexing, retries and safety margin. A buffer is finite; define backpressure or an explicit discard policy before it fills.

A stream of 1,000 readings/s at 100 bytes each carries 100,000 bytes/s before overhead. Aggregating to 10 summaries/s of the same size reduces this illustrative payload to 1,000 bytes/s, a **99% reduction**. That saving loses raw detail unless retained elsewhere. State the analytical trade-off.

Cost includes compute, storage, network transfer, monitoring, device hardware and fleet support. Lower cloud traffic can be offset by more complex device maintenance.

## 9. Worked design review

For a campus attendance gateway, define whether local acceptance is provisional or authoritative, what happens to revoked credentials offline, and how duplicate events reconcile. Draw the gateway, local store, identity/configuration source and cloud ingestion with trust and failure boundaries. Test disconnect, reconnect, full buffers, duplicate delivery, clock drift and interrupted update. Measure the user-visible outcome and recovery rather than merely confirming that messages eventually arrive.
