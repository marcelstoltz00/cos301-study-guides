## 1. What does “quality” mean in software?

Software quality means more than “the program runs.” A system can run and still be poor quality if it is insecure, confusing, unreliable, hard to change, or too slow.

The notes describe quality as meeting:

1. explicit functional and performance requirements
2. documented development standards
3. implicit professional expectations

The third one is important. A specification may forget to say “do not leak student marks to other students,” but users and professionals still expect confidentiality. So quality is not only about blindly matching a written document. It is also about reasonable expectations for the kind of system being built.

Examples of quality attributes:

| Attribute | Simple meaning |
|---|---|
| Reliability | Works without failing for a period of use |
| Availability | Is up and usable when needed |
| Security | Protects data and actions from unauthorised use |
| Usability | Real users can complete tasks without unnecessary confusion |
| Maintainability | Developers can understand and change it safely |
| Testability | Behaviour can be checked with reasonable effort |
| Portability | Can move across environments where required |
| Efficiency | Uses resources responsibly |

Quality attributes can conflict. Extra security checks can add complexity. More replicas can improve availability but increase cost. Highly optimised code can become harder to understand. A good answer explains the trade-off in context.

## 2. SQA versus quality control

This distinction is central:

| Term | Easy meaning | Focus |
|---|---|---|
| Software Quality Assurance (SQA) | Setting up and checking the process that should produce quality | Process |
| Quality Control (QC) | Checking the actual product/artifact for defects | Product |

SQA asks: “Do we have the right practices, standards, reviews, tests, and controls?”

QC asks: “Does this requirement, design, code, or test result contain a problem?”

Testing is quality control, but quality work is bigger than testing. Reviews, coding standards, change control, measurements, and defect tracking all contribute.

The lecture's three-part approach:

1. Establish organisation-wide policies and standards.
2. Tailor procedures and standards for the project.
3. Check that the agreed process is actually followed.

Why step 3 matters: a standards document that nobody uses does not improve quality. Evidence matters. Examples include review records, CI results, test reports, defect logs, and approved exceptions.

## 3. Why quality assurance is worth doing

SQA costs time and effort. Reviews take time. Tests take time. Standards can feel restrictive. Tooling must be configured. People must learn the process.

But skipping assurance often moves the cost later, where it is more expensive. A requirements ambiguity caught in a review may take minutes to clarify. The same ambiguity found after deployment may require emergency fixes, data repair, user communication, and lost trust.

Benefits include:

- fewer hidden defects
- less rework
- easier maintenance
- better reliability
- clearer team expectations
- stronger evidence for assessment or release decisions

The goal is not maximum paperwork. The goal is assurance effort that matches the risk. A safety-critical feature deserves stronger assurance than a temporary internal prototype.

## 4. Faults and failures

A **fault** is the defect in the artifact. A **failure** is the incorrect behaviour you observe when the system runs.

Example:

```text
Fault: The leap-year condition in code is wrong.
Failure: A valid 29 February booking is rejected.
```

The fault can exist for months without a visible failure if nobody uses the affected date. This is why “we have not seen a failure” does not prove “there are no faults.”

The lecture categories help you explain where defects come from:

| Code | Cause | Plain explanation |
|---|---|---|
| IES | Incomplete or erroneous specifications | The requirement was missing or wrong |
| MCC | Misinterpreted customer communication | The team misunderstood the stakeholder |
| IDS | Intentional deviation from specifications | Someone knowingly built something different |
| EDL | Error in design logic | The design reasoning was wrong |
| EDR | Error in data representation | Data was modelled or stored incorrectly |
| PLT | Error translating design into code | The implementation did not match the design |
| ICI | Inconsistent component interfaces | Components do not agree on contract or format |
| VPS | Violation of programming standards | Code breaks agreed rules |
| IET | Incomplete or erroneous testing | Tests miss important cases or assert the wrong thing |
| IID | Inaccurate or incomplete documentation | Docs mislead developers or users |
| HCI | Ambiguous or inconsistent human/computer interface | UI causes confusion or wrong use |

The bigger picture: not every defect is “a bad line of code.” Some defects start in requirements, communication, design, interfaces, or tests.

## 5. Reliability and availability

Reliability and availability are related, but different.

**Reliability** asks: how long can the system operate without failure under stated conditions?

**Availability** asks: when users need it, is it operational?

A system can fail often but recover quickly. That may give decent availability but poor reliability. Users still experience interruptions. A system can also fail rarely but take a long time to restore, damaging availability.

Lecture formulas:

```text
MTTF = total observed operating time / number of failures
MTTR = total observed repair time / number of repairs
MTBF = MTTF + MTTR
Availability = MTTF / (MTTF + MTTR) x 100%
```

Meanings:

| Metric | Meaning |
|---|---|
| MTTF | Average time the system runs before a failure |
| MTTR | Average time to repair or restore |
| MTBF | Average full cycle from one failure to the next under the lecture convention |
| Availability | Proportion of time expected to be operational |

Worked example:

```text
Operating times: 180 + 220 + 200 = 600 hours
Failures: 3
Repair times: 3 + 5 + 4 = 12 hours
Repairs: 3

MTTF = 600 / 3 = 200 h
MTTR = 12 / 3 = 4 h
MTBF = 200 + 4 = 204 h
Availability = 200 / 204 x 100 = 98.04%
```

If MTTR improves from 4 hours to 1 hour, availability becomes:

```text
200 / 201 x 100 = 99.50%
```

Notice the “why”: faster repair can improve availability even if the underlying fault still exists. Reliability and recovery should be discussed separately.

## 6. Metrics: useful indicators, not magic proof

A metric is a measurement of a product, process, or artifact. Metrics help you reason, but they do not automatically prove quality.

| Metric type | Meaning | Example |
|---|---|---|
| Control metric | Helps manage the process | Effort spent, elapsed time, defect count |
| Predictor metric | Estimates another quality | Complexity as an indicator of maintainability risk |
| Internal attribute | Measured from the product itself | Lines of code, fan-out |
| External attribute | Observed through use | Failure rate, time to complete task |

Maintainability depends on things like cohesion, coupling, understandability, and adaptability. A number can point to a risk, but context still matters.

**Fan-in** counts how many other components call or depend on a component. High fan-in may mean useful reuse, but also high change impact.

**Fan-out** counts how many components this component calls or depends on. High fan-out can make testing and reasoning harder because more collaborators are involved.

Information-flow complexity in the notes:

```text
component length x (fan-in x fan-out)^2
```

For length 10, fan-in 2, fan-out 3:

```text
10 x (2 x 3)^2
= 10 x 6^2
= 10 x 36
= 360
```

This is not cyclomatic complexity. Cyclomatic complexity is about independent control-flow paths through code.

## 7. Choosing the right quality check

Different tests answer different questions:

| Check | Main question |
|---|---|
| Unit test | Does this small unit behave correctly with dependencies controlled? |
| Integration test | Do real parts work together across a boundary? |
| Regression test | Did a change break something that used to work? |
| Non-functional test | Does the system meet qualities like performance or resilience? |
| Acceptance test | Does it meet user/stakeholder acceptance conditions? |
| Configuration test | Does it work across supported settings/environments? |
| Adapter/interface test | Does it correctly speak to an external protocol or UI boundary? |

Mocking is useful in unit tests because it isolates the unit. But if you mock the exact boundary you claim to be integrating, you have not proven that real integration works.

Example: a mocked database adapter can prove the caller handles a returned value. It cannot prove the real database query, credentials, schema, network, and serialization work.

Testing techniques:

| Technique | Meaning | Example |
|---|---|---|
| Equivalence partitioning | Choose representatives from groups expected to behave similarly | One valid age, one invalid negative age |
| Boundary value analysis | Test edges where mistakes often occur | 0, 1, 2, 99, 100, 101 for range 1-100 |
| Path analysis | Use code structure to test control-flow paths | White-box tests for branches |

## 8. Coding standards that actually help

Coding standards should make code easier to read, review, test, and maintain. They should not be empty rules followed only for appearance.

A useful standard includes:

- meaningful names
- consistent formatting
- clear responsibilities
- exception-handling rules
- input validation expectations
- security hygiene
- commenting guidance
- test expectations
- version-control conventions

The important part is the reason behind the rule.

Example:

```python
# Bad: hides every error and reports success.
def charge(order):
    try:
        gateway.charge(order)
    except Exception:
        return True
```

Why this is dangerous: if the payment gateway timed out after possibly charging the customer, returning `True` lies to the rest of the system. The system may mark the order as paid without knowing the real payment state.

Better idea:

```python
def charge(order):
    try:
        return gateway.charge(order)
    except GatewayTimeout as error:
        raise PaymentStatusUnknown(order.id) from error
```

Now the code communicates the uncertainty. The business process can reconcile the payment or retry safely using an idempotency rule.

Tools help enforce standards:

| Tool/check | What it does |
|---|---|
| Formatter | Applies layout consistently |
| Linter/static analyser | Checks configured rules and possible defects |
| Tests | Check expected behaviour |
| CI | Runs checks consistently for submitted changes |
| Human review | Checks meaning, design, trade-offs, and context |

Local hooks are useful, but they can be bypassed. CI gives a shared gate.

## Exam answer pattern

For quality questions:

1. Define the term.
2. Distinguish it from a nearby term.
3. Apply it to the scenario.
4. State what evidence would support the claim.

Example: “SQA is process-focused, while QC is product-focused. In this project, requiring code reviews and CI checks is SQA; finding a failing boundary test is QC evidence. The claim is supported by review records, test results, and defect follow-up.”

## Guided learning: Trace one defect through assurance and control

This is an example lifecycle, not a promise that every defect follows one path. Select the stage to see what evidence it contributes.

### 1. Prevent ambiguity

Quality starts with explicit requirements and expected qualities. A shared error-handling standard gives reviewers something concrete to evaluate.

**Example:** The payment workflow must never report confirmed success for an unknown outcome.

**Common trap:** A standards document with no examples or enforcement is weak assurance.

### 2. Inspect the artifact

Review requirements, design and code for contradictions and unsafe assumptions. A static fault can be found before anyone observes a runtime failure.

**Example:** A reviewer notices catch-all handling that returns success after a payment timeout.

**Common trap:** Passing formatting checks does not establish correct business semantics.

### 3. Activate the important paths

Test positive, negative and boundary cases with meaningful assertions. Use real collaborators when claiming evidence about an integration.

**Example:** Force a timeout after a provider may have accepted payment; assert an unknown state rather than paid.

**Common trap:** No exception was thrown is not a sufficient assertion for every service.

### 4. Measure and improve

Observe incidents and repair duration, then feed defects back into requirements, standards and regression coverage. Interpret metrics with their units and context.

**Example:** A runbook shortens restoration time even before the underlying fault is removed.

**Common trap:** Better availability does not necessarily mean fewer failures.
