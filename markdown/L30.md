## 1. What counts as quality?

Meeting the specification is necessary but insufficient: specifications can be incomplete, ambiguous or omit qualities users reasonably expect. The notes describe quality as conformance to explicit functional and performance requirements, documented development standards, and implicit professional expectations.

Quality attributes include safety, security, reliability, resilience, robustness, understandability, testability, adaptability, modularity, complexity, portability, usability, reusability, efficiency and learnability. They can conflict: extra redundancy can improve continuity while increasing resource use and complexity. Explain trade-offs in the system's context.

## 2. SQA versus quality control

**Software quality assurance (SQA)** establishes and checks the processes intended to produce quality. **Quality control (QC)** evaluates artifacts and software to discover problems. Testing is part of quality work, not all of it.

The notes' three-part approach is to establish organisation-wide policies, tailor project-specific procedures and standards, and ensure the agreed procedures are actually followed. An unused standards document provides little assurance.

SQA activities include technical methods, formal technical reviews, testing, standards enforcement, change control, measurement, record keeping and reporting. Reviews occur at requirements, design, code and test stages, with customer feedback during maintenance. Formal reviews seek defects in the artifact rather than blame in its author.

Benefits include fewer latent defects, reduced rework and maintenance, greater reliability and customer satisfaction. Costs include staff time, tooling, cultural change and difficulty allocating scarce resources. Tailor effort to project risk; eliminating assurance to save time can move a larger cost into maintenance.

## 3. Faults, failures and their causes

A **fault** is a static defect that can cause incorrect behaviour. A **failure** is observed erroneous or unexpected runtime behaviour. A faulty leap-year branch may remain dormant until an affected date is processed. Absence of observed failures is not proof of absence of faults.

The slides identify these defect sources:

| Code | Cause |
|---|---|
| IES | Incomplete or erroneous specifications |
| MCC | Misinterpreted customer communication |
| IDS | Intentional deviation from specifications |
| EDL | Error in design logic |
| EDR | Error in data representation |
| PLT | Error translating a design into program code |
| ICI | Inconsistent component interfaces |
| VPS | Violation of programming standards |
| IET | Incomplete or erroneous testing |
| IID | Inaccurate or incomplete documentation |
| HCI | Ambiguous or inconsistent human/computer interface |

Use these categories to explain prevention: interface reviews address ICI; requirements clarification addresses IES or MCC. Not every defect originates in a programmer's syntax.

## 4. Reliability and availability

**Reliability** concerns failure-free operation over a specified duration in a specified environment. An operational profile describes how the system is actually used; testing rare and common operations in the wrong proportions can distort a reliability estimate. Failure consequences also matter.

**Availability** concerns being operational when needed. A service can fail often but recover rapidly, giving relatively high availability while still interrupting users. Both the frequency and duration of failures matter.

Use the **lecture's convention**:

```text
MTTF = total observed operating time / number of failures
MTTR = total observed repair time / number of repairs
MTBF = MTTF + MTTR
Availability = MTTF / (MTTF + MTTR) × 100%
```

MTBF terminology varies between contexts; state this convention in calculations. The ratio models long-run availability under the assumed operating/repair cycle. Do not treat a small sample as a guarantee of future service.

### Worked example from the notes

Uptimes are 180, 220 and 200 hours; repair times are 3, 5 and 4 hours. MTTF = 600/3 = **200 h**. MTTR = 12/3 = **4 h**. MTBF = **204 h**. Availability = 200/204 × 100 = **98.04%**. Use these observed cycles; do not infer additional measurements from the narrative's six-month period.

If MTTR falls to 1 hour with the same MTTF, availability becomes 200/201 × 100 = **99.50%**. Recovery improvements can raise availability without removing the underlying fault.

## 5. Metrics and design quality

A metric measures a system, process or artifact. **Control metrics** support planning and management, such as elapsed time or effort. **Predictor metrics** estimate product qualities, for example complexity as a signal of maintenance difficulty. An internal attribute is measured from the software; an external attribute is observed through use or maintenance. A predictor is not a proof of the quality it predicts.

Maintainability depends on cohesion, coupling, understandability and adaptability. Structural **fan-in** counts incoming component dependencies or calls under the chosen counting rule; **fan-out** counts outgoing dependencies. High fan-in can indicate widespread reuse and a large change impact. High fan-out can increase coordination and testing complexity. Interpret them with context.

The notes' information-flow measure is **component length × (fan-in × fan-out)²**, using informational fan counts that also consider data flows and shared structures. For length 10, fan-in 2 and fan-out 3, the result is 10 × 6² = **360**. This is not cyclomatic complexity. Cyclomatic complexity instead describes independent control-flow paths; for one connected control-flow graph, it is E − N + 2.

## 6. Choose the right quality check

| Check | Main purpose |
|---|---|
| Unit | Check a unit's service and postconditions with dependencies controlled |
| Integration | Exercise real interactions and data flows across the boundary under test |
| Regression | Re-run relevant checks after change to detect lost behaviour or quality |
| Non-functional | Measure qualities such as performance, resilience and security |
| Acceptance | Establish whether user requirements and acceptance conditions are met |
| Configuration | Check supported combinations of settings and environments |
| Adapter | Verify external protocol/serialization adapters or human-facing interfaces |

The slides emphasise mocking dependencies in unit tests and avoiding mocks in integration tests. More precisely, the integration being claimed needs real collaborating parts; substituting the very boundary under test prevents evidence about it. A unit test should assert required outcomes, not merely that no exception occurred.

**Equivalence partitioning** selects representatives from input classes expected to behave similarly. **Boundary value analysis** targets edges and nearby values. **Path analysis** uses code structure and is a white-box technique. For an allowed integer range 1–100, useful boundary checks include 0, 1, 2, 99, 100 and 101.

## 7. Coding standards that can be enforced

Specify domain-meaningful names, language-appropriate casing, consistent formatting, clear responsibilities, exception handling, input checks, comments, tests, security hygiene and version-control conventions. Explain the purpose and give concrete good/bad examples. Short-function and line-length guidance should improve readability rather than become a substitute for design judgement.

```python
# Bad: suppresses all errors and reports success.
def charge(order):
    try:
        gateway.charge(order)
    except Exception:
        return True

# Better: handle an expected failure without claiming payment succeeded.
def charge(order):
    try:
        return gateway.charge(order)
    except GatewayTimeout as error:
        raise PaymentStatusUnknown(order.id) from error
```

This illustrative code assumes those domain exceptions exist. An unknown payment outcome requires reconciliation or an idempotent retry policy; blindly retrying can double-charge. Standards should explain both the pattern and its business reason.

Use comments for intent, rationale and non-obvious behaviour, and keep API documentation accurate. A **formatter** applies layout; a **linter/analyser** checks configured rules; **human review** evaluates semantics and trade-offs. Run consistent checks locally and in CI, document exceptions and review actual code for compliance. Local hooks alone can be bypassed.

**Exam method:** define the term, distinguish its nearest alternative, apply it to a scenario, and explain what evidence would support the claim.
