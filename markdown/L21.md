## DevOps & DevSecOps — IT, Development, and Security Combined

## Part A: Introduction to DevOps

### 1. The CI/CD Infinite Loop

DevOps is commonly visualized as an **infinite loop** of eight phases, split into two halves:

- **CI (Continuous Integration) half:** Plan → Code → Build → Test
- **CD (Continuous Delivery/Deployment) half:** Release → Deploy → Operate → Monitor

The loop is continuous — insights from Monitor feed back into the next Plan phase, and the cycle repeats indefinitely rather than ending at "deploy."

### 2. Step 1 — Plan

Planning happens in a work-tracking tool (e.g. Azure DevOps Boards) as a structured work item — a user story with:
- A **description** written from the user's perspective (e.g. "As an authenticated user, I want to see all my accounts and their balances on a dashboard"), including acceptance criteria embedded in the description (e.g. "API call failure shows user-friendly error; page loads within 2 seconds").
- **Planning fields**: story points, priority, and risk — used to estimate and prioritize the work.
- **Classification** fields (e.g. value area: Business) linking the technical task back to business value.
- Direct links from the work item to its **development** (commits/pull requests/branches) and **deployment** (release tracking), so planning, code, and delivery stay traceable to each other.

### 3. Step 2 — Code

Developers implement the planned work in an IDE, typically organizing the solution into clearly-separated services/layers (e.g. an `AccountService`, `PaymentService`, `TransactionService`, each split into Domain, Application, Infrastructure, and Api projects — a layered/domain-driven structure). Code here directly implements the acceptance criteria defined in the Plan step (e.g. a `SendPaymentCommandHandler` that validates a recipient account before creating a payment).

### 4. Step 3 — Build

The build step compiles the solution and restores dependencies — but a build is also where **dependency vulnerability scanning** naturally surfaces, because package managers (e.g. NuGet) can flag known-vulnerable dependencies automatically during restore:

```
warning NU1903: Package 'System.Security.Cryptography.Xml' 9.0 has a known high severity vulnerability
warning NU1902: Package 'OpenTelemetry.Api' 1.11.2 has a known moderate severity vulnerability
```

This is a concrete example of **security shifting left**: a real CVE (Common Vulnerabilities and Exposures) in a third-party dependency is surfaced automatically during a routine build, long before the vulnerable code would ever reach production — the developer sees the warning the moment they build locally or in CI, not after a security audit months later.

### 5. Step 4 — Test

Automated tests run via a test runner (e.g. Visual Studio's Test Explorer), reporting pass/fail counts per test group (e.g. "118 passed, 0 failed"). Testing also covers **input validation** at the UI layer — e.g. a "Send Payment" form rejecting an invalid recipient account number ("Enter a valid 7-digit account number") before the request is even submitted, mirroring the constraints-based validation principle from UI/UX design.

### 6. Step 5 — Release

Releasing is the step where a new version is prepared to go live, without yet being exposed to users. A common pattern (shown via container "pods" in a cluster):

- **Active running pods (live to end users):** the current version (e.g. `v1.2.3`) continues serving all live traffic.
- **Pods being created (not live to end users yet):** new pods running the next version (e.g. `v1.2.4`) are started up **in parallel**, but are **not yet receiving user traffic**.

New pods are created and started in the cluster; **they are not live to end users until traffic is switched.** This separation of "started" from "live" is what allows a release to be validated (health checks, smoke tests) before it's actually exposed — and allows an instant rollback (just don't switch traffic, or switch it back) if something is wrong, without needing to redeploy.

### 7. Step 6 — Deploy

Deploy is the step where traffic is actually switched to the new version — the point at which the newly-released pods stop being "not live" and start actually serving real users.

### 8. Step 7 — Operate

Once deployed, the system runs live in production, serving real users performing real actions — e.g. a live banking app where users view account dashboards, transfer funds between their own accounts, and send payments to other accounts. This is the system actually doing its job in the real world, not just passing tests in a controlled environment.

### 9. Step 8 — Monitor

Monitoring closes the loop by observing the running system from two complementary angles:

- **Technical/distributed tracing** (e.g. via Jaeger): individual requests are broken into **traces** made up of **spans** — e.g. a trace for `PaymentService: POST /api/v1/payments` shows exactly how long the request took and which downstream services (`AccountService`, `PaymentService`) it touched, letting engineers pinpoint exactly where latency or errors occur across service boundaries.
- **User behaviour analytics** (e.g. heatmaps, session replay, funnels): tools can show where users actually click, scroll, and spend attention on a live page (a heatmap), replay entire user sessions, and track engagement metrics — connecting the technical health of the system to how real users are actually experiencing it.

The insights from monitoring — a slow trace, a confusing UI heatmap, a recurring error — feed directly back into the next **Plan** phase, closing the infinite loop.

## Part B: Introduction to DevSecOps

DevSecOps means **security is integrated throughout the entire DevOps loop**, not bolted on as a separate final gate — security becomes part of Plan, Code, Build, Test, Release, Deploy, Operate, and Monitor, not a step that only happens right before (or after) release.

### 1. CVE — Common Vulnerabilities and Exposures

**CVE** is a publicly maintained, community-driven catalogue of publicly disclosed cybersecurity vulnerabilities — each one assigned a standard CVE identifier so that different tools, vendors, and researchers can all refer to the *same* vulnerability unambiguously. This is the exact mechanism behind the build-time warnings seen in Step 3 (`NU1903`, `NU1902`) — package ecosystems cross-reference dependency versions against CVE-style vulnerability databases to warn developers automatically.

### 2. OWASP — Open Web Application Security Project

**OWASP** is a well-known open community focused on web application security, best known for resources like the **OWASP Top 10** — a regularly updated list of the most critical web application security risks (e.g. injection, broken access control, security misconfiguration) used industry-wide as a baseline for what to defend against.

### 3. Tooling: DAST vs. SAST

Two complementary categories of automated security testing tooling:

- **SAST (Static Application Security Testing)** — analyzes source code (or compiled bytecode) **without running it**, looking for known-insecure patterns directly in the code (e.g. string-concatenated SQL queries, hardcoded credentials, use of unsafe functions). Runs early — can be part of the Build/Code step, catching issues before the application ever executes.
- **DAST (Dynamic Application Security Testing)** — tests a **running** application from the outside, the way an attacker would: sending malicious/unexpected inputs to a live running instance and observing the actual responses/behaviour, to catch vulnerabilities that only manifest at runtime (e.g. in how the app actually handles a crafted request), which static analysis of the source code alone can miss.

### 4. Secret Scanning

Automated scanning (of source code, commit history, and configuration files) for accidentally committed secrets — API keys, passwords, tokens, private keys — before or immediately after they land in a repository. This directly mirrors the "secrets do not belong in your repo" principle from L17's CI/CD material: secret scanning is the *automated tooling* that catches this class of mistake as part of the DevSecOps pipeline, rather than relying on developers to never make it.
