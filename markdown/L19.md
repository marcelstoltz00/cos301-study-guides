## Software Testing in Practice

### 1. Why Bother? A Case Study

**The scenario:** an HR Portal was developed on a low-code/customisable platform (SharePoint), with a customisable data structure and workflows. It had no local development environment, extremely slow deployment, painful release cycles, and unhappy users.

**Why it got so bad:**
- Issues were only caught in production — never earlier.
- Business logic was heavily coupled to the platform, making it hard to isolate and change safely.
- The development environment was extremely inefficient (no fast local loop).
- It was hard to work as a team — changes collided.
- There was a **negative compounding effect**: each new problem made the next change riskier and slower.

**Lessons:**
- Your reputation is affected by the quality of the software you release.
- The hard part of software engineering isn't writing the first version — it's **ensuring software keeps working correctly as it changes over time.**
- More automated tests would have caught this earlier.

**How automated tests would have helped:**
- Issues get caught early in the development process, not in production.
- Writing tests **forces you to abstract out external dependencies and isolate logic** (untestable code is usually a sign of tangled coupling).
- Testing changes in a local development environment is much faster than testing in production.
- Tests catch when one team member's changes interfere with and break another's code.
- Testing has a **positive compounding effect** — the inverse of the horror story's negative one: good tests make each subsequent change safer and faster, not riskier and slower.

### 2. Testing Attitude

- Your attitude towards testing determines its value.
- Good tests lead to **acceleration**, not overhead — a test suite is a fast feedback mechanism.
- It helps you refactor and abstract dependencies in your code correctly.
- It makes sure a growing codebase remains maintainable.
- **Tests should not be an afterthought — they are development,** not something bolted on after "the real work" is done.

### 3. Testing Concepts (the test types)

- **Unit** — does this one piece of logic do what it claims?
- **Integration** — do these pieces work together?
- **Functional** — does this feature behave as intended?
- **E2E (End-to-End)** — does the whole journey work, from the user's perspective?
- **Load** — does it hold up when the users show up (i.e. under realistic/peak traffic)?

### 4. Implementing Tests

- Design code to be **testable** — testability is a design property, not something you retrofit for free.
- **Name tests appropriately** — the name should immediately tell you what failed, without needing to read the test body.
- Tests can serve as **self-documentation** of a system's intended behaviour — a well-named, well-written test tells a future reader what the code is supposed to do.

### 5. Code Coverage

- Code coverage is a metric showing **how much of your code is being exercised by tests.**
- Tooling can show which lines of code are executed, and which branches are traversed, by the test suite.
- An open question for any team: **what percentage of code must be covered** before a change is considered adequately tested? (There's no universal number — coverage is a signal, not a guarantee of correctness; 100% coverage does not mean zero bugs, and low coverage on critical logic is a red flag regardless of the overall percentage.)

### 6. Test-Driven Development (TDD) — Red, Green, Refactor

1. **Red** — write the test(s) first. They will fail, since the implementation doesn't exist yet.
2. **Green** — implement just enough code to make the failing tests pass.
3. **Refactor** — clean up the code (and/or the tests) now that you have passing tests as a safety net.

A key benefit: **TDD eliminates premature optimisation** — you write the simplest code that satisfies the test, then improve it, rather than trying to design the "perfect" implementation upfront before you even know it behaves correctly.

### 7. Testing Strategy

**Continuous Integration:**
- Tests should run on **every** code change.
- Pull requests cannot succeed (cannot be merged) unless tests have passed.
- This ensures teams can collaborate and deliver quality together — a shared, enforced quality gate rather than an individual discipline.

**User Acceptance Testing (UAT):**
- Not all testing can be automated — some features genuinely require human verification.
- Humans can break things in unexpected ways. A really good manual tester is an extremely valuable team member, precisely because they find the paths automated tests didn't anticipate.
- It's far better to catch an unexpected end-user action during testing than in production.

### 8. Testing Strategy — Advanced

- **Smoke tests** — a limited set of tests covering critical paths, used to quickly verify a deployment succeeded (i.e. "did the basic things not catastrophically break").
- **Feature switches / dark features (feature flags)** — ship code to production without exposing it to users yet. This **decouples deployment from release** — the code can be deployed and verified safely, then "released" (turned on) independently, and rolled back instantly by flipping the flag rather than re-deploying.
- **Canary releases** — roll a change out to a small subset of users/traffic first, to reduce risk and/or measure user reaction, before a full rollout.

### 9. Key Takeaways

- **Plan for testing** — have an explicit testing strategy, don't leave it implicit.
- **Design for testability** — testable code is a design outcome, not an accident.
- **Automated tests have a compounding effect** — good tests make future change safer and faster; poor/absent tests make future change riskier and slower (the horror story's negative compounding effect, inverted).
- **Implement against tests** — write the test first (or alongside), and execute tests consistently (e.g. via CI on every change), not sporadically.
