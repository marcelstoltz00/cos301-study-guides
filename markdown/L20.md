## Designed for Humans — The UI/UX Survival Guide for Developers

### 1. Why Design Matters for Developers

Developers tend to focus purely on functionality: does it work? Is it fast? Are all the features there? But **users experience software differently** — they experience the *design*, not the implementation.

- When done right, good design is **invisible**.
- When done wrong, bad design is **frustrating**.
- If a product frustrates users enough, **they stop using it.**

It's worth caring about the user experience of your software, not just its correctness or feature completeness.

### 2. Properties of a Good Product

A great user experience sits at the intersection of three properties:

- **Useful** — does it solve a real problem?
- **Usable** — can people actually operate it successfully?
- **Desirable** — do people want to use it (is it pleasant, well-crafted)?

## Part A: How to Design *Usable* Products — "Don't Make Me Think"

### 3. User-Centred Thinking (the biggest mindset shift in UX)

- Stop thinking about **how the system works** (the implementation model).
- Start thinking about **what goal the user wants to achieve** (the user's mental model).
- **Implementation model** → how the code actually works internally.
- **User mental model** → how the user *thinks* it works, based on what they can see and predict.
- **Your product is not the goal** — the user's goal is the goal; your product is only a means to it.

### 4. Constraints

Constraints prevent users from performing certain (invalid) actions. **Good design prevents mistakes before they happen**, instead of showing an error message after the mistake was already made — it guides users toward valid actions in the first place.

**Benefits of constraints:**
- Reduce confusion and decision-making effort.
- Make interfaces feel safer and more predictable.

**Example:** a free-text date-of-birth field (e.g. typing "16 Apr 2003") can be entered in an ambiguous or wrong format, triggering an error message ("Wrong format. Try again.") only after the user submits. A **constrained** input — a structured date picker/calendar widget — makes it *impossible* to enter an invalid format in the first place, because the only actions available are valid ones.

### 5. Discoverability

**Make the possible actions obvious.** Users should not have to stop and think about how your interface works. Good discoverability means users can:

- Easily see the available actions.
- Predict what will happen *before* clicking.
- Explore the interface without fear of breaking something.

**Good interfaces communicate how they work.** A classic failure case: a row of unlabeled icons that give no visual cue as to what each one does (the user is left wondering "what do these do?") — versus clearly labelled actions like "Add," "Edit," "Delete," "More actions," which are self-explanatory without needing to be clicked to find out.

### 6. Feedback

**Users should always know what is going on.** Every action should have a **visible response**:

- Loading a page? → show a skeleton screen.
- Clicked a button? → show a spinner (or other busy indicator).

The interface should show the current state of the system at all times — the user should **not need to remember** what happened; the interface should give them the answer directly.

**Example failure:** a user clicks "Create task," gets no visible response, and is left wondering "did it work?" for five full seconds before anything confirms success. The fix: **immediately** show a busy state the instant the action is triggered, then show a clear confirmation (e.g. an alert/toast: "Task created") once it completes.

Good feedback makes an app feel **responsive and predictable.**

### 7. The Paradox of Choice

**Common misconception:** more options → more freedom → more power to the user.

**The actual paradox:** more options → **fewer actions taken** → **less power to the user.** Overwhelming users with too many simultaneous choices increases decision-making effort to the point that they take less action overall, not more.

**Good design reduces the number of decisions a user has to make at once**, via **progressive disclosure**:
- Show only the most relevant choices upfront.
- Reveal more options only when the user actually looks for them (e.g. behind a "More options" or secondary menu), rather than presenting every possible action at once.

## Part B: How to Design *Desirable* Products — "Make It Easy on the Eyes"

### 8. Visual Hierarchy

Visual hierarchy is about creating structure in an interface so the eye knows what matters most.

**Common mistakes:**
- Bright colours everywhere.
- Large or bold text everywhere.
- **If everything is emphasized, nothing is emphasized.**

**Create hierarchy using:** spacing, size, weight, and colour — applied selectively, not uniformly.

### 9. Whitespace

**Use plenty of whitespace to let your interface breathe.** Cramped interfaces with no breathing room between elements feel cluttered and harder to scan, even if the actual content is identical to a version with generous spacing.

### 10. Ambiguous Spacing (Proximity)

**Related items should have less space between them than unrelated items.** For example, a "First name" label and its input field should sit close together (they're related), while the gap before the next unrelated field group ("Last name," "Email") should be visibly larger — spacing itself communicates grouping, independent of any other visual cue.

### 11. Font Pairings

Choose **one or two fonts** that work well together, and use different **weights** for variation rather than introducing more typefaces. A common pairing pattern: a serif font for headings paired with a sans-serif font for body text, or vice versa (e.g. "Inter & Roboto," "DM Serif & Inter," "Roboto Mono & IBM Plex Serif"). (Tools like FontPair can help find pairing ideas.)

### 12. Line Heights

**Paragraphs need larger line heights than headings or buttons.** A line height that's too tight (e.g. 1.0×) makes body text feel cramped and harder to read; a line height that's too loose (e.g. 2.0×) makes lines feel disconnected from each other. A middle value (e.g. ~1.5× for body text) is typically "just right" — while headings and short UI text (buttons) generally want tighter line heights than long-form paragraphs.

### 13. Line Lengths

**Avoid long lines of unbroken text longer than roughly 80 characters per line.** A paragraph spanning ~120 characters per line forces the eye to travel further and makes it easier to lose your place between lines; constraining body text to roughly ~80 characters per line (e.g. via a max-width on the text container) keeps reading comfortable.

### 14. Colour

**Use colour sparingly, and prefer a limited palette with shades** of a small number of hues, rather than many competing colours. A UI redesigned with a disciplined, limited colour palette communicates state and hierarchy more clearly than one where every element uses a different, arbitrary colour.

### 15. Colour Palettes

Use existing, tested colour palettes to more easily produce a cohesive, attractive design rather than picking colours ad hoc. (Tools like Coolors can help generate/explore palettes.)

### 16. Colour Contrast

**Ensure text has sufficient contrast with the background it's placed on.** Low-contrast text (e.g. light gray text on a white background) can be difficult or impossible to read for many users, even when it looks acceptable to the designer's own eyes/screen.

**Contrast checkers** remove the guesswork — WCAG defines explicit contrast ratio thresholds:

| Level | Normal text | Large text |
|---|---|---|
| AA | 4.5:1 | 3:1 |
| AAA | 7:1 | 4.5:1 |

(Tools like the WebAIM colour contrast checker can measure a specific foreground/background pair against these thresholds.)

### 17. Style Guides

A style guide provides rules and guidelines for creating consistent designs. **Limits choices → easier decisions → faster development.** A style guide typically covers: colours, typography, spacing, icons, and illustrations — giving the whole team a single reference instead of re-deciding these choices for every new screen.

### 18. Further Reading

Recommended books referenced for going deeper on this material: *The Design of Everyday Things* (Don Norman), *Don't Make Me Think* (Steve Krug), *Thinking with Type* (Ellen Lupton).
