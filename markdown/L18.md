## Part A: Domain Modelling Recap

### 1. Core Vocabulary

- **Class** — a type; an abstraction that groups objects.
- **Attribute** — defines a class's properties.
- **Operation** — defines the behaviour of objects.
- **Object** — an instance of a class.
- **Encapsulation** — defining and storing the properties and behaviour of a class/object together.
- **Polymorphism** — the ability to assume more than one form.

> **Gap-fill — the four pillars of OOP:** the lecture names Encapsulation and Polymorphism explicitly, but they're two of the traditional **four pillars of Object-Oriented Programming**, worth knowing as a set since exams often ask for all four: **Encapsulation** (bundling data and behaviour together, hiding internal state), **Abstraction** (exposing only what's relevant — a class *is* an abstraction, per the vocabulary above), **Inheritance** (the IS-A relationship — see the Relationships table below), and **Polymorphism** (an object can be treated as its supertype while still behaving according to its own actual type — e.g. calling `.speak()` on any `Animal` correctly invokes `Dog.speak()` or `Cat.speak()` depending on the real object).

### 2. UML Class Diagrams

- A **UML class diagram** is a *structural* diagram. It shows classes, their attributes and operations, and the relationships between classes.
- A **domain model** is represented by a class diagram **without showing operations** — it models the concepts and their relationships, not the behaviour/implementation.

### 3. Relationships Summary

| Relationship | Notion | Notation direction | Example |
|---|---|---|---|
| Inheritance (IS-A) | Between classes; a subclass *is a* kind of its superclass | Arrow points from subclass to superclass | `Manager` → `Employee` |
| Aggregation (part-of, shared) | A "has-a" relationship where the part can exist independently of the whole | Diamond at the aggregate (whole) side, arrow toward the part | `Car` ◇→ `Engine` |
| Composition (part-of, exclusive ownership) | A stronger "has-a" — the whole exclusively owns the part; the part's lifecycle is bound to the whole | Filled diamond at the aggregate side, arrow toward the part | `Building` ◆→ `Room` |

### 4. Domain Modelling Process (4 steps)

1. **Collect application domain information** — focus on the functional requirements, but also consider other requirements and documents, and business descriptions.
2. **Brainstorm** — list the important application domain concepts, list their properties/attributes, and list their relationships.
3. **Classify the domain concepts** into: classes; attributes/attribute values; relationships (association, inheritance, aggregation).
4. **Visualize the result** using a UML class diagram.

### 5. Pitfalls — Get the Model Wrong, Every Layer Above Inherits the Confusion

Get the domain model right and the architecture writes itself; get it wrong and every layer built on top inherits the confusion.

| What you see (symptoms) | What's actually wrong |
|---|---|
| Every feature requires touching ten files | Boundaries drawn around database tables, not around domain concepts |
| Two developers use the same word to mean different things | Vocabulary is technical, not what users actually say (no shared ubiquitous language) |
| Business says "ship quickly"; the codebase says no | Business rules scattered across services and helper functions instead of living in the model |
| Bugs cluster around the same area for months | Data flow was modelled, but behaviour was ignored |
| Rewrites get pitched, often | Architecture was chosen before the domain was actually understood |

### 6. Entity vs. Value Object — Identity Is the Test

**The test:** *"If I changed every field, would it still be the same thing?"* Yes → it's an **Entity**. No → it's a **Value Object**.

| | Entity | Value Object |
|---|---|---|
| Example | `Customer` | `Money` |
| Identity | Has an ID. Two customers with the same name are still different people. Can change email and remain the same customer. | No ID. R100 ZAR is R100 ZAR — interchangeable. You don't "change" a value object; you replace it. |
| Equality | Compared by identity (the ID) | Compared by comparing all fields |

```ts
class Customer {
  readonly id: CustomerId;
  email: Email;
  status: CustomerStatus;

  changeEmail(e: Email) {
    this.email = e;
    this.emit(EmailChanged);
  }
}

class Money {
  constructor(
    readonly amount: Decimal,
    readonly currency: Currency,
  ) {}

  add(other: Money): Money {
    return new Money(this.amount.plus(other.amount), this.currency);
  }
}
```

Note how `Customer.changeEmail` **mutates** the entity in place and emits an event (identity persists through change), while `Money.add` **returns a new instance** rather than mutating (a value object is replaced, never changed in place).

## Part B: Architecture Recap

### 1. What Is Software Architecture?

Software architecture is the fundamental organization of a software system. It serves as a high-level "blueprint" that defines the structures, components, and relationships between different parts of the system to ensure it meets both technical and business requirements.

**An architecture is technology neutral** — choosing an architectural style is not the same as choosing specific technologies/frameworks.

Architecture decisions cover:

- **Structural Elements** — defining the major modules, subsystems, and databases.
- **Communication** — determining how components interact: via APIs, messaging, or data buses.
- **Quality Attributes** — prioritizing the "ilities": scalability, maintainability, security, reliability.
- **Trade-offs** — balancing conflicting needs, such as speed of development vs. high performance.

### 2. How to Choose an Architecture — Four Questions

1. **How well do you actually understand the domain?** Don't know yet → monolith. Stable model → start splitting.
2. **How many teams will work on it concurrently?** 1–2 teams → one deployable. 5+ teams → microservices may pay off.
3. **Where's the read/write asymmetry?** Roughly equal reads/writes → same model for both. Reads far exceed writes → consider CQRS.
4. **Does history matter as much as current state?** Audit, finance, healthcare domains → event sourcing earns its place.

### 3. N-Layer Architecture (Horizontal Decomposition)

Organizes concerns into logical **layers** (e.g. Presentation, Business, Data). Each layer has a specific responsibility. Layers only communicate with **adjacent** layers (separation of concerns) — this enhances modifiability and lets layers be developed independently. A common example is the **4-layer architecture** (e.g. Presentation → Application/Business → Domain → Data/Infrastructure).

### 4. N-Tier Architecture (Vertical Decomposition)

Organizes concerns into physical **tiers** — each tier has a specific responsibility and is **physically separated** (can run on different machines/processes), unlike layers which are a logical organization within one deployable. The classic example is the **3-tier architecture** (presentation tier, application/logic tier, data tier), each of which can be deployed and scaled independently.

### 5. Microservices Architecture

- **Decentralized control** — the application is split into small, autonomous services that communicate over lightweight protocols (REST/gRPC).
- **Independent deployment** — each service has its own lifecycle, allowing teams to deploy updates without affecting the entire system.

### 6. Event-Driven Architecture

- **Asynchronous nature** — systems respond to "events" (state changes) rather than direct commands.
- **Publish/Subscribe** — producers send events to a broker; consumers listen for specific events they care about.
- **Extreme scalability** — ideal for systems requiring high throughput and low coupling between modules.

| Pros | Cons | Use when |
|---|---|---|
| Producers don't know who's listening — true decoupling | Eventual consistency by default — no "after this, that" guarantee | High-throughput pipelines (orders, telemetry, IoT) |
| Add a new consumer without touching the producer | Debugging crosses async boundaries — needs distributed tracing | Multiple consumers care about the same fact |
| Buffers absorb spikes; system stays responsive | Schema evolution is hard once N consumers depend on event v1 | You want to add capabilities later without redeploying |

### 7. Service-Oriented Architecture (SOA)

- **Interoperability** — diverse systems communicate via an Enterprise Service Bus (ESB).
- **Granularity** — coarse-grained services compared to microservices (fewer, larger services vs. many small ones).
- **SOAP/WSDL** — often relies on formal contracts and heavier protocols than modern REST/gRPC microservices.

### 8. Command Query Responsibility Segregation (CQRS)

Separates **read operations (Queries)** from **write operations (Commands)**. Allows independent scaling of read and write workloads, and enables using different data models for reading vs. writing.

| When it fits | When it doesn't |
|---|---|
| Read patterns are wildly different from write patterns | A simple CRUD app where "show me the record I just edited" is the norm |
| Reports/dashboards that would crush the OLTP database | The team is uncomfortable reasoning about eventual consistency between the read and write models |
| Audit + history matter (pairs naturally with event sourcing) | You haven't actually proven a single read-model bottleneck yet |

### 9. Model-View-Controller (MVC)

| Model | Controller | View |
|---|---|---|
| Represents the data structure and business logic. Notifies the view of state changes. | The "brain." Receives input, updates the model, and selects the appropriate view. | The presentation. Renders data from the model into a user-friendly interface. |

### 10. Pattern Evolution: MVVM vs. MVT

| Feature | MVVM (Model-View-ViewModel) | MVT (Model-View-Template) |
|---|---|---|
| Intermediary | **ViewModel** (data-binding focus) | **View** (controller-like logic — Django's "View" plays the Controller's role) |
| UI Rendering | Client-side (Angular, Vue, React) | Server-side (Django) |
| Core strength | Complex UI interaction / state management | Rapid, content-heavy development |
| Dependency flow | Loosely coupled via events/data-binding | Django's View handles the "Control" flow directly, rendering a server-side Template |
