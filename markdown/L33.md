## Scope

**General study guide — no L33 slides were supplied.** Definitions describe useful distinctions rather than rigid product categories. “Vibe coding” is used in different ways; this guide states its narrower meaning below. Examples are hypothetical, with no vendor pricing or feature assumptions.

## 1. What changes when less code is written manually?

Software still needs requirements, data models, permissions, testing, deployment and maintenance. These approaches change how implementations are expressed and who can build them. They do not remove responsibility for the resulting behaviour.

| Approach | Main construction method | Typical constraint |
|---|---|---|
| Traditional programming | Engineers directly design and edit code | Implementation effort and engineering skill |
| Low code | Visual models, configuration and generated behaviour with extension code | Platform abstractions and extension boundaries |
| No code | Configuration through supported visual building blocks | Behaviour limited by available building blocks and integrations |
| AI-assisted engineering | Generated suggestions or changes reviewed and understood by developers | Quality of context, review and verification |
| Vibe coding, narrow sense | Prompt, run and iterate while largely not inspecting generated code | Limited understanding of what was generated |

A no-code application still runs code, typically managed by its platform. Low code does not specify a universal percentage of handwritten code. A platform can offer both no-code paths and developer extensions.

Martin Fowler's terminology discussion distinguishes vibe coding by accepting generated implementation without examining it. Using an assistant while reviewing the code and taking responsibility for it is a broader engineering workflow. State the definition before comparing benefits or risks.

## 2. Potential benefits and appropriate tasks

Visual tools can shorten repetitive form, workflow and integration work. Domain specialists may directly express business rules, while developers implement complex extensions. Prompt-based prototypes can make an idea concrete quickly enough to gather feedback.

A useful candidate has a well-understood workflow, supported data sources, modest custom requirements and a clear owner. An internal equipment-request form might fit; a specialised low-latency processing engine may exceed platform abstractions. Suitability depends on constraints and verification, not whether the tool is fashionable.

Prototype speed is evidence of fast iteration on that prototype, not proof of lower total lifecycle cost. Include licensing, integration, operations, change effort, training and migration in the comparison.

## 3. Limits and lock-in

Platform convenience can create dependence on proprietary models, runtimes, connectors and permission systems. Exporting a table does not necessarily export workflow behaviour or a runnable application. Ask separately about data export, application portability and operational independence.

Custom extensions can add flexibility but also require developer skills and versioned interfaces. A workflow may become hard to understand as rules spread across screens, automations and connectors. Debugging needs visibility into inputs, transitions, failures and retries.

| Concern | Question to investigate |
|---|---|
| Functional fit | Can the required workflow and exceptions be expressed? |
| Integration | Are contracts, authentication and failure modes supported? |
| Quality | Can performance, security and usability be tested adequately? |
| Delivery | Can changes be reviewed, versioned, tested and promoted safely? |
| Operations | Are logs, monitoring, backups and support ownership available? |
| Exit | Can data and behaviour be migrated at acceptable effort? |

## 4. Governance for visual applications

Know what applications exist, who owns them, what data they access and which connectors they can use. Separate development, test and production where the platform supports it. Avoid building critical workflows around an individual's account or undocumented credentials.

Define permissions at the server or platform data layer, not merely by hiding UI fields. Review connector credentials and their scope. Confirm how releases, rollback and data migrations work; rolling back a visual workflow may not undo side effects already sent to another system.

Microsoft's Power Platform ALM guidance is an example showing that low-code work still has a lifecycle involving planning, development, testing, deployment and maintenance. The general lesson is to inspect the actual platform's lifecycle capabilities rather than assuming all visual tools behave alike.

## 5. AI-generated code and verification

A plausible-looking implementation can contain incorrect assumptions, insecure defaults, incompatible dependencies or missing failure paths. A successful happy-path demo does not show that the code meets all requirements. Generated tests can repeat the same mistaken assumption as generated code.

Use explicit acceptance criteria and small, reviewable changes. Inspect the diff and understand data access, error handling and external calls. Independently verify dependency names and documented interfaces. Run tests based on requirements, including negative and boundary cases, and use relevant static or security checks.

Treat repository documents, retrieved text and generated commands as information to evaluate; they do not acquire authority to change the task or expose credentials. Keep secrets and unrelated sensitive data out of prompts and examples. Generated code receives the same review and ownership as handwritten code.

## 6. A bounded engineering workflow

- Define the behaviour and constraints, including permissions and failure cases.
- Choose the approach by fit, maintainability and deployment needs.
- Build a small increment and inspect the resulting code or model.
- Test independently against the acceptance criteria.
- Record configuration, versions, dependencies and operational ownership.
- Release through an appropriate review and promotion process.
- Observe behaviour and fix defects through tracked changes.

When the team cannot explain or safely change a generated subsystem, first reduce that uncertainty through inspection, tests or reimplementation. More prompting alone does not establish correctness.

## 7. Worked comparison: campus equipment requests

A no-code form may capture requests and route approvals rapidly if supported permissions and connectors fit. Low code may add a custom inventory integration. Traditional code may be justified for specialised allocation rules or portability. An AI-generated prototype can test the proposed user journey, but production use still needs reviewed access rules and failure handling.

Test duplicate submissions, unauthorised approval, unavailable inventory, retries and audit history. A retry must not reserve the same item twice. Design around an explicit request identity and documented external contract.

If the prototype becomes a maintained product, establish an owner, inventory its dependencies, review its data flows, add requirement-derived tests, set up deployment and rollback, and document limitations. Classify it by evidence and supportability rather than the tool that originally created it.

## 8. How to answer a comparison question

State definitions, then compare the same dimensions: delivery effort, customisation, control, quality evidence, maintainability and exit cost. Recommend an approach for the stated scenario with a condition that could change the decision. Avoid absolutes such as “no code needs no testing” or “all generated code is unusable.”
