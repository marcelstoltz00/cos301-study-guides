## Scope

**General study guide — no L33 slides were supplied.** This rewrite explains low code, no code, AI-assisted engineering, and vibe coding in a slower way. The categories are useful distinctions, not perfect boxes.

## 1. Less manual code does not mean less responsibility

Low-code, no-code, and AI-generated systems still become real software. They still have users, data, permissions, integrations, bugs, deployment concerns, and maintenance needs.

The main change is **how the implementation is created**.

| Approach | How it is mainly built | Important reality |
|---|---|---|
| Traditional programming | Developers directly write and edit code | Highest control, but more engineering effort |
| Low code | Visual models/configuration plus possible extension code | Faster for supported patterns, limited by platform abstractions |
| No code | Visual building blocks with little or no custom code | Good for simple supported workflows, limited custom behaviour |
| AI-assisted engineering | AI suggests code that developers review and own | Quality depends on context, review, and tests |
| Vibe coding, narrow sense | Prompt, run, and iterate without really inspecting generated code | Fast exploration, but weak understanding and control |

The key study point: “no code” does not mean no software. Code still runs somewhere. The platform hides or manages it. You still need to understand behaviour, data, security, and lifecycle.

## 2. What low code and no code are useful for

These approaches can be very useful when the problem fits the platform.

Good candidates often have:

- well-understood workflows
- standard forms and approvals
- supported data sources
- simple business rules
- clear ownership
- modest custom logic
- acceptable platform constraints

Example: an internal equipment request form may fit a no-code or low-code platform. Users submit a request, a manager approves it, and a notification is sent.

Poor candidates often need:

- unusual performance requirements
- complex algorithms
- strict portability
- highly customised UI or logic
- unsupported integrations
- deep control over runtime behaviour

The bigger picture: choose the approach based on fit, not fashion. A quick prototype proves fast prototype creation. It does not automatically prove lower total cost, production readiness, or long-term maintainability.

## 3. Low code versus no code

No code usually means the builder uses supported visual pieces and configuration. Low code usually means visual building plus places where developers can add custom logic or integrations.

The boundary is blurry. Many platforms offer both.

Important comparison:

| Dimension | No code | Low code |
|---|---|---|
| Builder skill | Often domain specialist friendly | Often needs some developer involvement |
| Custom behaviour | Limited to available blocks | More extension options |
| Speed | Fast for supported workflows | Fast, but extension work adds effort |
| Risk | Hidden complexity and platform limits | Platform limits plus custom-code complexity |
| Maintenance | Depends on platform governance | Depends on platform plus code review |

Do not define low code by a fixed percentage of handwritten code. The important question is what the platform controls and where custom logic begins.

## 4. Vibe coding and AI-assisted engineering

AI-assisted engineering can be responsible when the developer reviews, understands, tests, and owns the result.

Vibe coding, in the narrow sense used here, means generating and iterating mostly by feel, without carefully inspecting the code. That can be useful for exploration, but risky for production.

Why? Generated code can look plausible while containing:

- incorrect assumptions
- missing permission checks
- insecure defaults
- nonexistent library calls
- poor error handling
- hidden dependency issues
- tests that repeat the same misunderstanding as the code

The difference is not whether AI was used. The difference is whether the human team has understanding, evidence, and ownership.

Safe pattern:

```text
Prompt -> inspect diff/model -> understand important behaviour -> test from requirements -> fix -> review -> release
```

Risky pattern:

```text
Prompt -> run happy path -> ship
```

## 5. Platform limits and lock-in

Low-code and no-code platforms can speed up work by providing ready-made storage, workflows, forms, connectors, and hosting. The trade-off is dependency on the platform.

Lock-in can appear in several forms:

| Lock-in area | Question to ask |
|---|---|
| Data | Can we export records in a useful format? |
| Behaviour | Can workflows, rules, and automations be moved? |
| Integrations | Are connectors proprietary or standard? |
| Identity/permissions | Can access rules be represented elsewhere? |
| Operations | Can we observe logs, failures, and performance? |
| Cost | What happens as usage grows? |

Exporting data is not the same as exporting the application. A CSV of requests does not recreate approval rules, notifications, retries, permissions, or UI behaviour.

This does not mean platforms are bad. It means exit cost and maintenance cost must be part of the decision.

## 6. Governance: keeping visual apps under control

Visual apps can spread quickly inside an organisation. That is useful, but it can also create hidden systems that depend on one person's account or undocumented credentials.

Governance means knowing:

- what apps exist
- who owns them
- what data they access
- which connectors they use
- what credentials they depend on
- how changes are reviewed
- how production differs from test
- how rollback and recovery work

Permissions should be enforced at the platform or server/data layer, not only by hiding fields in a screen. If users can call an underlying API or connector directly, UI hiding is not enough.

Also remember that rolling back a workflow version does not automatically undo side effects already sent to external systems. If an approval workflow reserved equipment in another system, rollback may need compensation or reconciliation.

## 7. AI-generated code still needs verification

Generated code should be treated like any other code: useful, but not trusted blindly.

Verification steps:

1. Write acceptance criteria before relying on generated output.
2. Inspect the generated diff or model.
3. Check data access and permission logic.
4. Verify dependencies against real documentation.
5. Test positive, negative, boundary, and failure cases.
6. Run relevant static, security, and dependency checks.
7. Keep secrets and sensitive data out of prompts.
8. Record ownership and maintenance notes.

Generated tests can be helpful, but they may share the same wrong assumption as the generated implementation. Independent tests based on requirements are safer.

Example: if the prompt forgot “a user may approve only their own department's requests,” both the generated code and generated tests may omit that rule.

## 8. A bounded engineering workflow

A sensible workflow for any of these approaches:

| Step | Why it matters |
|---|---|
| Define behaviour and constraints | Prevents building the wrong thing quickly |
| Choose approach by fit | Avoids forcing a platform onto an unsuitable problem |
| Build a small increment | Keeps review possible |
| Inspect code/model/configuration | Builds understanding |
| Test from requirements | Checks behaviour independently |
| Record versions and dependencies | Supports maintenance and rollback |
| Release through review | Reduces accidental production damage |
| Observe and fix defects | Treats it as real software |

If the team cannot explain or safely change a generated subsystem, pause and reduce uncertainty. Add tests, inspect the code, simplify it, or rebuild the risky part. More prompting alone does not prove correctness.

## 9. Worked example: campus equipment requests

Scenario: students or staff request equipment. A manager approves. Inventory is reserved. Notifications are sent.

Possible approaches:

| Approach | When it may fit |
|---|---|
| No code | Simple form, approval, and email notifications using supported connectors |
| Low code | Needs custom inventory integration or extra validation |
| Traditional code | Complex allocation rules, strict portability, or unusual performance/security needs |
| AI-generated prototype | Useful to explore the journey before committing |

Important tests:

- duplicate submission does not reserve twice
- unauthorised user cannot approve
- unavailable inventory service is handled safely
- retries do not duplicate external effects
- audit history records important actions
- permissions match organisational rules

If the prototype becomes a maintained product, it needs an owner, documented dependencies, reviewed data flows, tests, deployment process, rollback plan, and known limitations.

## 10. How to answer comparison questions

Use the same dimensions for each approach:

| Dimension | Question |
|---|---|
| Delivery speed | How quickly can this scenario be built? |
| Customisation | Can the required exceptions be expressed? |
| Control | Can the team inspect and change the important behaviour? |
| Quality evidence | Can performance, security, and correctness be tested? |
| Maintainability | Who will own and safely change it? |
| Operations | Can it be monitored, backed up, and recovered? |
| Exit cost | Can data and behaviour move elsewhere? |

Avoid absolutes. “No code needs no testing” is false. “All generated code is useless” is also false. The correct answer depends on scenario, risk, evidence, and supportability.

## Exam answer pattern

For low-code/no-code/AI questions:

1. Define the terms you are using.
2. Identify the scenario requirements and risks.
3. Compare approaches using the same dimensions.
4. Recommend one approach with reasons.
5. State what would change the recommendation.

Example: “A no-code platform fits a simple internal approval form if the required permissions, connectors, and audit trail are supported. Low code may be better if custom inventory integration is needed. Traditional code may be justified if portability or complex allocation rules dominate. In all cases, test duplicate requests, unauthorised approval, failure handling, and ownership.”

## Guided learning: Move from a quick idea to maintained software

The path is about evidence and ownership. A visual or generated implementation still needs the later stages.

### 1. Make the desired behaviour explicit

Write the important workflow, permission rules and failure cases. Choose an approach that can express them rather than starting with a platform label.

**Example:** An equipment request must not reserve the same item twice when the user retries.

**Common trap:** A vague prompt can lead to a plausible implementation of the wrong requirement.

### 2. Produce a small inspectable increment

Use visual configuration, extension code or generated code as appropriate. Keep a version of the artifact and understand important integration boundaries.

**Example:** A form and approval route use platform blocks; an inventory adapter implements a documented contract.

**Common trap:** No code describes how the builder works, not an absence of executable software.

### 3. Check independently of the implementation

Inspect behaviour and derive tests from actual requirements. Generated tests can reproduce the same mistaken assumption as generated code.

**Example:** Use another account to attempt an unauthorised approval, and repeat an uncertain reservation operation.

**Common trap:** Compilation and a happy-path demo do not establish production readiness.

### 4. Plan changes, operation and exit

Assign durable ownership, review credentials and confirm how data and workflows are recovered or migrated. Account for the full lifecycle cost.

**Example:** Exporting a CSV preserves records, but rebuilding proprietary workflow behaviour may still take substantial work.

**Common trap:** Data export is not the same as a portable runnable application.

### Interactive experiment: Inspect the fit of a visual platform

Toggle scenario requirements to see what evidence you would need. This is a reasoning checklist, not a vendor comparison or an automatic purchasing recommendation. Open the HTML guide to change the inputs and see the result.

### Check 1: A generated feature passes tests generated from the same prompt. What should you add?

- Independent checks based on the real requirements.
- A claim that the code has no defects.
- Only a longer prompt next time.

**Answer:** Independent checks based on the real requirements. Correct. Review and test assumptions independently, including failures and permissions.

### Check 2: Rolling back an approval workflow leaves a reservation in an external service. Why?

- Version control is impossible for visual models.
- Changing the executable version does not undo completed external effects.
- The rollback must have erased all business state.

**Answer:** Changing the executable version does not undo completed external effects. Correct. Plan reconciliation or compensation using stable operation identities.
