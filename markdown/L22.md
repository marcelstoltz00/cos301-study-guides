## Practical Architectural Design — How Architecture Actually Gets Done

The chapter has four themes: **Quantify → Decide → Communicate → Enforce.**

### 0. Why This Lecture Exists

An earlier lecture (styles) gave you *structure*; another (tactics) gave you *behaviour*. This lecture combines the two into practice.

**Two laws (Richards & Ford, *Fundamentals of Software Architecture*):**
- **First Law:** Everything in software architecture is a trade-off.
- **Second Law:** The why is more important than the how.

**The job of an architect:** turn fuzzy requirements into testable targets, make and record defensible decisions, communicate them to different audiences, keep them alive against drift, and evolve systems you didn't design.

### 1. The Whole Lecture Is One Mapping

Practical architectural design is a chain you can walk in both directions — every step has to justify the one before it:

| Step | Question | Source |
|---|---|---|
| 1. NFR | What must be true, as a number? | This lecture |
| 2. Quality attribute | Which "-ility" is it? This decides which tactics are even candidates. | ISO 25010 |
| 3. Tactic | What is the design move? Still technology-free. | Tactics lecture |
| 4. Pattern | What named structure implements that move? | GoF design patterns |
| 5. ADR | What did you decide, what did you reject, what trade-off did you accept? | This lecture |
| 6. Architectural design | The diagram, for whoever has to act on it. | Styles lecture |
| 7. NFR test | What check keeps it true after you stop looking? | This lecture |

**Rows 1 and 7 are a pair:** the test is just the NFR turned back into a question. If you cannot write row 7, row 1 was never a real requirement.

## Part 1: Quantify

### 2. "Scalable" Is Not a Requirement

You cannot design against "the system must be scalable," and QA cannot test it. **If you can't measure it, you can't architect for it, or prove you achieved it.** (Example: "checkout latency during a flash sale" only became actionable once it produced a number — 200ms → 5s.)

### 3. The Six-Part Quality Attribute Scenario

| Part | Booking-platform example |
|---|---|
| Source of stimulus | 50,000 concurrent users |
| Stimulus | Requests for seat availability |
| Environment | During a flash-sale promotion (overload) |
| Artifact | Availability query service |
| Response | Serve availability data |
| Response measure | p99 latency ≤ 800ms, error rate < 0.1% |

The **response measure** is what makes the scenario testable, and it is how you derive an SLO (Service Level Objective).

### 4. Step 2: Which "-ility" Is It? (ISO 25010 Quality Characteristics)

The characteristic you pick decides which family of tactics is even a candidate.

| Characteristic | Sub-characteristics |
|---|---|
| Functional suitability | completeness, correctness, appropriateness |
| Performance efficiency | time behaviour · resource utilisation · capacity |
| Compatibility | co-existence, interoperability |
| Interaction capability | *(was "usability" in the 2011 version of the standard)* |
| Reliability | faultlessness, availability, fault tolerance, recoverability |
| Security | confidentiality, integrity, accountability, authenticity, resistance |
| Maintainability | modularity, reusability, analysability, modifiability, testability |
| Flexibility | adaptability, scalability, installability, replaceability *(new grouping in the 2023 revision)* |
| Safety | fail safe, hazard warning, risk identification *(new in the 2023 revision)* |

**Two traps:**
- **"Scalable" is not performance** — since the 2023 revision, scalability sits under **Flexibility**, not Performance efficiency.
- **"Fast" and "fits in 1GB" are two different sub-characteristics** — time behaviour and resource utilisation respectively — so they are two separate requirements with two separate tests, not one.

### 5. From a Business Driver to an NFR: The Utility Tree

Start from what the business says, and refine until you hit something measurable. Each leaf is tagged with **(importance, difficulty)**, because you cannot afford to pursue all of them.

| Quality attribute | Sub-characteristic | (Importance, Difficulty) | Leaf requirement |
|---|---|---|---|
| Performance efficiency | time behaviour | (H, M) | Event page p99 ≤ 800ms during a flash sale |
| Performance efficiency | resource utilisation | (M, L) | Cache working set stays ≤ 1GB |
| Reliability | fault tolerance | (H, H) | Gateway slow: checkout still completes, no lost booking |
| Maintainability | modifiability | (M, L) | Add a payment provider in ≤ 3 person-days |
| Security | confidentiality | (H, M) | Card data never stored on the platform |

**Why the pair (importance, difficulty) matters:**
- **(H, H)** — this is where your design effort goes; where the interesting trade-offs live.
- **(H, L)** — you just do it.
- **(L, H)** — you push back on it; you're about to spend the year on something the business doesn't actually need.

### 6. Exercise 1 (worked): "The Booking Platform Must Stay Up Even If Things Fail"

| Step | Answer | Why this and not something else |
|---|---|---|
| Source of stimulus | One application server instance | Pick the smallest failure worth designing for — a whole-region outage is a different scenario with a different budget. |
| Stimulus | The instance crashes or stops responding to health checks | "Stops responding" matters — a hung process passes a naive check and keeps taking traffic. |
| Environment | Peak of a flash sale, at full concurrent load | The same failure on an idle Tuesday is not a design problem — the environment is what makes it hard. |
| Artifact | The booking API tier behind the load balancer | Name the thing that must survive, not "the system." |
| Response | The balancer detects the unhealthy instance and routes only to healthy replicas; in-flight requests are retried | Detection is part of the response — a system that recovers but takes four minutes to notice has not met this. |
| Response measure | < 0.1% of requests fail, full capacity restored within 30s, zero duplicate bookings | Three numbers, because "stays up" hides three separate promises: failure rate, recovery time, and correctness. |

**What the measure just bought you:** "< 0.1% failures" forces replication and a load balancer. "Within 30s" forces health checks and fast startup (ruling out a service that takes two minutes to warm up). "Zero duplicates" forces idempotency on the retry path.

## Part 2: Decide

### 7. "Six Months Later, Nobody Remembers Why"

A common failure timeline: a team debates Postgres vs. DynamoDB; Postgres wins, for reasons; two engineers leave; a new hire asks "why are we on Postgres?"; the whole debate happens again. **A decision that lives only in a meeting has zero durability and zero enforcement.** Second Law: the why is more important than the how — and the why is the part you write down.

### 8. The Architecture Decision Record (ADR) — Nygard, 2011

| Field | Content |
|---|---|
| Title + status | Proposed → accepted → superseded-by-ADR-023. The log stays honest. |
| Context | The problem, the forces, the alternatives considered. Not a project history — only what materially influenced the decision. |
| Decision | Crisp enough that someone could check whether the system actually complies. |
| Consequences | The trade-offs, including the negative ones and the debt you're taking on. **An ADR with no downsides is marketing, not engineering.** |

An ADR lives in the repo, next to the code — version-controlled like everything else.

### 9. Worked ADR Example — ADR-007: Cache Event & Venue Reads (Redis, 60s TTL)

**Context:** flash sales cause 25× read amplification on event/venue data (relates to a quality attribute scenario, "QAS-3"). Data changes ~daily. DB saturates at ~8,000 QPS. Alternatives considered: read replicas (lag on all reads, cost), CDN (per-event invalidation too slow), do nothing (violates QAS-3).

**Decision:** cache-aside in Redis for `GET /events/*` and `GET /venues/*`. 60s TTL + explicit invalidation on staff edit. Seat availability is explicitly *excluded* from caching — it's correctness-sensitive.

**Consequences:**
- (+) DB read load −90% under promotion; QAS-3 met at current scale.
- (−) Users may see details up to 60s stale; staff must be told edits aren't instant.
- (−) Redis is now on the critical path → needs its own availability scenario and a fallback (serve from DB, accept degraded latency).
- (−) Cold-start stampede on hot keys at TTL expiry → mitigate with request coalescing.

### 10. What a Bad ADR Looks Like

> "Decision: we will use Kafka. Consequences: better scalability."

This fails on three counts:
- **Nothing checkable** — no scope, no boundaries, no forces. Could you tell whether the system complies? No.
- **No negative consequences** — every real decision costs something (First Law). Where are the queue trade-offs: latency, duplicates, ordering, poison messages?
- **No alternatives** — you cannot defend a choice you never compared. What lost to Kafka, and why?

### 11. How Industry Wraps ADRs: The Design Review

Nearly every digital-native organisation reviews designs as written docs (RFCs / design docs) — e.g. Amazon, Airbnb, LinkedIn, Spotify, Uber, Monzo, GitLab. The process: **Draft the doc → Seniors comment → Revise → Ratify → ADR.** The loop between "draft" and "revise" is where the value is.

Google's framing: surface issues early, build consensus, force the trade-off discussion — "detailed but short enough to actually be read by busy people." In your first job you will write one of these, and senior engineers will comment on it.

## Part 3: Why Tactics Exist

### 12. The Eight Fallacies of Distributed Computing (Deutsch et al., Sun Microsystems, 1994)

Every one of these assumptions is false, and still causes 2am outages:

1. The network is reliable.
2. Latency is zero.
3. Bandwidth is infinite.
4. The network is secure.
5. Topology doesn't change.
6. There is one administrator.
7. Transport cost is zero.
8. The network is homogeneous.

### 13. Mapping Fallacies to Tactics

| Fallacy | Tactic that answers it |
|---|---|
| 1 · The network is reliable | Retries + idempotency · circuit breakers · dead-letter queues |
| 2 · Latency is zero | Caching · merging chatty services · coarse-grained requests |
| 4 · The network is secure | Zero trust: authenticate service-to-service; don't trust the VPC |
| 6 · There is one administrator | Version internal APIs · contract tests (renaming a field like `userId` must not crash a downstream team's service) |

**The lesson:** stop happy-path engineering. Assume the network drops packets and the partner API is down. Design for *when*, not *if*.

### 14. What Ignoring the Fallacies Produces

- **The distributed monolith** — separately deployed, but tightly coupled: nothing can change or fail independently. All the cost of microservices, none of the benefit. The most common modern design error.
- **Premature distribution** — a day-one-microservices startup: you cannot distribute what you haven't modularised yet. Splitting early just spreads your existing problems across a network (Fowler's "monolith-first").
- **The operational tax** — ~40% of engineering time spent on infrastructure, not features. The tax scales with *service count*, not user count, and is heaviest when the team is smallest.

**Pragmatic default:** the modular monolith, with clean internal boundaries, as one deployable — until scale (or Conway's Law) forces otherwise. In a monolith, a call is a function; in microservices, it's a network request subject to all eight fallacies.

## Part 4: Map It

### 15. Steps 3 and 4: A Tactic Is Not a Pattern

| | Tactic | Pattern |
|---|---|---|
| Definition | A design decision that influences how the system responds for one quality attribute. Technology-free, usually one sentence. | A named, reusable structure that implements one or more tactics. ("Patterns are bundles of tactics" — Bass.) |

| Tactic (the move) | Patterns that implement it (the structure) |
|---|---|
| Cache the read path | Cache-aside · read-through · write-through · refresh-ahead, using Proxy or Decorator to intercept the call |
| Tolerate a failing dependency | Circuit Breaker · Bulkhead · Retry with backoff · Fallback |
| Decouple producer from consumer | Queue · Publish-Subscribe · Observer |
| Isolate the volatile part | Adapter · Strategy · dependency inversion |
| Restrict what may call what | Layers · package boundary with a public API · Facade |

**Why the distinction earns its keep:** the tactic follows from the quality attribute, so it's nearly forced. The pattern follows from your context, so it's a genuine choice — and *that's* what you argue about and record in the ADR. One tactic, several candidate patterns, one decision to justify.

**Common mis-map:** the *State* pattern varies an object's behaviour as its internal state changes — it is **not** a cache-consistency pattern. Cache consistency is cache-aside or write-through, plus an invalidation mechanism.

### 16. Step 5: Where the Trade-off Actually Lives

| Concept | Definition |
|---|---|
| Sensitivity point | A property critical for achieving one quality attribute response. A "yellow flag" — use caution when changing this. |
| Trade-off point | A property that is a sensitivity point for *more than one* attribute. Turning it up helps one and hurts another. |
| Risk | A potentially problematic decision, or one you haven't made yet. |
| Non-risk | A good decision that rests on an assumption. It stays a non-risk only while the assumption holds. |

| Turn this up… | …this improves | …and this degrades |
|---|---|---|
| Cache TTL | time behaviour, load on the database | consistency: users see stale data for longer |
| Cache size | hit rate, so time behaviour again | resource utilisation, and the monthly bill |
| Encryption strength/scope | confidentiality | time behaviour, and operational complexity |
| Number of replicas | availability, read throughput | consistency, cost, debugging difficulty |
| Retry count | fault tolerance on a flaky call | latency, duplicate risk, load on something already failing |
| Layers of abstraction | modifiability, testability | simplicity, and sometimes performance |

**None of these has a "correct" setting.** Your ADR's consequences section is the record of which side you chose, and what you accepted in exchange.

### 17. Worked Example: "Load Pages Fast, and Cache Data When Needed, up to 1GB"

| Step | The mapping, filled in |
|---|---|
| 1 · NFR | Not testable as given, and it's two requirements in one sentence. Quantified: (a) event page server response p99 ≤ 50ms with the cache warm; (b) cache working set ≤ 1GB, evicting least-recently-used. |
| 2 · Quality attribute | Performance efficiency. (a) is time behaviour, (b) is resource utilisation — different sub-characteristics, so two separate tests. |
| 3 · Tactic | Cache the read path in memory. (Says nothing about Redis yet.) |
| 4 · Pattern | Cache-aside on read, with explicit invalidation on staff edit. Not the State pattern — State varies behaviour with internal state, it doesn't manage cache consistency. |
| 5 · ADR | ADR-007: Redis, 60s TTL, maxmemory 1GB, allkeys-lru. Rejected: read replicas (lag on every read), CDN (per-event invalidation too slow). Accepted cost: up to 60s stale, and Redis is now on the critical path. |
| 6 · Architectural design | Redis appears as its own box on the read path, with the fallback to the database drawn explicitly, because it will be used. |
| 7 · NFR test | (a) A CI performance test asserts p99 ≤ 50ms with the cache warm. (b) A monitor asserts `used_memory` ≤ 1GB and alerts when the eviction rate spikes. |

**Trade-off point:** TTL is a sensitivity point for time behaviour *and* for consistency at the same time — exactly what makes it a trade-off point rather than a simple tuning knob. 60s is a business decision about acceptable staleness, not a purely technical one.

**Architectural design (step 6), described:** the application talks to *both* the cache and the database (that's what makes it cache-aside rather than read-through). Seat availability reads go straight to the database, bypassing the cache entirely, because correctness beats latency on that specific path. When box-office staff edit an event, the cache key is invalidated immediately — the system does not wait for the TTL to expire.

### 18. Exercise A (worked): "Must Not Lose Bookings When the Payment Gateway Goes Down"

| Step | Answer |
|---|---|
| 1 · NFR | Zero accepted bookings are lost while the gateway is unavailable, and every accepted booking reaches a terminal state (paid or cancelled) within 24 hours. Checkout p99 stays ≤ 2s while the gateway is degraded. |
| 2 · Quality attribute | Reliability: fault tolerance and recoverability. **Not** availability — your system is up; the failure is in a dependency you don't own. |
| 3 · Tactic | Isolate the failing dependency so it cannot consume your threads, and defer the work rather than dropping it. |
| 4 · Pattern | Circuit Breaker and Bulkhead for the isolation; a queue with an idempotency key for the deferral; retry with exponential backoff behind the breaker. |
| 5 · ADR | On breaker trip, accept the booking as payment-pending and reconcile asynchronously. Accepted cost: the customer holds a confirmation that is not yet a payment, so finance needs a reconciliation report and a cancellation path. |
| 6 · Architectural design | A breaker at the caller's boundary, a queue and worker, a reconciliation job, and a new "pending" state in the booking model. Three of those four are operational work, not code. |
| 7 · NFR test | Stub the gateway as down and as slow, then assert zero lost bookings and a terminal state within the window. Run it in CI, and kill the gateway in staging on a schedule. |

**Architectural design, described:** the circuit breaker sits on the caller's side of the boundary (Checkout API), wrapping every call out to the external payment gateway with a 2-second timeout. On trip, the booking is accepted as payment-pending and pushed onto a booking queue (with an idempotency key), processed by a worker, and a reconciliation job (running on a schedule) later settles it as paid or cancelled. **The uncomfortable box:** "payment-pending" is a state the business has to understand, staff have to explain, and finance has to clear — that's the real cost of this design. Everything below the top row of the diagram exists only because the gateway can fail.

**Trade-off point:** retry count and breaker threshold. Turning them up improves fault tolerance and degrades latency, duplicate risk, and the load on something already failing.

### 19. Exercise B (worked): "User Payment Data Must Be Protected" (POPIA Applies)

**Hint given:** the strongest answer to "how do we protect this data?" is usually "we do not hold it."

| Step | Answer |
|---|---|
| 1 · NFR | No card number is ever persisted or logged by the platform. Every access to stored personal data is authenticated, authorised, and written to an audit log retained for the POPIA-required period. |
| 2 · Quality attribute | Security: confidentiality, integrity, and accountability. Accountability is the sub-characteristic students most often drop — and it's the one POPIA actually enforces. |
| 3 · Tactic | Reduce the attack surface by not holding the data; authenticate and authorise every access; audit everything; encrypt in transit and at rest for what remains. |
| 4 · Pattern | Tokenisation with a vault — the gateway holds the card, you hold a token. An Adapter keeps all crypto/token handling in one component. Role-based access control on the rest. |
| 5 · ADR | Store a gateway token, never a card number. Accepted cost: refunds and recurring billing now depend on that gateway's token lifetime, so switching providers becomes genuinely expensive — you have traded portability for confidentiality. |
| 6 · Architectural design | Card data never crosses the platform boundary at all. The payments adapter holds the token; key management sits outside the application. |
| 7 · NFR test | A build-failing scan for card-shaped data in the database and in logs, plus a rule that any new column on the payments table fails review until it is classified. |

**Architectural design, described:** the whole design is one line — where the trust boundary falls, and what is never allowed to cross it. Card data goes straight from the customer's browser to the gateway's vault; it never enters the booking platform at all. Only a token crosses into the platform, held by the payments adapter (the only crypto-aware code) and stored in the database as a token, never a PAN (Primary Account Number). Key management and the audit store deliberately sit **outside** the application — if the app can read its own keys, an attacker inside the app can too. **Read the diagram for what's missing:** there is no arrow carrying a card number into any box the platform owns — that absence *is* the security design (and it's also why swapping payment gateways later is expensive).

**Trade-off point:** scope of encryption and key-rotation frequency — both sensitivity points for confidentiality *and* for time behaviour/operability. A second trade-off hides in the ADR row: tokenisation buys confidentiality and sells replaceability.

### 20. Exercise C (worked): "Add a New Payment Provider Quickly"

**Hint given:** a modifiability measure is usually a count or a blast radius, not a duration. "No change outside this module" is a measurable claim.

| Step | Answer |
|---|---|
| 1 · NFR | Adding a provider requires no change outside the payments package, introduces no new cross-package dependency, and takes ≤ 3 person-days measured on a stub provider. |
| 2 · Quality attribute | Maintainability: modifiability. (Flexibility: replaceability is the neighbouring characteristic — the 2023 ISO 25010 revision separates them. Say which you mean and the measure follows.) |
| 3 · Tactic | Isolate the volatile part, depend on an abstraction rather than a concrete provider, and put an explicit contract at the boundary. |
| 4 · Pattern | One `PaymentProvider` interface; an Adapter per provider; Strategy to select at runtime; dependency inversion so the domain never imports a provider SDK. |
| 5 · ADR | The domain depends only on the interface. Accepted cost: one more layer of indirection, and a real leaky-abstraction risk when providers differ (e.g. on 3-D Secure or partial refunds) — the interface will need to change, and that is the expensive day. |
| 6 · Architectural design | A package diagram. What must **not** appear on it: any arrow from the domain package to a provider package. The absence is the design. |
| 7 · NFR test | A static rule that fails the build when anything outside `payments.adapters` imports a provider SDK directly. (This is exactly what Shopify's Packwerk tool does — see the Synthesis case study below.) |

**Architectural design, described:** the `Booking domain` package depends on a `PaymentProvider` interface (the contract). `StripeAdapter`, `PayFastAdapter`, and `PeachAdapter` packages each implement that interface and depend on their respective external SDKs. The domain package knows nothing about any specific provider. The one arrow that must never exist: a direct dependency from the domain package to any provider SDK.

**Trade-off point:** number of layers of abstraction. It buys modifiability and sells simplicity, and sometimes performance. An interface built for one provider is a guess; an interface built for three is a design — which is why premature abstraction is as costly as no abstraction at all.

## Part 5: Organizational Reality

### 21. Conway's Law Is Not Optional

**Conway's Law (1968):** a system copies the organisation's communication structure. Team boundaries become service boundaries, whether you intend it or not.

**Cognitive load:** overloaded teams slow down and make mistakes — draw service boundaries a single team can actually hold in its head.

**Inverse Conway Manoeuvre (Team Topologies):** reshape the teams *first* to get the architecture you want, rather than accepting whatever architecture your current org chart produces by default.

**Punchline:** microservices are fundamentally an organisational pattern. "Should we use them?" starts with "how many teams do you have?" — "Team assignments are the first draft of the architecture." (Michael Nygard)

### 22. The Constraints the Textbook Might Not Tell You

| Constraint | Description |
|---|---|
| Cost | Every tactic is a monthly bill — a replica, a cache, a queue. Cost is itself a quality attribute. |
| Time | Defer what's cheap to reverse. Decide early only what's expensive to reverse — e.g. data ownership, sync vs. async boundaries. |
| Team skill | Technology your team can't operate at 2am is, in practice, an availability decision. |
| Compliance | E.g. POPIA constrains how the platform handles user and payment data. Encryption is necessary, not sufficient — keys, auditing, and access control matter too. |
| Legacy | Most engineers will never see a greenfield project. You will inherit an existing system — which is the next topic. |

### 23. Evolving What You Inherit: The Strangler Fig

Fowler, 2004: you don't stop a system to replace it — you build around it while it keeps running.

| Phase | Description |
|---|---|
| 1. Front it with a façade | All traffic routes through an indirection layer; behaviour unchanged. |
| 2. Replace slice by slice | Build new components; redirect one capability at a time. Each cycle is self-contained and reversible. |
| 3. Decommission | When nothing routes to the legacy system anymore, switch it off. |

**In the wild:** Shopify (monolith → services, while revenue grew from $100M to $1B+), Netflix (datacenter → AWS). This is the opposite of a big-bang rewrite.

**The catch:** data migration is the hardest part of every slice — shared databases, batch jobs, and reporting parity all have to be reconciled along the way.

## Part 6: Enforce

### 24. Documentation Does Not Stop Drift. Running Checks Do.

A decision can be correct and still have zero enforcement once it leaves the meeting room. A **fitness function** (term from *Building Evolutionary Architectures*) is any automated check of an architectural constraint — architecture tests, run in CI, next to your unit tests.

**Examples:**
- **ArchUnit-style rule:** "No class in `web.*` may depend on `persistence.*`."
- **Contract tests:** a breaking API change without a version bump fails the build (this directly answers Fallacy #6 — "there is one administrator").
- **Latency budget:** a CI performance test asserts a quality attribute scenario's p99 ≤ 800ms before merge.

**Litmus test for any ADR:** "Can I describe what a violation looks like?" If yes — write the check.

**The whole chain, one more time:** NFR sets the target → tactic and pattern shape the design → ADR records the trade-off → the NFR test keeps it true.

## Synthesis: Two Real Case Studies

### 25. Case 1 — Netflix Runs This Chain for Availability

| Step | Netflix's answer |
|---|---|
| 1. Quality attribute | Availability. One home page is assembled from a large number of independent services. |
| 2. NFR as a scenario | A failure or latency spike in any single downstream service must not take down playback or the home page. Measure: the page still renders, degraded, and the failure does not cascade. |
| 3. Tactic | Circuit breaker, bulkhead isolation, and a defined fallback for every remote call. |
| 4. Pattern | Circuit Breaker (from Nygard's *Release It!*), implemented as Hystrix around every cross-service call. |
| 5. Decision + cost | Every caller must define a degraded response. Consequence: thread-pool isolation costs memory and context switching, and someone has to decide what "degraded" means for every single feature. |
| 6. Architectural design | The breaker sits at the caller's boundary, not inside the callee — so it wraps every outbound call on the diagram. |
| 7. Fitness function | Chaos Monkey terminates production instances at random. If resilience has regressed, you find out on a Tuesday afternoon, not during a launch. |

**Postscript:** Hystrix is now in maintenance mode, and Netflix points new work at resilience4j — the pattern outlived the specific implementation, which is the First Law in miniature: they traded a mature library for a better fit and accepted the migration cost.

### 26. Case 2 — Shopify Runs the Same Chain for Modifiability

| Step | Shopify's answer |
|---|---|
| 1. Quality attribute | Modifiability, inside a Rails monolith of millions of lines worked on by hundreds of developers. |
| 2. NFR as a scenario | A change inside one business domain must not require touching, or even understanding, another. Measure: no new cross-package dependency, and no reach past another package's public API. |
| 3. Tactic | Isolate responsibilities, depend on abstractions, and put explicit contracts at the boundaries. |
| 4. Pattern | The modular monolith: packages with a declared public API — information hiding and low coupling, applied at package scale. |
| 5. Decision + cost | Stay one deployable and enforce boundaries statically, rather than splitting into microservices. Consequence: no independent deploys or scaling, plus a tool to run and a backlog of existing violations to burn down. |
| 6. Architectural design | A package diagram — there is still only one deployable unit. |
| 7. Fitness function | Packwerk, a static analyser run in CI. It reports two violation types: dependency and privacy. Roughly 48 packages with 30 enforcements in the core monolith. |

**Read rows 4 and 7 together:** Shopify's fitness function checks exactly the two design principles taught earlier in the course — low coupling is the dependency check, information hiding is the privacy check.

## Postscript: AI, Two Points

1. **AI components are a new architectural element.** An LLM in the loop makes a deterministic system non-deterministic — output varies, and edge cases arrive faster and at scale. That is a quality-attribute problem, and you already own the vocabulary for it: timeouts, fallbacks, validation layers, circuit breakers around model calls, and a quality attribute scenario for accuracy and latency.
2. **AI accelerates the *how*. The *why* is still your job.** Architecture is long-horizon trade-off analysis across code, infrastructure, people, regulation, cost, and failure. Studies of LLM-generated architectures still show weak design rationale. The why is precisely what an ADR captures — the Second Law is your job security.

## Final Takeaway

Styles organise systems. Tactics shape behaviour under load, failure, attack, and change. This lecture is the *practice*: **Quantify → decide & record → communicate → respect the organisation → enforce → evolve.**

Everything is a trade-off. The why matters more than the how.
