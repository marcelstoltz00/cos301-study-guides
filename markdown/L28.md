## Scope and source

Based on the supplied L28 Deployment Diagrams notes. The worked design and questions are study exercises. UML vocabulary and recovery caveats below are supporting explanations, rather than additional claims about the exam.

## 1. Purpose: where does the software actually run?

A deployment diagram connects software to its runtime infrastructure. It answers **where instances run, how they communicate, and what happens when infrastructure fails**. In the 4+1 architectural model this is the physical view. A view describes the system from selected concerns; a viewpoint supplies conventions for constructing that view.

A logical component diagram can remain the same across environments. Deployment views usually cannot: production and staging can have different replica counts, recovery arrangements, and boundaries. Name one system and one environment per view. Choose detail for the reader: an operator needs recovery paths; a security reviewer needs trust and identity; a cost reviewer needs instance counts and sizes.

### Eight questions to remember

| Question | Evidence the diagram should contain |
|---|---|
| Which system and environment? | Name, purpose, production/staging scope |
| Which failure domains? | Region, zone/site, host, runtime nesting |
| What runs where, how many copies? | Deployable name, version, instance count |
| What provides isolation? | VM, runtime, account, process and policy boundaries |
| How do boxes communicate? | Directed, labelled protocol connections |
| Where does trust change? | Boundaries, authentication and authorisation points |
| Where is state, how is it recovered? | Stores, replicas, backups, RPO and RTO |
| Who maintains the view? | Owner, source of truth, verification date |

## 2. Names and notation

Use **the concept first, product second**: “workload packet filter (security group)” is understandable beyond one provider. Common concepts include private network, failure-isolated site, L4/L7 entry point, workload identity, relational store, object store, secret store and durable queue.

A legend resolves overloaded words: a C4 container is a runnable application or data store, not necessarily an operating-system container; a service can mean a business capability or a Kubernetes networking resource. A node may mean a deployment target or a worker machine.

**UML supplement:** a node is a computational resource; a device represents hardware; an execution environment hosts executable software; an artifact is a deployable physical piece such as an executable or package. Deploy artifacts to nodes and show communication paths between nodes. A component describes modular software structure; an artifact can implement it. Do not mix these levels without a legend.

## 3. Failure domains and isolation

Nest according to shared failure: **region → zone/site → host → runtime → process**. Three replicas on one host survive a process crash only if the others remain healthy; they do not survive loss of that host. Two zones in one region still share regional risks.

Security isolation and failure isolation answer different questions. An account separates credentials and administration; a zone separates some infrastructure failures. Neither automatically implies the other.

| Boundary | What to remember |
|---|---|
| Separate account/subscription | Can reduce administrative blast radius when credentials and permissions are separated |
| VM/hypervisor | Separate guest kernels; still depends on configuration and hypervisor security |
| Sandboxed runtime | Adds a boundary beyond an ordinary shared-kernel container |
| Ordinary OS container | Shares the host kernel; a kernel compromise may cross isolation |
| Kubernetes namespace | Naming and access-control scope; not network isolation by itself |
| Application tenant check | Requires correct enforcement on every relevant access |
| Threads in one process | Share process memory; no independent security boundary |

## 4. Label every connection

Use a consistent pattern: **protocol/version :port, encryption, authentication, sync/async**. Specify in the legend that arrows show the connection initiator; responses can travel back on that connection.

Example: `order-api → database: PostgreSQL :5432, TLS, certificate authentication, sync, pool 20`. These are example configured values, not mandatory ports for all deployments. JDBC and ODBC are client APIs, not the database wire protocol. Show the actual protocol and configured port so network rules can be reviewed.

An L4 balancer distributes connections. One long-lived HTTP/2 connection can carry many requests to one selected backend; adding replicas alone may not spread those requests. An appropriate L7 balancer or client-side balancing can distribute work more effectively. HTTP/1.1 can also reuse connections: the important distinction is connection-level versus request-level balancing.

**Synchronous calls** put downstream latency and availability directly on the request path. **Asynchronous messaging** can absorb a temporary consumer outage, but only within queue capacity and retention. Show durability, consumer lag, retries, dead-letter handling and backpressure. At-least-once delivery needs idempotent processing to avoid duplicate effects.

## 5. Trust and identity

A trust boundary separates security assumptions, policies or privilege levels. Examples include internet/private network, tenant boundaries, operator access and artifact registry/runtime. Show TLS termination and each hop after it. Encrypted transport alone does not prove that a caller may perform an action. mTLS can authenticate both endpoints when certificates are validated, but resource authorisation remains necessary.

Use STRIDE to question crossings: **Spoofing, Tampering, Repudiation, Information disclosure, Denial of service, Elevation of privilege**. For browser-to-API traffic, consider stolen sessions, modified input, missing audit evidence, verbose errors, resource exhaustion and unauthorised administration.

## 6. State, replication and recovery

**RPO** is the target maximum acceptable data-loss interval. **RTO** is the target maximum acceptable restoration time. Targets need measurements: asynchronous replication lag may exceed a target during an incident. Synchronous replication can protect acknowledged writes against the failures covered by its configuration, but does not promise survival of every possible disaster.

Replication improves continuity; backups preserve recoverable history. A mistaken deletion can propagate to every live replica. Record database engine/version, replication mode, placement, failover mechanism, backup retention and restore tests.

## 7. Keep the view trustworthy

Keep diagram source beside infrastructure code, review changes together and render in CI. One model can produce several views with consistent names. Record an owner, source path, verification date and commit where appropriate. A generated view still needs checking against deployed reality.

Leave internal class structure, every environment variable and the full delivery pipeline out unless they answer the chosen deployment concern. **Exam method:** name the failure or threat, point to the missing topology fact, propose a change, and state the cost or remaining limitation.

## Guided learning: Follow a request through the deployment

Select each box. The arrows show the illustrative request path, not separate failure domains. Then change the placement in the failure experiment.

### 1. Start outside the trust boundary

A user request begins in an environment the application does not control. Identify what the user can send and where the server first validates identity and input.

**Example:** A valid session can identify Alice; it does not permit reading Bob’s order.

**Common trap:** A request arriving from an internal address is not automatically authorised.

### 2. Choose a backend

The entry point routes traffic to a running instance. Its own placement and health matter: multiple backends do not help when the only entry point fails.

**Example:** An L4 balancer assigns a connection. Many HTTP/2 streams can reuse that one assignment.

**Common trap:** A box labelled load balancer does not prove that requests are balanced at the application layer.

### 3. Look outside the replica boxes

Trace each instance to its host, zone and region. Redundancy protects only against failures that leave a usable instance and its dependencies alive.

**Example:** Two API processes on Host A both disappear when Host A is lost.

**Common trap:** Counting replicas without examining their common parents hides shared failure.

### 4. Follow the dependency to state

The request may still depend on one database. Show the primary, standby, promotion path and backup history. Confirm the recovery targets through exercises.

**Example:** A standby can support continuity after host loss; a historical backup can recover an accidental deletion copied to that standby.

**Common trap:** Replication is not a substitute for recoverable history.

### Interactive experiment: What survives this failure?

Predict first: will this placement leave an API and a usable database copy? This simplified model excludes entry-point failures and models topology, not failover time. Open the HTML guide to change the inputs and see the result.

### Check 1: Two APIs are in separate zones, but both use one database host. That database host fails. What is the strongest conclusion?

- The replicas guarantee checkout works.
- The database dependency may stop both request paths.
- There must be zero data loss.

**Answer:** The database dependency may stop both request paths. Correct. Review the complete request path, including state and failover.

### Check 2: A deletion reaches the primary and its live replica. Which control addresses recovery of the older records?

- A recoverable historical backup or point-in-time recovery path.
- One more replica of the already deleted state.
- Increasing the HTTP timeout.

**Answer:** A recoverable historical backup or point-in-time recovery path. Correct. Test restoration and retention rather than assuming a copy is usable.
