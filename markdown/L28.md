## Scope and source

Based on the supplied L28 Deployment Diagrams notes. This rewrite keeps the same ideas, but slows them down and explains why each idea matters when you are studying, drawing, or reviewing a deployment diagram.

## 1. What a deployment diagram is really trying to show

A deployment diagram answers a practical question: **where does the running software live, and what infrastructure does it depend on?**

That means it is not mainly about classes, methods, UI screens, or business rules. It is about runtime placement. If the system is online right now, which machines, containers, databases, queues, networks, and external services are involved? How are they connected? What could fail together?

The reason this matters is that many system problems are not visible in code alone. You might have three copies of an API in the code or configuration, but if all three copies run on the same host, one host failure can still remove them all. A deployment view helps you see operational risk.

Think of the difference like this:

| View | Main question | Example |
|---|---|---|
| Logical/component view | What are the main software parts? | Web app, API, payment service |
| Deployment view | Where do those parts run? | API v2 x3 across two zones, database in Zone A |
| Security/deployment review | Where do trust and failure boundaries exist? | Internet to private subnet, app to database |

In the 4+1 architecture model, deployment is the **physical view**. A **view** is the picture you produce. A **viewpoint** is the set of rules for what belongs in that picture. The important study point is simple: draw the system from the concerns of the person who must use the diagram.

An operator cares about recovery. A security reviewer cares about trust boundaries and identities. A cost reviewer cares about instance counts and resource sizes. If the diagram tries to show everything for everyone, it becomes unreadable.

## 2. Start every diagram with scope

Before drawing boxes, state the scope:

- which system is being shown
- which environment is being shown
- which level of detail is being shown
- when the diagram was last checked

Production and staging should usually be separate diagrams because they often differ. Staging may have one database and one API instance. Production may have replicas, backups, monitoring, and stricter network controls. If you mix them, the reader cannot tell what risk exists in the real service.

Use this checklist when studying or drawing:

| Question | Why it matters |
|---|---|
| Which system and environment? | Avoids mixing production, staging, and examples |
| What runs where? | Shows the connection between software and infrastructure |
| How many copies exist? | Helps reason about capacity and redundancy |
| What can fail together? | Reveals shared failure domains |
| How do parts communicate? | Helps review ports, protocols, latency, and firewall rules |
| Where does trust change? | Reveals where authentication and authorisation are needed |
| Where is state stored? | State is often the hardest part to recover |
| Who owns the diagram? | Prevents outdated diagrams from becoming misleading |

The bigger picture: a deployment diagram is not only documentation. It is a thinking tool. If you cannot explain what happens when a box fails, the diagram probably does not yet show enough.

## 3. Use names that explain the concept, not only the product

Cloud and platform names can hide the actual idea. A label like `SG-042` or `Azure NSG` may be meaningful to one team, but not to someone trying to understand the architecture. A clearer label is concept first, product second:

```text
workload packet filter (security group)
relational database (PostgreSQL)
durable object storage (S3 bucket)
L7 HTTPS entry point (application load balancer)
```

This helps because exams and design reviews usually care about what role the thing plays. The product name is secondary. You need to know whether something is a network boundary, a compute node, a database, a queue, or a secret store.

Also define overloaded words in a legend. For example, **container** can mean a C4 container, which is a runnable application or datastore, or it can mean an operating-system container such as Docker. **Node** can mean a UML deployment target or a Kubernetes worker machine. If the word can mean two things, the diagram must remove the ambiguity.

UML terms in plain English:

| UML term | Easy meaning |
|---|---|
| Node | A place where software can run |
| Device | Physical hardware |
| Execution environment | Runtime that hosts software, such as a JVM or container runtime |
| Artifact | Deployable thing, such as a package, executable, or image |
| Communication path | A connection between deployment nodes |

The study trick is to keep levels separate. Components explain software structure. Artifacts are the physical deployable pieces. Nodes are where those artifacts run.

## 4. Failure domains: what disappears together?

A **failure domain** is a group of things that can be affected by the same failure. This idea is central to deployment diagrams.

A common nesting is:

```text
region -> zone/site -> host -> runtime -> process
```

If three API processes run on one host, they are three processes but only one host-level failure domain. A process crash might leave two alive. A host failure removes all three. If two zones are in the same region, they are separate for some failures, but still share regional risks.

Why this matters: redundancy only helps against failures it is actually separated from.

| Placement | What it protects against | What it may not protect against |
|---|---|---|
| Multiple processes on one host | One process crash | Host loss |
| Multiple hosts in one zone | One host loss | Zone outage |
| Multiple zones in one region | Some zone-level failures | Region outage |
| Multiple regions | Regional outage, depending on design | Global dependency or bad deployment |

Do not just count replicas. Ask where they live and what they still share.

## 5. Isolation is not the same as redundancy

Security isolation and failure isolation are related, but they are not the same thing.

A separate account or subscription can reduce administrative blast radius. A zone can reduce infrastructure failure blast radius. A container can isolate packaging and runtime dependencies. None of these automatically solves every security or availability problem.

Examples:

| Boundary | What it helps with | Important limitation |
|---|---|---|
| Separate account/subscription | Separates permissions and administration | Bad shared credentials can still break isolation |
| VM/hypervisor | Separates guest operating systems | Still depends on host and hypervisor security |
| OS container | Packages and isolates processes | Shares the host kernel |
| Kubernetes namespace | Groups names and access rules | Not automatic network isolation by itself |
| Tenant check in code | Enforces business-level separation | Must be checked on every relevant access |
| Threads in one process | Concurrent execution | Shared memory, not a security boundary |

The bigger picture: a good diagram should show enough boundaries for the reader to ask, “If this part is compromised or fails, what else is affected?”

## 6. Label every connection with useful facts

An arrow that only says `uses` is often too vague. A reviewer needs to know what kind of communication is happening.

Use a pattern like:

```text
source -> target: protocol/version :port, encryption, authentication, sync/async
```

Example:

```text
order-api -> database: PostgreSQL :5432, TLS, certificate authentication, sync
```

Why each part matters:

| Label part | Why it matters |
|---|---|
| Protocol | Determines compatibility and network rules |
| Port | Helps configure firewalls and security groups |
| Encryption | Shows whether traffic is protected in transit |
| Authentication | Shows how the caller proves identity |
| Sync/async | Shows whether the caller waits for the result |

JDBC and ODBC are client APIs, not the database wire protocol itself. If the network team needs to open a path, they need the actual protocol and configured port.

Arrow direction should also be defined. A common convention is that the arrow points from the connection initiator to the receiver. Responses can still travel back on that same connection.

## 7. Synchronous versus asynchronous communication

A **synchronous** call means the caller waits. If the database is slow, the API request is slow. If the database is unavailable, the API may fail. This puts the dependency directly on the request path.

An **asynchronous** design uses something like a queue. The caller can place work onto the queue and continue, while a worker processes it later. This can help during temporary outages, but it does not make failure disappear.

For async messaging, show:

- whether the queue is durable
- how long messages are retained
- what happens on retry
- where failed messages go
- how duplicate messages are handled
- what happens when consumers fall behind

The key reason is that many queues use at-least-once delivery. That means a message may be delivered more than once. The consumer must be **idempotent**, meaning processing the same message again should not create a duplicate business effect.

Example: retrying a payment message must not charge the customer twice.

## 8. Trust boundaries and identity

A **trust boundary** is a place where security assumptions change. Crossing from the public internet into a private service is a trust boundary. Crossing from one tenant to another is a trust boundary. Moving from normal user access to administrator access is a trust boundary.

Show where TLS terminates. If TLS ends at the load balancer, then traffic from the load balancer to the API is a separate hop that must be considered. Encryption proves traffic is protected in transit; it does not prove the caller is allowed to perform the business action.

Authentication answers: **Who are you?**

Authorisation answers: **Are you allowed to do this action on this resource?**

mTLS can authenticate both endpoints if certificates are validated correctly. It still does not replace resource-level authorisation.

Use STRIDE as a memory aid when reviewing a trust boundary:

| STRIDE | Question to ask |
|---|---|
| Spoofing | Can someone pretend to be another user or service? |
| Tampering | Can data be changed in transit or storage? |
| Repudiation | Can someone deny an action because evidence is missing? |
| Information disclosure | Can private data leak? |
| Denial of service | Can the system be made unavailable? |
| Elevation of privilege | Can someone gain powers they should not have? |

## 9. State, replication, backups, RPO, and RTO

State is data the system must remember. Databases, queues, uploaded files, sessions, and object stores can all hold state. State deserves special attention because it is harder to replace than stateless application instances.

Two recovery terms matter:

| Term | Meaning | Simple question |
|---|---|---|
| RPO | Maximum acceptable data loss | How much recent data can we afford to lose? |
| RTO | Maximum acceptable restoration time | How long can the service be down? |

If the last usable backup is 19 hours old, the possible data loss is up to 19 hours. If the target RPO was 1 hour, that backup strategy does not meet the target.

Replication and backups solve different problems:

| Mechanism | Helps with | Does not automatically solve |
|---|---|---|
| Replication | Keeping a current copy available | Accidental deletion copied to replicas |
| Backup | Recovering older history | Instant failover |

This is why “we have replicas” is not the same as “we can recover from data corruption.” If a mistaken delete is replicated everywhere, you need a historical backup or point-in-time recovery.

## 10. Worked example: checkout outage

Suppose checkout depends on one primary database host. There are four API replicas, but all API replicas need that database. The database host fails. What happens?

The API replicas may still be running, but checkout can still fail because the state dependency is gone. Adding more API replicas does not remove the database single point of failure.

A better deployment diagram would show:

- API instances and where they run
- database primary and standby
- whether the standby is in another failure domain
- replication mode
- backup location and retention
- failover owner or mechanism
- measured RPO and RTO

Example placement:

```text
UniMarket / production
Region R
  Zone A                         Zone B
    API v2 x2                      API v2 x2
    DB primary  --sync replica-->   DB standby

Client -> HTTPS entry point -> API instances
API -> DB endpoint: PostgreSQL :5432, TLS, authenticated, sync
DB -> protected backup store: scheduled backup
```

This improves resilience against a zone or host problem, depending on the exact setup. It still needs review for region failure, entry-point failure, backup restore testing, and operational ownership.

## Exam answer pattern

For deployment questions, use this structure:

1. Name the missing or risky topology fact.
2. Explain why it matters operationally or for security.
3. Propose a concrete diagram or design change.
4. State the remaining limitation or cost.

Example: “The diagram shows three API replicas but not their host or zone placement. If all replicas share one host, host failure removes all of them. Show host/zone boundaries and place replicas across independent failure domains. This still does not protect against a shared database failure unless the database is also made resilient.”

## Guided learning: Follow a request through the deployment

Select each box. The arrows show the illustrative request path, not separate failure domains. Then change the placement in the failure experiment.

### 1. Start outside the trust boundary

A user request begins in an environment the application does not control. Identify what the user can send and where the server first validates identity and input.

**Example:** A valid session can identify Alice; it does not permit reading Bob’s order.

**Common trap:** A request arriving from an internal address is not automatically authorised.

### 2. Choose a backend

The entry point routes traffic to a running instance. Its own placement and health matter: multiple backends do not help when the only entry point fails.

**Example:** An L4 balancer assigns a connection. Many HTTP/2 streams can reuse that one assignment.

**Common trap:** A box labelled load balancer does not prove that requests are balanced at the application layer.

### 3. Look outside the replica boxes

Trace each instance to its host, zone and region. Redundancy protects only against failures that leave a usable instance and its dependencies alive.

**Example:** Two API processes on Host A both disappear when Host A is lost.

**Common trap:** Counting replicas without examining their common parents hides shared failure.

### 4. Follow the dependency to state

The request may still depend on one database. Show the primary, standby, promotion path and backup history. Confirm the recovery targets through exercises.

**Example:** A standby can support continuity after host loss; a historical backup can recover an accidental deletion copied to that standby.

**Common trap:** Replication is not a substitute for recoverable history.

### Check 1: Two APIs are in separate zones, but both use one database host. That database host fails. What is the strongest conclusion?

- The replicas guarantee checkout works.
- The database dependency may stop both request paths.
- There must be zero data loss.

**Answer:** The database dependency may stop both request paths. Correct. Review the complete request path, including state and failover.

### Check 2: A deletion reaches the primary and its live replica. Which control addresses recovery of the older records?

- A recoverable historical backup or point-in-time recovery path.
- One more replica of the already deleted state.
- Increasing the HTTP timeout.

**Answer:** A recoverable historical backup or point-in-time recovery path. Correct. Test restoration and retention rather than assuming a copy is usable.
