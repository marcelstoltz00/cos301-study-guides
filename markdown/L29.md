## 1. Security is not a final checkbox

Secure software development means building software so that it resists misuse, protects important data, and can be maintained when new threats or vulnerabilities appear.

The key idea: security is a **lifecycle property**. It starts when requirements are written and continues after release. A penetration test near the end can find problems, but it cannot magically fix a design that was built around unsafe assumptions.

Example: if a system stores every tenant's records in one table and never checks which tenant the user belongs to, a late security scan might reveal the problem. But the real fix may require changing data access patterns, tests, and business rules. That is much harder than designing the access rule early.

NIST SSDF groups secure development work into four broad areas:

| Area | Easy meaning | Why it matters |
|---|---|---|
| Prepare the organisation | Set roles, standards, tools, and expectations | Teams need a repeatable way to build securely |
| Protect the software | Protect code, secrets, builds, and artifacts | Attackers may target the development pipeline |
| Produce well-secured software | Design, code, and test with security in mind | Most security defects are cheaper to fix early |
| Respond to vulnerabilities | Patch, investigate, and prevent repeat issues | Security changes after release as new facts appear |

The bigger picture is responsibility. A secure development process creates evidence: requirements, threat models, reviews, tests, findings, fixes, and response records.

## 2. The basic vocabulary: asset, threat, vulnerability, risk

These words are easy to mix up, so keep them separate:

| Term | Meaning | Example |
|---|---|---|
| Asset | Something valuable that must be protected | Student marks, payment records, service availability |
| Threat | Possible cause of harm | Someone tries to read another student's mark |
| Vulnerability | Weakness that can be exploited | API does not check record ownership |
| Risk | Likelihood and impact in context | High risk if many records are exposed through the internet |

Why this matters: you cannot choose good controls if you do not know what you are protecting and how it might be harmed.

Security goals are often described as CIA:

| Goal | Meaning | Example failure |
|---|---|---|
| Confidentiality | Prevent unauthorised disclosure | Student sees another student's result |
| Integrity | Prevent unauthorised modification | Mark is changed without permission |
| Availability | Keep service usable when needed | Results portal is down during publication |

Good security requirements are observable. “The system must be secure” is too vague. “A student may read only their own submissions” is testable. You can write positive and negative tests for it.

## 3. Threat modelling: thinking before something breaks

Threat modelling is a structured way to ask: **How could this system be abused, and what are we doing about it?**

A simple process:

1. Define the scope.
2. Identify valuable assets.
3. Draw actors, data stores, and data flows.
4. Mark trust boundaries.
5. Ask what could go wrong at each boundary.
6. Choose mitigations.
7. Assign owners and tests.

This helps because security problems often appear at boundaries: browser to server, public network to private network, user to admin function, app to database, trusted service to third-party API.

STRIDE is a checklist:

| STRIDE | Plain question |
|---|---|
| Spoofing | Can someone pretend to be another identity? |
| Tampering | Can data or requests be changed? |
| Repudiation | Can someone deny doing something because evidence is missing? |
| Information disclosure | Can private information leak? |
| Denial of service | Can the system be made unavailable? |
| Elevation of privilege | Can someone gain powers they should not have? |

Example: for file upload, do not only ask “does upload work?” Ask who may upload, what sizes are allowed, where files are stored, who may download them, whether the parser is safe, whether names can escape folders, and whether uploaded content can execute.

## 4. Authentication and authorisation are different

Authentication means proving identity: “This request is from Alice.”

Authorisation means checking permission: “Is Alice allowed to read this specific result?”

A logged-in user is not automatically allowed to do everything. This is one of the most important security ideas in web applications.

Example:

```text
GET /results/123
```

Even if Alice is logged in, the server must check whether result 123 belongs to Alice, or whether Alice has a role that permits reading it. Hiding the link in the UI is not enough, because someone can call the API directly.

Server-side checks matter because the client is outside the trust boundary. A browser, mobile app, or HTTP tool can send unexpected requests. The server must enforce the real rule.

## 5. Design principles in plain language

| Principle | Easy meaning | Why it matters |
|---|---|---|
| Least privilege | Give only the permissions needed | Limits damage if an account or service is compromised |
| Deny by default | Reject unless permission is explicitly granted | Missing rules should not become accidental access |
| Complete mediation | Check access on every relevant request | Attackers may bypass the normal UI path |
| Defence in depth | Use multiple layers of controls | One failed control should not expose everything |
| Minimise attack surface | Remove unnecessary entry points | Fewer exposed features means fewer places to attack |
| Fail securely | Errors should not grant access | A broken policy check must not become “allow” |

These principles are not abstract slogans. They help you explain design choices in an exam. For example: “We deny by default because if the permission service cannot answer, granting access would expose protected data.”

## 6. Common implementation failures and safer patterns

| Failure | What goes wrong | Safer pattern |
|---|---|---|
| SQL injection | User data is treated as query syntax | Parameterised queries |
| XSS | Untrusted data becomes executable page content | Context-aware output encoding or safe rendering |
| Broken object access | User can access another user's object | Server-side object and tenant checks |
| Secret exposure | Credentials are committed or logged | Secret manager, restricted access, scanning |
| Unsafe errors | Stack traces or tokens leak | Controlled messages and filtered logs |
| Resource exhaustion | Valid-looking requests consume too much | Limits, timeouts, quotas, rate controls |

The “why” behind SQL injection: a query is instructions to the database. If you build it by concatenating user input, the user may be able to change the instructions. Parameterised queries keep data values separate from executable query structure.

The “why” behind output encoding: the same input can be safe in one context and unsafe in another. Text inside HTML, an attribute, a script, and a URL each have different escaping rules.

Client-side validation is useful for friendly feedback, but it is not enforcement. The server must validate type, range, length, format, and business meaning at the boundary it controls.

## 7. Cryptography: use the right tool for the job

Do not invent cryptography. Use reviewed libraries and current recommended configurations.

Keep these concepts separate:

| Concept | Meaning | Example use |
|---|---|---|
| Encoding | Changes representation, reversible without a secret | Base64 |
| Hashing | One-way digest in intent | Password hashing with salt and work factor |
| Encryption | Reversible with a key | Protecting data in transit or at rest |
| Signing | Proves integrity and publisher/key holder | Release artifact signature |

A common mistake is thinking that encoding is security. Base64 text may look unreadable, but anyone can decode it. It is not encryption.

## 8. Verification: different techniques find different problems

Security verification needs multiple techniques because each has blind spots.

| Technique | What it does | What it may miss |
|---|---|---|
| SAST | Looks at source or compiled code without running it | Runtime configuration and business context |
| DAST | Tests a running application from the outside | Hidden code paths and source-level causes |
| SCA | Checks third-party dependencies | First-party business logic bugs |
| Secret scanning | Looks for exposed credentials | Misconfigured permissions without exposed secrets |
| Manual review | Uses human judgement on design and code | Can be inconsistent without checklist and time |
| Penetration testing | Authorised attack-style testing | Limited by scope and time |

A clean scanner report means “this scanner found no configured findings.” It does not mean “the application has no vulnerabilities.”

Good response pattern: triage the finding, reproduce it where useful, assess exposure, fix the cause, add a regression test, and document the decision.

## 9. Supply chain and release integrity

Your own code is not the only risk. Modern systems depend on packages, build tools, CI scripts, container images, and deployment credentials.

Important controls:

- review dependency changes
- pin or record versions where appropriate
- maintain a software component inventory
- restrict build and release credentials
- separate untrusted contributions from privileged release steps
- sign or verify artifacts where the environment supports it
- keep rollback plans realistic

An SBOM is a list of software components. It helps investigation, but it is not a certificate that the software is safe.

A signed artifact helps verify integrity and origin. But if malicious code was signed by a trusted pipeline, the signature only proves where it came from. Review and testing still matter.

## 10. Worked example: multi-tenant results API

For:

```text
GET /results/{id}
```

the secure flow should be:

1. Authenticate the caller.
2. Load the result through a tenant-aware access path.
3. Check whether this caller may read this result.
4. Use parameterised data access.
5. Return a controlled error if access is denied.
6. Log the security event without leaking tokens or full sensitive content.

Tests should include:

- owner can read their own result
- another student cannot read it
- assigned tutor can read permitted modules
- unassigned tutor is denied
- missing session is denied
- malformed ID is handled safely
- unavailable policy service fails securely

If a vulnerable release existed, response work includes containment, log review, user/data impact assessment, fix, verification, and regression coverage.

## Exam answer pattern

Use this structure:

1. Identify the asset.
2. Identify the abuse path or weakness.
3. Explain the control and why it works.
4. Give one positive test and one negative test.
5. State a limitation or operational follow-up.

Example: “The asset is student result confidentiality. The abuse path is changing the result ID to another student’s record. The control is server-side object authorisation on every `GET /results/{id}` request. Test that Alice can read Alice’s result and cannot read Bob’s result. Also audit denied attempts and add regression tests.”

## Guided learning: Watch a protected request pass through security checks

The arrows mean “the request must pass the next check”. One successful check does not imply the later checks succeeded.

### 1. Establish who is calling

Validate the caller’s credentials or session using the intended mechanism. Treat an identity supplied in an arbitrary request field as an assertion until verified.

**Example:** A valid session identifies student Alice.

**Common trap:** A logged-in user is not an administrator by default.

### 2. Check this action on this object

Evaluate the verified identity, requested operation and resource scope. Do this on the server for every relevant access, including direct API calls.

**Example:** Alice may read her own result; a tutor may read results only for assigned modules.

**Common trap:** Hiding a button or using a long record ID is not an access-control decision.

### 3. Enforce the operation’s constraints

Check types, bounds and business rules at the server boundary. Keep input values separate from executable syntax and use safe rendering for output.

**Example:** An authorised mark update still rejects a value outside the allowed range.

**Common trap:** An authorised user can still submit malformed or dangerous data.

### 4. Perform a bounded, attributable operation

Apply the change and record useful security events without exposing secrets. Handle failures accurately and investigate unexpected access patterns.

**Example:** An audit event identifies the actor and operation without copying their session token into logs.

**Common trap:** A detailed audit log does not undo an unauthorised disclosure.

### Interactive experiment: Try the access decision

A deliberately small policy: owners can read their result; assigned tutors can read or amend it. An unavailable permission service denies the protected operation. Open the HTML guide to change the inputs and see the result.

### Check 1: The application accepts only digits in an order ID. Is another user’s numeric order ID now safe to return?

- Yes, validation establishes ownership.
- No, object-level authorisation is still required.
- Yes, if the request uses TLS.

**Answer:** No, object-level authorisation is still required. Correct. A well-formed identifier can still refer to a forbidden record.

### Check 2: A security scan has no findings. Which statement can you defend?

- The application has no vulnerabilities.
- The checks detected no findings under their configuration.
- Manual access-control tests are redundant.

**Answer:** The checks detected no findings under their configuration. Correct. Describe the evidence and complement its blind spots.
