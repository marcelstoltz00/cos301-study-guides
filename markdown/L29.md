## 1. Security is a lifecycle property

Secure development reduces the likelihood and impact of exploitable defects from requirements through maintenance. A penetration test near release cannot compensate for an architecture that exposes every tenant's records. Security work needs owners, acceptance criteria and evidence.

NIST SSDF v1.1 groups practices into **Prepare the Organization, Protect the Software, Produce Well-Secured Software, and Respond to Vulnerabilities**. Use these as a lifecycle checklist, not as a claim that a tool or certificate proves a product secure.

| Stage | Example activity | Reviewable output |
|---|---|---|
| Requirements | Identify assets, misuse cases and access rules | Security acceptance criteria |
| Design | Model trust boundaries and abuse paths | Threat model and mitigations |
| Implementation | Apply secure patterns and review sensitive code | Reviewed change and unit tests |
| Verification | Combine static, dynamic and dependency checks | Findings with triage decisions |
| Release | Protect build credentials and artifact integrity | Traceable release and rollback plan |
| Operation | Monitor abuse, patch and investigate | Response records and regression tests |

## 2. Assets, threats and risk

An **asset** has value, such as student records or payment integrity. A **threat** is a possible cause of harm. A **vulnerability** is a weakness that can be exploited. **Risk** considers likelihood and impact in context. Severity scores assist prioritisation but do not replace analysis of exposure, reachability and business consequences.

Write security requirements as observable rules: “A student may read only their own submissions; a tutor may read submissions for assigned modules.” Include negative tests: another student's identifier must not bypass the rule. Confidentiality protects against unauthorised disclosure, integrity against unauthorised modification, and availability against unacceptable loss of service.

## 3. Threat modelling

Start with scope and assets, draw actors, stores and data flows, then mark trust boundaries. Examine misuse cases at each crossing, choose mitigations, assign owners and plan verification. Update the model when dependencies, privileges or deployment change.

STRIDE prompts six questions: **Spoofing** identity, **Tampering** with data, **Repudiation** of actions, **Information disclosure**, **Denial of service**, and **Elevation of privilege**. It helps organise reasoning; it does not prove the threat list complete.

Example: a file-upload service must consider who can upload, where files are stored, who can read them, size limits, allowed formats, parser behaviour and whether an uploaded file could execute. Checking only the filename extension is insufficient.

## 4. Design principles

- **Least privilege:** give users, workloads and build jobs only the permissions they need.
- **Deny by default:** absent an explicit permission, reject access.
- **Complete mediation:** verify permissions on every relevant server-side request.
- **Defence in depth:** combine controls with different failure modes, such as permission checks, network restrictions and audit monitoring.
- **Minimise attack surface:** remove unused endpoints, debug access and unnecessary privileges.
- **Fail securely:** an error in access checking must not turn into permission granted.

Authentication establishes identity. Authorisation decides whether that identity may perform an action on a resource. A logged-in user can still be unauthorised. OWASP recommends default denial and permission validation on every request; hiding a UI control is not enforcement.

## 5. Secure implementation patterns

| Failure mode | Safer pattern | Why the easy shortcut fails |
|---|---|---|
| SQL injection | Parameterised queries; allowlist any unavoidable dynamic identifiers | Concatenated strings mix data with executable syntax |
| Cross-site scripting | Context-appropriate output encoding and safe rendering APIs | Input validation alone does not handle every output context |
| Broken object access | Server-side action, object and tenant checks | An unpredictable ID is not permission |
| Secret exposure | Managed secret injection and restricted access | A secret committed once can remain in history |
| Unsafe errors/logs | Useful internal diagnostics with sensitive-data filtering | Stack traces or tokens can leak through responses and logs |
| Resource exhaustion | Size limits, timeouts, bounded work and rate controls | Valid-looking requests can still consume excessive resources |

Client-side validation improves feedback; server-side validation enforces constraints at the trust boundary. Validate type, range, length and semantic rules. Do not replace domain checks with a single regular expression.

Use established password-hashing and cryptographic libraries with reviewed configuration; do not invent cryptography. Encryption, hashing and encoding serve different purposes: encryption is reversible with a key, hashing is one-way in intent, and encoding simply changes representation.

## 6. Verification techniques

**SAST** examines source or intermediate code without running the application. **DAST** exercises a running application externally. **SCA** examines dependencies and associated component risk, often including known vulnerability and licence information. Secret scanning looks for exposed credentials. Manual review and authorised penetration testing explore contextual weaknesses that automated tools miss.

Use several techniques because their blind spots differ. Triage findings, reproduce where appropriate, assess exposure, fix the cause and add a regression test. A clean scanner report is evidence about the checks performed, not proof of no vulnerabilities.

## 7. Supply chain and release integrity

Review dependency changes, record exact versions where appropriate, maintain a component inventory, and patch through a tested process. A software bill of materials (**SBOM**) lists components; it is not a security certificate. Restrict build credentials, separate untrusted contributions from privileged release steps, and track what source produced each release.

A signed artifact supports integrity and publisher verification when trust is configured correctly; malicious code can still be signed. Test release behaviour and support rollback. Keep security work connected to the normal change-review process.

## 8. Worked example: multi-tenant results API

For `GET /results/{id}`, authenticate the caller, load the relevant record through a tenant-aware access path, and enforce an explicit read rule. Use parameterised data access. Return a controlled failure without exposing another student's details. Audit sensitive access without logging tokens or full result contents unnecessarily.

Test owner access, another student, an unassigned tutor, a missing session, malformed input and an unavailable policy service. For a vulnerable earlier release, investigate access logs, contain exposure, deploy and verify the fix, and add regression tests. Security response feeds back into design and coding standards.

**Exam answer pattern:** identify the asset and abuse path, explain the control's mechanism, give a positive and negative test, then state a limitation or operational follow-up.

## Guided learning: Watch a protected request pass through security checks

The arrows mean “the request must pass the next check”. One successful check does not imply the later checks succeeded.

### 1. Establish who is calling

Validate the caller’s credentials or session using the intended mechanism. Treat an identity supplied in an arbitrary request field as an assertion until verified.

**Example:** A valid session identifies student Alice.

**Common trap:** A logged-in user is not an administrator by default.

### 2. Check this action on this object

Evaluate the verified identity, requested operation and resource scope. Do this on the server for every relevant access, including direct API calls.

**Example:** Alice may read her own result; a tutor may read results only for assigned modules.

**Common trap:** Hiding a button or using a long record ID is not an access-control decision.

### 3. Enforce the operation’s constraints

Check types, bounds and business rules at the server boundary. Keep input values separate from executable syntax and use safe rendering for output.

**Example:** An authorised mark update still rejects a value outside the allowed range.

**Common trap:** An authorised user can still submit malformed or dangerous data.

### 4. Perform a bounded, attributable operation

Apply the change and record useful security events without exposing secrets. Handle failures accurately and investigate unexpected access patterns.

**Example:** An audit event identifies the actor and operation without copying their session token into logs.

**Common trap:** A detailed audit log does not undo an unauthorised disclosure.

### Check 1: The application accepts only digits in an order ID. Is another user’s numeric order ID now safe to return?

- Yes, validation establishes ownership.
- No, object-level authorisation is still required.
- Yes, if the request uses TLS.

**Answer:** No, object-level authorisation is still required. Correct. A well-formed identifier can still refer to a forbidden record.

### Check 2: A security scan has no findings. Which statement can you defend?

- The application has no vulnerabilities.
- The checks detected no findings under their configuration.
- Manual access-control tests are redundant.

**Answer:** The checks detected no findings under their configuration. Correct. Describe the evidence and complement its blind spots.
