## Security Testing — Red Team vs. Blue Team

> **Note on this lecture's source material:** the original L24 slide deck was almost entirely a company profile/recruitment presentation (from guest presenters at Integrity360), and the actual technical content was delivered as a **live, unscripted Red Team vs. Blue Team demonstration** that isn't captured in any slide text. The content below is therefore built from standard, industry-standard security testing knowledge covering the concepts a live red-team/blue-team demo would typically be built around, rather than transcribed from specific lecture slides. Treat this as solid general preparation for the topic area, and cross-check against your own notes from the live demo if you took any.

### 1. What Is Security Testing?

Security testing is the practice of deliberately probing a system for weaknesses **before an attacker does**, so they can be fixed proactively. It spans a spectrum from automated scanning to fully manual, human-driven attack simulation:

- **Vulnerability scanning** — automated tools compare a system against known-vulnerability databases (e.g. CVEs) and misconfiguration checklists. Fast, cheap, broad coverage, but shallow — it finds known patterns, not novel logic flaws.
- **Vulnerability assessment** — a broader, still mostly tool-driven review of a system's security posture, typically producing a prioritized list of weaknesses.
- **Penetration testing ("pentesting")** — a human tester actively attempts to exploit vulnerabilities to demonstrate real, chained impact (e.g. "this misconfiguration lets me read the admin's session token, which lets me impersonate them, which lets me exfiltrate customer data") — going beyond just *listing* weaknesses to *proving* what an attacker could actually achieve.
- **Red team engagement** — a broader, more adversarial, often longer-running simulation of a real attacker, frequently without the defensive (blue) team knowing in advance, testing not just technical vulnerabilities but detection and response capability too.

### 2. Red Team vs. Blue Team vs. Purple Team

| Team | Role |
|---|---|
| **Red Team** | Plays the attacker. Attempts to breach the system using real-world adversary techniques — reconnaissance, exploitation, lateral movement, exfiltration — to test both technical defenses and human/process response. |
| **Blue Team** | Plays the defender. Responsible for detecting, responding to, and containing the red team's (or a real attacker's) activity — monitoring logs, alerting on anomalies, investigating incidents, and hardening the environment. |
| **Purple Team** | Not a separate team but a **collaborative mode** — red and blue actively share findings and techniques *during* the exercise (rather than only in a report afterward), specifically to accelerate the blue team's detection capability improvements. |

**Why run both sides at once (a red/blue exercise) rather than just a pentest report:** a pentest report alone tells you *what* vulnerabilities exist. A live red-vs-blue exercise additionally tests whether your **detection and response process** actually works in practice — did the blue team notice the attack at all, how long did it take them, and what did they do about it. Many organisations have real vulnerabilities *and* real gaps in their ability to detect exploitation of those vulnerabilities — a red/blue exercise surfaces both.

### 3. A Typical Attack Lifecycle (What the Red Team Follows)

A common way to structure an attack simulation, loosely based on frameworks like the Cyber Kill Chain / MITRE ATT&CK:

1. **Reconnaissance** — gather information about the target: exposed services, employee names/emails (for phishing), technology stack, public code repositories, leaked credentials.
2. **Initial access** — get a first foothold, e.g. via a phishing email with a malicious attachment, exploiting an internet-facing vulnerability, or using a leaked/weak credential.
3. **Execution** — run code on the compromised system.
4. **Persistence** — ensure continued access even if the initial entry point is closed (e.g. a reboot, a patched vulnerability) — e.g. a scheduled task, a new admin account, a backdoor.
5. **Privilege escalation** — move from a low-privilege foothold (e.g. a regular user's laptop) to higher privileges (e.g. domain administrator).
6. **Lateral movement** — move from the initially compromised system to other systems on the network, using harvested credentials or trust relationships.
7. **Exfiltration / impact** — achieve the actual objective: stealing data, encrypting systems (ransomware), or disrupting operations.

**What the Blue Team is doing throughout:** monitoring logs and alerts (often via a SIEM — Security Information and Event Management system) for signs of each stage above, investigating anomalies, and — once an incident is confirmed — following an incident response process (containment, eradication, recovery, and a post-incident review).

### 4. Application-Layer Security Testing: The OWASP Top 10

For testing web applications specifically (as opposed to network/infrastructure), the **OWASP Top 10** is the industry-standard baseline of the most critical risks to test for, including (representative categories, exact list/wording is periodically revised):

- **Broken Access Control** — a user can access data or perform actions they shouldn't be authorized for (e.g. changing a URL parameter to view another user's account).
- **Injection** (e.g. SQL injection) — untrusted input is concatenated into a query/command, letting an attacker alter its meaning (e.g. bypassing a login check, or reading arbitrary database rows).
- **Cryptographic Failures** — sensitive data transmitted or stored without adequate encryption, or using weak/broken cryptographic algorithms.
- **Security Misconfiguration** — default credentials left in place, unnecessary features/ports enabled, verbose error messages leaking internal details.
- **Vulnerable and Outdated Components** — using a library or dependency with a known, unpatched vulnerability (directly connecting to the CVE/dependency-scanning material covered in the DevSecOps lecture).
- **Identification and Authentication Failures** — weak password policies, missing multi-factor authentication, session tokens that don't expire or aren't invalidated on logout.
- **Server-Side Request Forgery (SSRF)** — an attacker tricks the server into making a request to an unintended destination (e.g. reaching internal-only services from an external-facing input).

### 5. Common Technical Testing Techniques

- **SQL Injection (SQLi):** submitting crafted input like `' OR '1'='1` into a query built by string concatenation, to bypass authentication or extract data. Defended against by using parameterised queries/prepared statements rather than concatenating user input into SQL.
- **Cross-Site Scripting (XSS):** injecting malicious script into a web page that then executes in another user's browser (e.g. via an unsanitised comment field), potentially stealing session cookies or performing actions as that user. Defended against by properly escaping/encoding output and using a strict Content-Security-Policy.
- **Phishing / social engineering:** targeting people rather than technology directly — a crafted email tricking an employee into entering credentials on a fake login page, or opening a malicious attachment. Often the initial access vector in real-world breaches, which is why red team exercises frequently include a phishing component alongside purely technical testing.
- **Privilege escalation:** exploiting a misconfiguration or vulnerability to gain higher-level access than originally granted (e.g. a web app running as root, so compromising the app grants root on the host).
- **Credential stuffing / password attacks:** trying previously-leaked username/password combinations (credential stuffing) or systematically guessing passwords (brute force) against a login endpoint.

### 6. Blue Team Defensive Concepts

- **SOC (Security Operations Center):** a dedicated team/facility that continuously monitors an organisation's systems for security events, typically staffed to provide 24/7 coverage given attacks aren't limited to business hours.
- **SIEM (Security Information and Event Management):** a system that aggregates logs and security events from across an organisation's infrastructure into one place, correlating them to surface suspicious patterns a human wouldn't spot by looking at any single log source alone.
- **Detection engineering:** writing and tuning the specific rules/alerts a SIEM (or other tooling) uses to flag suspicious activity — a red team exercise is a direct way to test whether these detections actually fire when they should.
- **Incident response:** the structured process followed once a security incident is confirmed — typically covering identification, containment (stopping the attack from spreading further), eradication (removing the attacker's access), recovery (restoring normal operation), and a post-incident/lessons-learned review.
- **Defense in depth:** the principle that no single security control should be relied upon alone — layering multiple, independent controls (network segmentation, endpoint detection, access control, monitoring) means a failure or bypass of any one layer doesn't immediately lead to full compromise.

### 7. Why Run Red/Blue Exercises at All

- They test the **whole system**, not just the code — including human process, detection tooling, and response speed, which a purely automated vulnerability scan cannot evaluate.
- They surface **detection gaps**, not just vulnerability gaps — a known vulnerability that the blue team would actually catch and respond to quickly is a very different risk than one that would go completely unnoticed.
- They build **real operational muscle memory** for the blue team, under realistic (if simulated) pressure, ahead of facing a genuine incident.
- Findings feed directly back into improving detection rules, patching processes, and security training — closing the loop, conceptually similar to how DevSecOps integrates security checks throughout the development pipeline rather than treating it as a one-time audit.
