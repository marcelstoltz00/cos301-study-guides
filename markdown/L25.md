## API Service Contracts

### 1. The Integration Nightmare

A familiar scenario: the frontend team builds one component, the backend team builds the other. The night before a demo, you attempt to connect them, and absolutely nothing works.

- A lack of upfront agreement leads to integration chaos and massive code blockers.
- Without a standard, you rely on assumptions and "he said, she said" arguments about how the application should communicate.

### 2. What Is an API Service Contract?

**Definition:** an API service contract in software engineering is a **formal agreement** that defines the rules, inputs, outputs, and behaviors in a **machine-readable format** for communication between different software systems or components.

Two complementary framings:

- **The Blueprint:** it formally defines endpoint URLs, allowed HTTP methods (GET, POST, ...), required request payloads, and the exact shape of the response data. It completely eliminates guesswork from the development process by documenting expectations clearly.
- **The Agreement:** it acts as a strict agreement between the backend provider and the frontend consumer. If both teams commit to and strictly adhere to the contract, system integration is virtually guaranteed to work flawlessly on the first try.

### 3. Why Use Contracts (Especially in a Capstone / Team Project)

| Benefit | Description |
|---|---|
| Parallel Development | Backend and frontend can work simultaneously. The frontend uses mock data generated from the contract while the backend builds the actual database logic. |
| Single Source of Truth | Eliminates confusion and arguments about how an endpoint should behave. The written contract is the absolute authority on data structures. |
| Reliable Testing | Enables automated contract testing to ensure neither the frontend nor the backend inadvertently breaks the agreement during subsequent code updates. |

### 4. OpenAPI vs. Swagger — Clearing Up a Common Terminology Confusion

**The Blueprint vs. The Tools:**
- **OpenAPI** — the official, vendor-neutral *specification*. It dictates the rules for writing your API document (in JSON or YAML). It is the blueprint itself.
- **Swagger** — a *suite of tools* (Swagger UI, Swagger Editor, Swagger Codegen) that process an OpenAPI specification to generate documentation and interactive interfaces.

**Analogy:** think of OpenAPI as the universal standard for a USB-C port. Swagger represents a specific brand of tools that utilise and build upon that standard.

**In short:** you *write* an OpenAPI file, and you *view* it using Swagger tools.

### 5. Anatomy of an OpenAPI Document

| Section | Purpose |
|---|---|
| Paths & Operations | Defines the specific endpoints of your application (e.g. `/users` or `/orders`). Specifies the appropriate HTTP method (GET, POST, PUT, DELETE) and details the required query parameters, path variables, and necessary security headers. |
| Components & Schemas | Defines reusable data models. For example, a `User` object must contain an integer `id` and a string `email`. Defining these schemas guarantees data integrity and prevents malformed data exchanges between your components. |

**Example OpenAPI document:**

```yaml
openapi: 3.0.4
info:
  title: Sample API
  description: Optional multiline or single-line description in CommonMark or HTML.
  version: 0.1.9
servers:
  - url: http://api.example.com/v1
    description: Optional server description, e.g. Main (production) server
  - url: http://staging-api.example.com
    description: Optional server description, e.g. Internal staging server for testing
paths:
  /users:
    get:
      summary: Returns a list of users.
      description: Optional extended description in CommonMark or HTML.
      responses:
        "200": # status code
          description: A JSON array of user names
          content:
            application/json:
              schema:
                type: array
                items:
                  type: string
```

### 6. Mock Servers

A **mock server** is a simulated backend service that is automatically generated from an API service contract, such as an OpenAPI specification. Rather than communicating with a real backend, the frontend sends requests to the mock server, which returns predefined example responses that conform to the agreed contract — letting frontend development proceed before any real backend logic exists.

### 7. Contract-First vs. Code-First

| | Contract-First | Code-First |
|---|---|---|
| Approach | Design the API first | Write the backend first |
| Frontend impact | Frontend can start immediately (against the contract/mocks) | Frontend waits (for the real backend to exist) |
| Collaboration | Better collaboration | — |
| Fit | Preferred for teams | Common for prototypes / easier for small projects |

### 8. Integration Workflow (Four Steps)

1. **Design:** the team agrees on the API contract before writing any code. Write the OpenAPI YAML file together.
2. **Mocking:** the frontend uses tools like Swagger to mock backend responses and begins building the UI immediately.
3. **Development:** simultaneously, the backend builds the actual server logic to fulfill the agreed-upon API contract.
4. **Integration:** because both teams strictly followed the blueprint, connecting frontend to backend is seamless.

### 9. Breaking the Contract

Changing the contract means everyone depending on it must update their code accordingly. **To prevent this from silently breaking consumers, use versioning when updating services** — rather than silently changing an existing endpoint's shape.

```
// GET /v1/users              // GET /v2/users
{                              {
  "name": "Alice"                "fullName": "Alice"
}                              }
```

Here, renaming the `name` field to `fullName` is a breaking change — instead of altering `/v1/users` in place (which would silently break every existing consumer expecting `name`), a new `/v2/users` version is introduced, so existing consumers on `/v1` continue to work unaffected while new consumers can adopt `/v2`.

### 10. Capstone Best Practices

- **Design-First Approach:** never write the backend code and then generate the contract as an afterthought. Design the API first, agree on it, and *then* implement.
- **Version Control:** store your `openapi.yaml` file in your main Git repository. Treat it as critical production code that the whole team relies on.
- **Descriptive Errors:** define standard error formats (e.g. `400 Bad Request`, `404 Not Found`) in your contract so the frontend can catch them and display helpful UI messages.
- **Communicate Changes:** if backend developers must alter the contract, the frontend team must be consulted and agree to the update beforehand.
