## Architecture in Practice — Built to Last

### 1. Design Considerations

Best practices when approaching architecture:
- **Determine the non-functional requirements early.**
- **Architecture design first, tech choices later** — decide the structure and responsibilities before picking specific frameworks/products.
- **Avoid over-engineering.**
- **Consider the implementation teams' structure** (their skills, size, and organization shape what architecture they can actually deliver and operate).

**Design considerations to weigh for any system:**
- Security
- Maintainability
- Scalability
- Reliability & Availability
- Extensibility
- Teams and collaboration

## Case Study 1: Road Security (Success Factors: Performance & Scalability)

### 2. Problem Domain

A road-security system aimed at making South Africa safer:
- Performs **license plate lookups** to identify warnings on a vehicle and/or driver.
- The South African Police Service (**SAPS**) can subscribe for **notifications** of vehicle sightings (i.e. get alerted when a flagged plate is seen again).

### 3. Design Challenges

- **Sub-second response times**, with **asynchronous responses** where needed.
- **Scalability** for increased request volumes.
- **Compatibility** with various client environments (different agencies/devices integrating with the system).

### 4. Design: High-Performance, Scalable, Event-Driven Architecture

**Overall architecture shape:** Clients connect through a **Communications** layer, which talks to an **Enterprise Message Bus (EMB)** at the center of the system. The message bus routes messages out to, and receives results back from, four surrounding components:
- **Request Processing** ↔ **License Queries** (the "query" side of the flow)
- **Response Processing** ↔ **Notifications** (the "result" side of the flow)

All four surrounding components communicate with each other only through the central Enterprise Message Bus — none of them call each other directly.

### 5. Component: Clients

**Key considerations:** varying client technologies; sub-second response times required.

**Design decisions:** use **web sockets** as the communication protocol; clients are free to decide which tech stack they implement this with on their end (the protocol is the contract, not the language/framework).

### 6. Component: Communications

**Key considerations:** thousands of simultaneous connections; authentication and authorization; two-way communication; scaling *stateful* services (a websocket connection is inherently stateful — tied to a specific server instance).

**Design decisions:**
- Web sockets for communication (enabling genuine two-way, low-latency messaging, unlike simple request/response HTTP).
- Authentication through **issued certificates** (rather than e.g. username/password per message).
- A **Redis cache** to share state *between multiple instances* of the communications service — since a client's websocket connection is pinned to one specific server instance, but the system runs many instances, Redis lets those instances coordinate (e.g. to know which instance holds which client's connection).

### 7. Component: Request Processing

**Key considerations:** determine which sources need to be queried for a given request; specify whether responses should be combined or returned separately.

**Design decisions:**
- Receive **one** incoming request, then create separate messages for each operation that needs to happen — enabling those operations to run **in parallel** rather than sequentially.
- Create a **unique identifier** (correlation ID) attached to those messages, so that if configured, the separate results can later be **combined** back into one response tied to the original request.

### 8. Component: License Queries

**Key considerations:** this component has the **most significant impact on response times** (it's doing the actual lookup work); it needs to be **extensible** (new data sources will be added over time).

**Design decisions:**
- **Query sources in parallel** (rather than one at a time) to minimize total response time.
- **Add new query sources as new services**, without impacting or requiring changes to the existing sources — new lookup sources plug in independently.

### 9. Component: Response Processing

**Key considerations:** responses may need to be separated or combined (depending on the original request's configuration); the system experiences **very high load**; scaling *stateful* services is again a concern here (building up a combined response requires tracking partial state until all parallel queries return).

**Design decisions:**
- Each individual response should **already contain information about how to combine it** with others (i.e. carry its own correlation/combination metadata, rather than requiring a separate lookup).
- A **Redis cache** is used to build up the combined-response state across the parallel results as they arrive, before the fully combined response is sent back.

### 10. Component: Notifications

**Key considerations:** clients can **subscribe** to be alerted on specific license plate "hits" (sightings); the system needs to be **extensible** to support additional notification methods over time (e.g. SMS, push, email, a SAPS-specific integration).

**Design decisions:**
- Notifications are sent **in parallel**, specifically so that sending a notification does **not** impact the response time of the original query that's still in flight.
- **Add new notification methods as new services**, without impacting the existing notification services — the same extensibility principle used for License Queries.

## Case Study 2: Financial Services (Success Factors: Maintainability, Availability & Resilience)

### 11. Problem Domain

A large financial-services **group organisation with multiple subsidiaries** ("sub-businesses"), requiring a **unified user experience** across them — despite each subsidiary potentially having its own subsystems, data, and security architecture.

### 12. Design Considerations

- Security & data protection
- Maintainability
- Resilience
- Availability (deployment/DevOps concerns)

### 13. Design: Highly-Available, Resilient, Modular Service-Oriented Architecture

**Overall architecture shape:** client entry points — several web **Modules** (one per subsidiary/business unit) and a **Mobile App** — all route through a single **API Gateway**. The gateway talks to an **Identity** service (handling authentication/authorization for every request) and routes requests onward to the appropriate **Domain Service** (Domain Service-1, Domain Service-2, ... Domain Service-n — one per business domain). Domain Service-1 and Domain Service-2 share a **Cache**, which in turn connects to a **domain-specific policy engine**. Domain Service-n connects onward to its own **domain-specific back-end service**. Each domain service, and the resources behind it, stays logically separated from the others, even though all requests enter through the same gateway.

### 14. Design Area: Security & Data Protection

**Key considerations:** highly sensitive user data; authorization/authentication needed consistently across every subsidiary's traffic.

**Design decisions:**
- **Identity management** — a dedicated identity service (as shown centrally in the architecture) rather than each subsidiary handling auth independently.
- **Single Sign-On (SSO)** — one login session works across all the subsidiaries/modules, delivering the "unified user experience" the problem domain calls for.

### 15. Design Area: Maintainability

**Key considerations:** multiple development teams (likely one per subsidiary); multiple subsystems that need to evolve independently.

**Design decisions:** **modularisation / micro-frontends** — each subsidiary's UI module can be built, changed, and deployed largely independently by its own team, while still composing into one unified application for the end user.

### 16. Design Area: Resilience

**Key considerations:** susceptibility to **existing integration challenges** (a large group organisation likely has legacy or third-party systems behind each domain service that aren't fully reliable).

**Design decisions:**
- **Caching** — reduces how often the system needs to depend on a potentially-unreliable downstream integration to answer a request.
- **Timeouts / retries / backoff strategies** — the standard tactics for tolerating a slow or intermittently-failing dependency, rather than letting one failing integration cascade into a full request failure.

### 17. Design Area: Availability

**Key considerations:** the application is a **24/7 service portal** and therefore cannot be down or unavailable at any time.

**Design decisions:** the **blue/green deployment strategy** — two identical production environments exist ("blue" = the currently live version, "green" = the newly deployed version). A router sits in front of both; it currently directs all live user traffic to the blue (production) environment while the new version is deployed and can be verified in the green environment. When ready, the router switches traffic over to green — achieving a release with effectively zero downtime, since the previously-live environment (now idle) can also serve as an instant rollback target if needed.

## Tools & Techniques

### 18. Design and Modelling Tools

- **UML** (Unified Modelling Language)
- **Sequence diagrams**
- **C4 Model**
- **Infrastructure diagrams**

### 19. What These Tools Are Useful For

- Communicating structure, data, infrastructure, technology choice, scope, and abstraction to different audiences.
- Visualizing system structure.
- **Identifying risks early** — a diagram often surfaces a missing consideration before any code is written.
- Ensuring consistency across the solution — a shared, explicit reference that different teams building different parts of the system can align to.
